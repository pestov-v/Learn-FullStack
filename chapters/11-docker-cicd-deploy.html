Пояснення для п'ятирічного

Уяви, що ти зібрав з LEGO чудову машинку і хочеш показати її другові. Але у друга вдома інші деталі, інший килим і його кіт постійно щось скидає. Машинка в нього розвалюється. Що робити? Покласти машинку разом з усіма її деталями, інструкцією і навіть шматочком твого килима в коробку. Друг відкриває коробку — і машинка працює точнісінько як у тебе, бо всередині коробки все твоє.

Ця коробка — контейнер (container). Інструкція, як зібрати коробку, — Dockerfile. А конвеєр CI/CD — це робот, який щоразу, коли ти щось змінив у машинці, сам перевіряє, чи вона їздить, пакує її в нову коробку і відвозить другові. Тобі лишається тільки будувати.

1. Проблема «у мене працює»

Класична сцена: розробник каже «у мене все працює», а на сервері застосунок падає. Причини можуть бути будь-якими: інша версія Node (у вас 22, на сервері 18), відсутня системна бібліотека для обробки зображень, інший часовий пояс, інша локаль, інший шлях до файлів, змінна середовища, яку хтось колись прописав у себе в .zshrc і забув. Кожен сервер потроху «дрейфує» від еталону, і за рік ніхто не знає, що на ньому насправді встановлено.

Контейнер розв'язує це радикально: ви описуєте все оточення застосунку в коді (Dockerfile) — базову ОС, версію Node, залежності, файли, команду запуску. З цього опису збирається образ (image) — незмінний архів, який однаково запускається на ноутбуці, у CI і на продакшені. Немає «у мене працює» — є «в образі працює», і образ один для всіх.

Чому це важливо

Контейнери — це не лише про «однаково всюди». Вони зробили можливим сучасний деплой: сервер не знає нічого про Node чи Python, він знає лише «запусти образ X». Тому один і той самий сервер може крутити Node-API, Python-воркер і Go-сервіс, не конфліктуючи версіями. А оркестратори (Compose, Kubernetes) можуть перезапускати, масштабувати і переносити контейнери між машинами, бо контейнер — це самодостатня одиниця.

2. Віртуальна машина проти контейнера

До контейнерів ізоляцію давали віртуальні машини (virtual machine, VM): гіпервізор емулює «залізо», і в кожній VM працює повноцінна операційна система зі своїм ядром. Це надійно, але важко: кожна VM важить гігабайти і стартує хвилину.

Контейнер — це не окрема ОС, а ізольований процес на спільному ядрі хоста. Ізоляцію дають механізми ядра Linux: простори імен (namespaces) — процес бачить лише свої файли, мережу, PID-и; контрольні групи (cgroups) — обмеження CPU і пам'яті. Тому контейнер стартує за мілісекунди і важить лише стільки, скільки його файли.

Це не означає, що VM мертві: хмарні провайдери запускають ваші контейнери всередині VM для безпечної ізоляції між клієнтами. На macOS і Windows Docker Desktop також запускає невелику Linux-VM, у якій живуть усі контейнери. Але для розробника одиницею роботи став контейнер.

3. Docker: образ, контейнер, шари, Dockerfile

Образ (image) — це рецепт плюс усі інгредієнти: файлова система, зібрана шар за шаром, і метадані (яку команду запускати, які порти відкривати). Образ незмінний. Контейнер (container) — запущений екземпляр образу: страва, приготована за рецептом. З одного образу можна запустити десять контейнерів, і кожен матиме свою тонку «записувану» плівку поверх спільних шарів образу.

Кожна інструкція у Dockerfile створює новий шар (layer) — різницю у файловій системі відносно попереднього. Шари кешуються: якщо інструкція і її вхідні дані не змінилися, Docker бере готовий шар. Звідси головне правило порядку: те, що змінюється рідко (базовий образ, залежності), кладемо вгору; те, що змінюється часто (код), — вниз. Тоді правка в одному файлі не змушує переустановлювати node_modules.

# Dockerfile — багатоетапна збірка (multi-stage build) для Node-застосунку

# ---------- Етап 1: збірка ----------
# Alpine — мінімальний Linux (~5 МБ). Пінимо мажорну версію Node.
FROM node:22-alpine AS builder

# Усі подальші команди виконуються в цій теці всередині образу
WORKDIR /app

# Вмикаємо pnpm через corepack (вбудований у Node) — без окремої установки
RUN corepack enable

# Спочатку ТІЛЬКИ файли залежностей — щоб шар з node_modules кешувався,
# поки package.json / lock-файл не змінилися
COPY package.json pnpm-lock.yaml ./

# --frozen-lockfile: падати, якщо lock не збігається з package.json (як у CI)
RUN pnpm install --frozen-lockfile

# Тепер решта коду (див. .dockerignore — node_modules і .git сюди не потраплять)
COPY . .

# Компілюємо TypeScript → dist/
RUN pnpm build

# Прибираємо dev-залежності: у runtime нам потрібні лише production
RUN pnpm prune --prod

# ---------- Етап 2: runtime ----------
# Чистий образ: без tsc, vitest, eslint — менший розмір, менша поверхня атаки
FROM node:22-alpine AS runner
WORKDIR /app

# Не запускаємо процес від root: якщо застосунок зламають, шкода обмежена.
# Образ node вже містить користувача "node" з uid 1000.
USER node

# Копіюємо з етапу builder тільки те, що потрібно для запуску.
# --chown робить файли власністю користувача node.
COPY --chown=node:node --from=builder /app/node_modules ./node_modules
COPY --chown=node:node --from=builder /app/dist ./dist
COPY --chown=node:node --from=builder /app/package.json ./

# Змінні середовища за замовчуванням (можна перевизначити при запуску)
ENV NODE_ENV=production PORT=3000

# Документує, який порт слухає застосунок (нічого не «відкриває» сам по собі)
EXPOSE 3000

# Docker перевіряє здоров'я контейнера кожні 30 с через наш /health
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD wget -qO- http://localhost:3000/health || exit 1

# Exec-форма (масив) — процес node стає PID 1 і отримує сигнали напряму
CMD ["node", "dist/server.js"]
# .dockerignore — що НЕ копіювати в образ (як .gitignore для docker build)
node_modules
dist
.git
.env
.env.*
coverage
*.md
.vscode
Dockerfile
compose*.yaml

Чому це важливо: без .dockerignore команда COPY . . затягне локальні node_modules (можливо, зібрані під macOS — і не сумісні з Alpine Linux), файл .env з секретами і всю історію git. Образ роздується, а секрети опиняться в реєстрі.

Підводні камені
  • Shell-форма CMD node dist/server.js запускає /bin/sh -c "node ...": PID 1 — це shell, він не передає SIGTERM дочірньому node, і контейнер зупиняється «жорстко» через 10 с. Завжди використовуйте масив.
  • Alpine і native-модулі. Alpine використовує musl замість glibc; пакети з нативними бінарниками (sharp, bcrypt, prisma) іноді не мають musl-збірки. Тоді беріть node:22-bookworm-slim.
  • COPY . . перед pnpm install — вбиває кеш: будь-яка зміна коду переустановлює всі залежності.

4. Команди, томи, мережі, реєстри

# Зібрати образ з Dockerfile у поточній теці, дати тег (ім'я:версія)
docker build -t notes-api:1.0.0 .

# Запустити контейнер: -d у фоні, -p хост:контейнер, --name для зручності,
# -e змінна середовища, --rm видалити після зупинки
docker run -d --name notes -p 3000:3000 -e DATABASE_URL=postgres://... notes-api:1.0.0

docker ps                    # запущені контейнери
docker logs -f notes         # логи в реальному часі (stdout/stderr контейнера)
docker exec -it notes sh     # зайти всередину працюючого контейнера
docker stop notes            # SIGTERM, через 10 с — SIGKILL
docker rm notes              # видалити зупинений контейнер
docker image ls              # локальні образи
docker system prune          # прибрати зупинені контейнери, невикористані образи і кеш

Томи (volumes)

Файлова система контейнера зникає разом із ним. Для даних, які мають пережити перезапуск (база даних, завантажені файли), використовують томи: Docker зберігає їх окремо і монтує в контейнер. Є два види: іменовані томи (-v pgdata:/var/lib/postgresql/data) — Docker керує ними сам, це правильний вибір для продакшену; і bind mount (-v ./src:/app/src) — пряме прокидання теки з хоста, зручно для розробки з гарячим перезавантаженням.

Мережі (networks)

Кожен контейнер має власний мережевий стек. Контейнери в одній користувацькій мережі бачать один одного за іменем: контейнер app підключається до postgres://db:5432, де db — ім'я контейнера, яке Docker резолвить через вбудований DNS. Порт -p 3000:3000 пробиває отвір із хоста в контейнер; без нього ззовні контейнер недоступний — і для бази даних це саме те, що треба.

Реєстри (registries)

Реєстр — це «GitHub для образів»: сховище, куди ви push-ите образ із CI, а сервер pull-ить його. Docker Hub — публічний за замовчуванням (звідти беруться node, postgres). GitHub Container Registry (GHCR, ghcr.io/user/repo) — зручний, бо живе поруч із кодом і має вбудовану автентифікацію в Actions. Хмарні: AWS ECR, Google Artifact Registry.

# Тег з адресою реєстру — і push
docker tag notes-api:1.0.0 ghcr.io/olya/notes-api:1.0.0
docker login ghcr.io -u olya          # токен з правами write:packages
docker push ghcr.io/olya/notes-api:1.0.0

# На сервері
docker pull ghcr.io/olya/notes-api:1.0.0

5. Docker Compose: app + Postgres + Redis

Реальний застосунок — це кілька контейнерів: API, база, кеш, можливо воркер. Запускати їх вручну п'ятьма командами docker run з правильними мережами — мука. Docker Compose описує всю зв'язку в одному файлі і піднімає її однією командою.

# compose.yaml (Compose v2 більше не потребує поля "version")
services:
  app:
    build: .                          # збирати з Dockerfile у поточній теці
    image: ghcr.io/olya/notes-api     # ім'я, під яким зберегти зібраний образ
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: production
      PORT: 3000
      # Хост "db" — ім'я сервісу нижче; Compose створює мережу і DNS сам
      DATABASE_URL: postgres://notes:${POSTGRES_PASSWORD}@db:5432/notes
      REDIS_URL: redis://cache:6379
    env_file: .env                    # додаткові змінні з файлу (не комітити!)
    depends_on:
      db:
        condition: service_healthy    # чекати не просто старту, а готовності
      cache:
        condition: service_started
    restart: unless-stopped           # підняти після падіння або перезавантаження хоста
    deploy:
      resources:
        limits: { cpus: "1.0", memory: 512M }   # cgroups: не дати з'їсти весь сервер
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/health"]
      interval: 30s
      timeout: 3s
      retries: 3

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: notes
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}   # береться з .env або оточення
      POSTGRES_DB: notes
    volumes:
      - pgdata:/var/lib/postgresql/data          # дані переживуть перезапуск
      - ./db/init:/docker-entrypoint-initdb.d:ro # SQL-скрипти при першому старті
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U notes -d notes"]
      interval: 5s
      timeout: 3s
      retries: 10
    # Порт НЕ публікуємо: база доступна лише всередині Compose-мережі

  cache:
    image: redis:7-alpine
    command: ["redis-server", "--maxmemory", "128mb", "--maxmemory-policy", "allkeys-lru"]
    volumes:
      - redisdata:/data

volumes:
  pgdata:
  redisdata:
docker compose up -d --build     # зібрати і підняти все у фоні
docker compose ps                # стан сервісів + healthy/unhealthy
docker compose logs -f app       # логи одного сервісу
docker compose exec db psql -U notes   # консоль Postgres
docker compose down              # зупинити і видалити контейнери (томи лишаються)
docker compose down -v           # ...і томи теж (дані зникнуть!)

Ключові моменти: depends_on з condition: service_healthy — без цього app стартує, поки Postgres ще ініціалізується, і падає з «connection refused». healthcheck визначає, що означає «здоровий» для кожного сервісу. Порт бази не публікується назовні — це і безпека, і відсутність конфліктів з локальним Postgres. Для розробки часто тримають окремий compose.override.yaml, який Compose підхоплює автоматично: там bind-mount коду, команда pnpm dev і опублікований порт бази для DBeaver.

Спробуй сам
  1. Візьміть API нотаток з розділу 04, додайте Dockerfile і .dockerignore з цього розділу. Зберіть образ і подивіться його розмір через docker image ls. Потім приберіть multi-stage (усе в одному етапі) і порівняйте — різниця буде у сотні мегабайт.
  2. Напишіть compose.yaml з app + db. Запустіть, створіть нотатку через curl, виконайте docker compose down і up — нотатка має залишитися (том). Тепер down -v — нотатка зникне.
  3. Змініть один рядок у коді і перезберіть. У виводі docker build знайдіть рядки CACHED — переконайтеся, що pnpm install не запускався знову.
  4. Зайдіть у контейнер (docker compose exec app sh) і виконайте whoami — має бути node, не root.

6. 12-factor, конфігурація і секрети

«The Twelve-Factor App» — маніфест від творців Heroku (2011), який досі є базовим чек-листом для застосунків, що деплояться у хмару. Найважливіші пункти для нас:

  • Codebase — один репозиторій, багато деплоїв (dev, staging, prod) з одного коду.
  • Dependencies — усі залежності явно оголошені (package.json + lock), нічого «встановленого на сервері».
  • Config — конфігурація, яка відрізняється між середовищами (URL бази, ключі), живе у змінних середовища, а не в коді. Один образ — різні env.
  • Backing services — база, кеш, пошта — це приєднані ресурси, які підмінюються через конфіг без зміни коду.
  • Build, release, run — три окремі етапи: збірка образу, поєднання з конфігом, запуск. Не можна змінювати код у runtime.
  • Processes — застосунок не зберігає стан у пам'яті чи на диску між запитами (stateless); сесії — у Redis, файли — в object storage. Тоді можна запускати N копій.
  • Port binding — застосунок сам слухає порт, а не покладається на зовнішній сервер застосунків.
  • Disposability — швидкий старт, коректна зупинка за SIGTERM (див. graceful shutdown нижче).
  • Dev/prod parity — розробка максимально схожа на продакшн: та сама база (Postgres, а не SQLite «для зручності»), той самий образ.
  • Logs — писати в stdout, а не у файли; збиранням займається платформа.

Секрети

Пароль бази, ключ Stripe, JWT-секрет — це секрети (secrets). Правила: ніколи не в git, ніколи не в Dockerfile (ENV SECRET=... залишається в шарі образу назавжди — його можна витягти через docker history), ніколи не в аргументах збірки. Куди можна: змінні середовища, які підставляє платформа (GitHub Secrets → env у workflow; Vercel/Fly/Railway мають свої сховища), Docker secrets або файли, змонтовані в /run/secrets/, менеджери секретів (AWS Secrets Manager, HashiCorp Vault, Doppler, 1Password CLI). Локально — .env у .gitignore плюс .env.example без значень у репозиторії, щоб колеги знали, які змінні потрібні.

// src/config.ts — валідуємо змінні середовища при старті, а не при першому запиті
import { z } from "zod";

const schema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
  JWT_SECRET: z.string().min(32, "JWT_SECRET має бути хоча б 32 символи"),
});

// Якщо чогось бракує — застосунок падає одразу з чітким повідомленням,
// а не через годину з "undefined is not a valid connection string"
export const config = schema.parse(process.env);

7. CI/CD і GitHub Actions

Безперервна інтеграція (Continuous Integration, CI) — на кожен push автоматично запускаються перевірки: лінтер, типи, тести, збірка. Мета — ловити проблеми за хвилини, а не в день релізу. Безперервна доставка/розгортання (Continuous Delivery / Deployment, CD) — якщо перевірки зелені, зібраний артефакт автоматично (або одним кліком) потрапляє на сервер. Delivery — готово до деплою, Deployment — задеплоєно без участі людини.

# .github/workflows/ci-cd.yml
name: CI/CD

on:
  push:
    branches: [main]
  pull_request:

# Права токена GITHUB_TOKEN — мінімально необхідні
permissions:
  contents: read
  packages: write        # для push у GHCR

# Якщо запушили двічі поспіль — скасувати попередній прогін тієї ж гілки
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  IMAGE: ghcr.io/${{ github.repository }}   # ghcr.io/olya/notes-api

jobs:
  check:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [20, 22]                        # перевіряємо на двох версіях Node
    services:
      postgres:
        image: postgres:16-alpine
        env: { POSTGRES_PASSWORD: test, POSTGRES_DB: notes_test }
        ports: ["5432:5432"]
        options: --health-cmd pg_isready --health-interval 5s --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: pnpm                         # кеш pnpm store між прогонами
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm tsc --noEmit
      - run: pnpm vitest run
        env:
          DATABASE_URL: postgres://postgres:test@localhost:5432/notes_test

  build:
    needs: check                              # лише після зелених перевірок
    if: github.ref == 'refs/heads/main'      # образи збираємо тільки з main
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3   # buildx: кеш шарів, multi-platform
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: meta
        uses: docker/metadata-action@v5       # генерує теги: sha-abc1234, latest
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha,prefix=sha-
            type=raw,value=latest
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha                 # кеш шарів у GitHub Actions cache
          cache-to: type=gha,mode=max

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production                   # захищене середовище: секрети + approve
    steps:
      - uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: deploy
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script: |
            cd /srv/notes
            echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
            export IMAGE_TAG=sha-${GITHUB_SHA::7}
            docker compose pull app
            docker compose up -d app          # rolling для одного контейнера: новий підніметься, старий зупиниться
            docker image prune -f

Що тут відбувається: три джоби, послідовні через needs. check запускається на кожен PR і на push у main, у матриці з двох версій Node, з Postgres як сервісом. build — тільки з main: логін у GHCR через вбудований GITHUB_TOKEN, тег за SHA коміту (щоб кожен образ був унікальний і відтворюваний) плюс latest для зручності, кеш шарів між прогонами. deploy — по SSH на сервер, де лежить compose.yaml, який читає IMAGE_TAG з оточення: image: ghcr.io/olya/notes-api:${IMAGE_TAG:-latest}.

Чому тег за SHA, а не тільки latest

latest — рухома мітка: сьогодні вона вказує на одну збірку, завтра на іншу. Якщо продакшн зламався, ви не знаєте, що саме там крутиться, і не можете відкотитися на «попередній latest» — його вже немає. Тег sha-abc1234 назавжди прив'язаний до коміту: docker compose up з попереднім SHA — і ви відкотилися за 20 секунд. Те саме стосується базових образів: FROM node:22-alpine краще за FROM node:latest.

8. Стратегії деплою

Деплой — це заміна старої версії на нову. Питання в тому, чи буде простій (downtime) і що робити, якщо нова версія погана.

  • Recreate — зупинити стару, запустити нову. Простій на секунди-хвилини. Годиться для внутрішніх інструментів і застосунків, де короткий простій прийнятний. Найпростіша, і саме так працює docker compose up для одного контейнера, якщо не старатися.
  • Rolling — замінювати екземпляри по одному: підняти новий, дочекатися healthcheck, зняти старий. Без простою, але певний час працюють дві версії одночасно — API і схема бази мають бути сумісні з обома (це називають backward-compatible міграціями). Стандарт для Kubernetes.
  • Blue-Green — два однакові середовища. Нова версія розгортається у неактивне (green), тестується, потім балансувальник перемикає весь трафік. Відкат — перемкнути назад. Ціна — вдвічі більше ресурсів у момент деплою. Описано Мартіном Фаулером у 2010-му.
  • Canary — нова версія отримує маленьку частку трафіку (1–5 %), і ви дивитеся на метрики: помилки, латентність, бізнес-показники. Якщо все гаразд — частку збільшують. Назва від канарок, яких шахтарі брали під землю: птах непритомнів від газу раніше за людей. Потребує балансувальника з ваговим маршрутизуванням і хорошого моніторингу.

9. Куди деплоїти: PaaS, VPS, хмара

PaaS — платформа як сервіс

Vercel, Railway, Fly.io, Render беруть на себе все: ви даєте репозиторій або Dockerfile, вони збирають, деплоять, дають HTTPS-домен, логи, автоскейл. Ідеально для старту і для команд без DevOps. Vercel — рідний дім Next.js, serverless-функції, edge, безкоштовний хобі-план; але бекенд з довгими з'єднаннями (WebSocket) або воркерами туди не покладеш. Fly.io — запускає ваш Docker-образ на мікро-VM у регіонах по всьому світу, є Postgres і Redis. Railway і Render — «Heroku нового покоління»: підключив репозиторій, обрав базу з каталогу, готово. Мінус усіх PaaS — ціна зростає швидше, ніж на VPS, і менше контролю.

VPS — власний віртуальний сервер

Hetzner, DigitalOcean, Vultr дають Linux-машину за 4–10 € на місяць. На ній: Docker, ваш compose.yaml і зворотний проксі (reverse proxy), який приймає HTTPS на 443 порту і перенаправляє запити до контейнерів. Це найдешевший варіант для невеликих проєктів і найкращий спосіб зрозуміти, як усе працює.

Caddy — проксі, який сам отримує і оновлює сертифікати Let's Encrypt. Конфіг на п'ять рядків:

# Caddyfile
notes.app {
    # Автоматичний HTTPS: Caddy отримає сертифікат від Let's Encrypt через ACME-челендж
    encode gzip zstd
    handle /api/* {
        reverse_proxy app:3000        # ім'я сервісу з compose.yaml
    }
    handle {
        reverse_proxy web:3000
    }
}
# Додаємо до compose.yaml
services:
  proxy:
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data           # сертифікати мають пережити перезапуск
    depends_on: [app, web]
volumes:
  caddy_data:

Той самий результат на nginx вимагає більше рядків і окремого certbot для сертифікатів, але nginx — індустріальний стандарт, і його конфіги ви зустрінете всюди:

# nginx.conf (фрагмент server-блоку); сертифікати отримує certbot
server {
    listen 443 ssl http2;
    server_name notes.app;
    ssl_certificate     /etc/letsencrypt/live/notes.app/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/notes.app/privkey.pem;

    location /api/ {
        proxy_pass         http://app:3000;
        proxy_set_header   Host $host;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto https;
    }
    location / {
        proxy_pass http://web:3000;
    }
}
server {                                # HTTP → HTTPS
    listen 80;
    server_name notes.app;
    return 301 https://$host$request_uri;
}

10. Kubernetes: огляд

Kubernetes (K8s) — оркестратор контейнерів: система, яка на кластері з багатьох машин запускає потрібну кількість копій кожного сервісу, перезапускає впалі, розподіляє трафік, масштабує під навантаження і робить rolling-деплої. Ви описуєте бажаний стан у YAML, а Kubernetes постійно приводить реальність до нього.

  • Pod — найменша одиниця: один або кілька контейнерів, які ділять мережу і диск. Зазвичай один контейнер на Pod. Pod смертний: впав — створюється новий з новим IP.
  • Deployment — «я хочу 3 Pod-и з образом X». Стежить за кількістю, робить rolling update при зміні образу, зберігає історію для відкату.
  • Service — стабільна адреса і балансування на набір Pod-ів (бо IP Pod-ів змінюються).
  • Ingress — правила «домен/шлях → Service», термінація TLS. Реалізується контролером (nginx-ingress, Traefik).
  • ConfigMap / Secret — конфігурація і секрети, які монтуються у Pod як env або файли.
  • HPA (Horizontal Pod Autoscaler) — автоматично змінює кількість Pod-ів за метриками.

Коли Kubernetes потрібен: десятки сервісів, кілька команд, потреба в автоскейлі і самовідновленні, кілька середовищ на одній інфраструктурі. Коли ні: один-три сервіси, маленька команда, немає людини, яка готова його підтримувати. Kubernetes — це не «наступний крок після Compose», це інша вагова категорія з власною операційною складністю. Багато успішних продуктів роками живуть на Compose + VPS або PaaS. Якщо хочеться спробувати — k3s (легкий дистрибутив) на одному VPS або керований кластер у DigitalOcean.

11. Середовища, healthcheck, graceful shutdown

Середовища (environments)

dev — ноутбук розробника, Compose, гарячий перезапуск, тестові дані. staging — копія продакшену з тими самими образами і конфігами, але окремою базою: тут тестують перед релізом, сюди автодеплоїться main. prod — те, що бачать користувачі; деплой з тегу або через ручне підтвердження (GitHub Environments з required reviewers). Ключове правило: один образ проходить через усі середовища, змінюється лише конфіг. Якщо для prod збирається інший образ — ви тестуєте не те, що деплоїте.

Health-ендпоінт

// src/health.ts — два ендпоінти з різним змістом
import { Router } from "express";
import { db } from "./db.js";

export const health = Router();

// liveness: «процес живий?» — якщо ні, оркестратор перезапустить контейнер
health.get("/health", (_req, res) => res.json({ status: "ok" }));

// readiness: «готовий приймати трафік?» — перевіряє залежності.
// Якщо база недоступна — прибрати з балансування, але НЕ перезапускати
health.get("/ready", async (_req, res) => {
  try {
    await db.execute("SELECT 1");
    res.json({ status: "ready" });
  } catch (err) {
    res.status(503).json({ status: "not ready", reason: "database" });
  }
});

Graceful shutdown

Коли оркестратор зупиняє контейнер, він надсилає SIGTERM і дає ~10 секунд (у K8s — 30). Якщо процес просто вмирає, запити, які зараз обробляються, обриваються, а користувачі бачать помилки при кожному деплої. Правильно: перестати приймати нові з'єднання, дочекатися поточних, закрити базу, вийти.

// src/server.ts
import { createApp } from "./app.js";
import { db } from "./db.js";
import { config } from "./config.js";

const server = createApp().listen(config.PORT, () => {
  console.log(`listening on :${config.PORT}`);
});

// Keep-alive з'єднання можуть тримати сервер відкритим довго — обмежуємо
server.keepAliveTimeout = 5_000;

async function shutdown(signal: string) {
  console.log(`${signal} received, shutting down`);

  // 1. Перестати приймати нові з'єднання; колбек — коли всі поточні завершено
  server.close(async () => {
    // 2. Закрити пул з'єднань з базою
    await db.end();
    console.log("clean exit");
    process.exit(0);
  });

  // 3. Страховка: якщо за 8 с не завершилися — виходимо примусово
  //    (менше, ніж таймаут оркестратора, щоб встигнути залогувати)
  setTimeout(() => {
    console.error("forced exit");
    process.exit(1);
  }, 8_000).unref();
}

process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT", () => shutdown("SIGINT"));   // Ctrl+C локально

Нагадування з розділу про Dockerfile: це працює лише якщо node — PID 1 (exec-форма CMD). Інакше сигнал отримає shell і проігнорує його.

12. Вартість і типові помилки

Орієнтовна вартість для маленького продукту (API + фронт + Postgres): VPS Hetzner CX22 — близько 4 €/міс за все; Fly.io — 5–15 $/міс залежно від бази; Railway — від 5 $ + споживання; Vercel Hobby — безкоштовно для фронтенду, база окремо (Neon free tier). AWS для того самого — від 30–50 $/міс, якщо брати керовані сервіси, і легко більше через непомітні витрати (NAT Gateway, трафік, снапшоти). Ставте billing alerts у перший день.

Типові помилки, які коштують дорого
  • latest у продакшені. Неможливо відтворити чи відкотити. Тегуйте за SHA або семвером.
  • Секрети в образі. COPY .env . або ENV JWT_SECRET=... — секрет у шарі назавжди, навіть якщо потім видалити файл наступною інструкцією. Передавайте через env при запуску.
  • Root у контейнері. Уразливість у застосунку + root = уразливість у хості через втечу з контейнера. USER node — один рядок.
  • Без лімітів ресурсів. Витік пам'яті в одному контейнері з'їдає весь сервер і кладе базу поруч. limits.memory у Compose, resources у K8s.
  • Без healthcheck. Контейнер «запущений», але застосунок завис — оркестратор не знає і трафік іде в нікуди.
  • База без бекапів. Том — не бекап. pg_dump за cron у S3/R2 і хоча б раз перевірене відновлення.
  • Порт бази назовні. ports: ["5432:5432"] на VPS з паролем postgres — ботів, які сканують інтернет, це знайде за години.
  • Деплой без міграцій або міграції без сумісності. При rolling-деплої стара версія коду ще працює з новою схемою. Додавайте колонки з дефолтами, не видаляйте одразу — видаляйте через реліз.
Для просунутих

Наступний рівень після цього розділу: інфраструктура як код (Terraform, Pulumi) — сервери і бази описуються у файлах і створюються командою, а не кліками у консолі; GitOps (ArgoCD, Flux) — стан кластера синхронізується з git-репозиторієм, а деплой = merge; сканування образів (Trivy, Docker Scout) у CI на відомі вразливості; SBOM і підпис образів (cosign) для ланцюга постачання; distroless-образи від Google без shell взагалі. І окремо — preview environments: кожен PR автоматично отримує власне тимчасове середовище з URL (Vercel робить це з коробки, для Compose є інструменти на кшталт Coolify).

Спробуй сам: повний шлях до продакшену
  1. Орендуйте найдешевший VPS (Hetzner CX22 або DigitalOcean Basic). Встановіть Docker за офіційною інструкцією, створіть користувача deploy без пароля з SSH-ключем, вимкніть вхід за паролем.
  2. Купіть або візьміть безкоштовний домен (наприклад, у Cloudflare чи через DuckDNS) і направте A-запис на IP сервера.
  3. Покладіть на сервер compose.yaml з app + db + cache + Caddy. docker compose up -d. Відкрийте https://ваш-домен/health — має бути валідний сертифікат.
  4. Налаштуйте workflow із секції 7: додайте секрети DEPLOY_HOST, DEPLOY_SSH_KEY у репозиторій, зробіть push у main і подивіться, як деплой проходить сам.
  5. Під час деплою запустіть у сусідньому терміналі while true; do curl -s -o /dev/null -w "%{http_code}\n" https://домен/health; sleep 0.2; done. Побачите, чи є помилки під час перемикання. Якщо є — це recreate; спробуйте зробити два екземпляри app і оновлювати їх по черзі.
  6. Налаштуйте pg_dump за cron у Cloudflare R2 і відновіть базу з дампу на локальній машині.

Перевір себе

Питання
1. Чим образ відрізняється від контейнера?

Образ — незмінний набір шарів файлової системи плюс метадані (рецепт). Контейнер — запущений процес з цього образу з власним тонким записуваним шаром зверху (страва). З одного образу — багато контейнерів.

2. Чому в Dockerfile залежності копіюють до коду?

Бо шари кешуються по порядку. Якщо package.json не змінився, шар з pnpm install береться з кешу, і зміна одного файлу коду не переустановлює всі залежності.

3. Що дає multi-stage build?

Фінальний образ містить лише runtime-файли (Node + production-залежності + dist), без компілятора, тестів, dev-залежностей і вихідного коду. Менший розмір, менша поверхня атаки, швидший pull.

4. Навіщо depends_on з condition: service_healthy?

Просте depends_on чекає лише запуску контейнера, а не готовності бази приймати з'єднання. З service_healthy Compose чекає, поки healthcheck Postgres пройде, і застосунок не впаде з «connection refused».

5. Чим blue-green відрізняється від canary?

Blue-green перемикає 100 % трафіку одразу між двома повними середовищами — швидкий деплой і відкат, але ×2 ресурсів. Canary поступово збільшує частку трафіку нової версії (5 % → 100 %), спостерігаючи за метриками — безпечніше, але потребує вагового балансування і моніторингу.

6. Чому shell-форма CMD ламає graceful shutdown?

CMD node app.js запускає sh -c "node app.js": PID 1 — це sh, який не пересилає SIGTERM дочірньому процесу. Node не дізнається про зупинку і буде вбитий SIGKILL через таймаут. Exec-форма CMD ["node","app.js"] робить node PID 1.

7. Чим liveness відрізняється від readiness?

Liveness: «процес живий?» — при провалі контейнер перезапускають. Readiness: «готовий обслуговувати?» — перевіряє залежності (база); при провалі контейнер прибирають з балансування, але не перезапускають, бо проблема не в ньому.

8. Коли Kubernetes — зайвий?

Коли сервісів мало, команда маленька і немає людини для підтримки кластера. Compose на VPS чи PaaS покривають більшість потреб дешевше і простіше. K8s виправданий при десятках сервісів, потребі в автоскейлі й самовідновленні на кількох машинах.

Що запам'ятати

  • Контейнер — ізольований процес на спільному ядрі; образ — незмінні шари; Dockerfile — код, що їх описує.
  • Порядок у Dockerfile: базовий образ → залежності → код; multi-stage, USER node, exec-форма CMD, .dockerignore.
  • Compose описує всю зв'язку: сервіси бачать одне одного за іменем, дані живуть у томах, depends_on + healthcheck для порядку старту, порти бази не публікуються.
  • 12-factor: конфіг у env, stateless-процеси, логи у stdout, один образ для всіх середовищ; секрети — ніколи в git чи образі.
  • CI — перевірки на кожен PR (швидке спершу); CD — збірка образу з тегом за SHA і деплой тільки з main.
  • Стратегії: recreate (простій), rolling (по одному, дві версії разом), blue-green (перемикач), canary (поступово за метриками).
  • Куди: PaaS для швидкого старту, VPS + Compose + Caddy для контролю і дешевизни, хмара — коли справді треба; K8s — не для трьох сервісів.
  • Обов'язково: healthcheck (liveness + readiness), graceful shutdown за SIGTERM, ліміти ресурсів, бекапи, billing alerts.
