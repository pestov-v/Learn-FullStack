Пояснення для п'ятирічного

Уяви, що ти возиш вантаж на одному коні. Вантажу стає більше. Можна купити більшого коня — він тягне більше, але найбільший кінь у світі все одно має межу, і коли він захворіє, ти не возиш нічого. А можна купити ще п'ять звичайних коней і запрягти їх разом. Тепер якщо один захворів, решта чотири тягнуть далі. Але з'являються нові турботи: коней треба годувати всіх, вони мають бігти в один бік, і якщо кожен кінь "пам'ятає" своє власне, то коли ти пересядеш на іншого, він не знатиме, куди ти вже їздив.

Масштабування (scaling) — це саме про це: як зробити так, щоб систему тягнуло багато звичайних серверів, і як домовитися між ними, хто що пам'ятає і хто головний.

1. Вертикальне і горизонтальне масштабування

Вертикальне масштабування (vertical scaling, scale up) — більший кінь: замість сервера з 4 ядрами і 16 ГБ берете 64 ядра і 512 ГБ. Плюси: нічого не треба міняти в коді, немає розподілених проблем, база даних на одній машині зберігає всі свої гарантії транзакцій. Мінуси: ціна росте швидше за потужність (найбільші машини коштують непропорційно дорого), є фізична стеля, і сервер лишається єдиною точкою відмови. Не зневажайте цей шлях: сучасний сервер із 96 ядрами і NVMe-дисками витягує навантаження, для якого 15 років тому був потрібен цілий кластер.

Горизонтальне масштабування (horizontal scaling, scale out) — більше коней: замість одного великого сервера — 20 звичайних. Плюси: майже без стелі, відмова одного — це втрата 5% потужності, а не 100%; можна додавати і забирати сервери автоматично залежно від навантаження (autoscaling). Мінуси: усе, про що цей розділ, — координація, консистентність, мережеві відмови.

Чому це важливо

Горизонтальне масштабування — це не лише про продуктивність, а й про доступність (availability). Навіть якщо один сервер витягує ваше навантаження, два сервери за балансувальником дають можливість оновлювати код без простою (по черзі), переживати падіння заліза і перезавантажуватися вдень, а не о 4 ранку. Тому "два сервери" — це часто мінімальна продакшен-конфігурація, навіть для невеликого проєкту.

2. Stateless-сервери: де тримати стан

Щоб можна було додати десятий сервер або вбити третій, сервери мають бути взаємозамінними: будь-який запит будь-якого користувача може обробити будь-який сервер. Це означає, що сервер не має тримати стан (state), що потрібен між запитами. Такий сервер називають stateless. Що зазвичай ламає цю властивість:

  • Сесії в пам'яті процесу (express-session з MemoryStore): користувач залогінився на сервері A, наступний запит потрапив на B — і він "не залогінений".
  • Файли на локальному диску: користувач завантажив аватар на сервер A, а сторінку віддає B, у якого цього файлу немає.
  • Кеш у пам'яті: не ламає коректність, але кожен сервер гріє свій кеш окремо, і після деплою всі 20 серверів одночасно йдуть у БД.
  • Локальні cron-задачі й лічильники: 20 серверів — 20 разів надіслана розсилка.

3. Балансування навантаження: L4, L7, алгоритми, DNS

Балансувальник навантаження (load balancer, LB) — це швейцар, який стоїть перед рядом однакових серверів і каже кожному відвідувачу, до якого віконця йти. Він знає, які віконця живі, і розподіляє чергу так, щоб ніхто не стояв без діла.

Два рівні, на яких він може працювати (номери — з моделі OSI):

  • L4 (транспортний рівень): балансувальник бачить лише IP і порт, він передає TCP-байти далі, не заглядаючи всередину. Дуже швидкий (мільйони з'єднань), працює для будь-якого протоколу (не тільки HTTP), не потребує TLS-ключів. Приклади: AWS NLB, HAProxy в режимі tcp, IPVS у Linux.
  • L7 (прикладний рівень): балансувальник розбирає HTTP, бачить URL, заголовки, cookie. Може маршрутизувати /api/* на один пул, /static/* на інший, термінувати TLS, стискати, кешувати, робити A/B. Повільніший і "розумніший". Приклади: NGINX, HAProxy http, Envoy, Traefik, AWS ALB, Cloudflare.

Алгоритми вибору сервера

  • Round robin (по колу): перший запит — A, другий — B, третій — C, знову A. Простий, добре працює, коли запити однакові за вартістю.
  • Weighted round robin: те саме, але потужнішому серверу дають більше "ходів".
  • Least connections (найменше з'єднань): новий запит іде туди, де зараз найменше активних. Кращий, коли запити різні за тривалістю (довгі завантаження, WebSocket).
  • IP hash: сервер обирається за хешем IP клієнта — той самий клієнт завжди потрапляє на той самий сервер. Дешевий спосіб "прилипання", але ламається, коли за одним NAT сидить офіс на 500 людей.
  • Random / power of two choices: обираємо два випадкових сервери і беремо менш завантажений. На диво близький до оптимуму і не потребує глобального стану — улюблений алгоритм великих систем.
# nginx.conf — L7 балансування з health check і вагами
upstream api {
    least_conn;                        # алгоритм: найменше активних з'єднань
    server 10.0.1.11:3000 weight=1 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:3000 weight=1 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:3000 weight=3;    # потужніша машина — втричі більше трафіку
    keepalive 64;                      # тримати з'єднання до бекендів відкритими
}
server {
    listen 443 ssl http2;
    location /api/ {
        proxy_pass http://api;
        proxy_connect_timeout 2s;      # таймаут на з'єднання з бекендом
        proxy_read_timeout 10s;        # таймаут на відповідь
        proxy_next_upstream error timeout http_503;  # при помилці — спробувати інший сервер
        proxy_set_header X-Request-Id $request_id;   # correlation id
    }
}

Health checks

Балансувальник періодично викликає GET /healthz. Тут важлива різниця між liveness ("процес живий?") і readiness ("готовий приймати трафік?"). Сервер, що щойно стартував і ще гріє кеш, живий, але не готовий; сервер, що завершує роботу під час деплою, має спочатку сказати "не готовий", дообробити активні запити і лише потім вийти (graceful shutdown). Health check має перевіряти залежності (БД, Redis) обережно: якщо БД лягла, і всі 20 серверів одночасно скажуть "не готовий", балансувальник виключить усіх — і навіть сторінка "тимчасово недоступно" не віддасться.

Sticky sessions і чому вони небажані

Липкі сесії (sticky sessions) — балансувальник ставить cookie і завжди відправляє клієнта на той самий сервер. Це милиця для застосунків зі станом у пам'яті. Проблеми: нерівномірне навантаження (один сервер "прилип" до важких користувачів), при падінні сервера всі його користувачі втрачають сесії, деплой стає болючим. Правильна відповідь — stateless-сервери з розділу 2. Виправдана sticky-конфігурація одна: WebSocket-з'єднання, які й так довгоживучі.

DNS-балансування, GeoDNS, anycast

Балансувальник теж може впасти, тому їх ставлять два (active-passive з "плаваючою" IP-адресою) або більше. Ще вище — DNS-балансування: ім'я api.example.com резолвиться в кілька IP, і клієнти беруть різні. Грубий інструмент: DNS кешується хвилинами, клієнт не знає, що IP помер. GeoDNS віддає різні IP залежно від країни клієнта — користувачі з Європи йдуть у Франкфурт, з Азії — у Сінгапур. Anycast — одна й та сама IP-адреса анонсується з десятків дата-центрів, і маршрутизатори інтернету самі ведуть пакет до найближчого. Так працюють Cloudflare, Google DNS 8.8.8.8 і великі CDN: ви завжди потрапляєте в найближчу точку, і при її падінні мережа сама перемаршрутизує.

4. Масштабування бази даних: пул, репліки, failover

Сервери масштабувати легко — вони stateless. Уся складність зосереджується в базі даних, бо саме там стан. Кроки, у порядку від дешевих до дорогих:

Крок 0: connection pooling

PostgreSQL створює окремий процес на кожне з'єднання, і кожне коштує кілька мегабайт та мілісекунд на встановлення. 20 серверів по 20 з'єднань — це 400 процесів, і БД більше часу перемикає контексти, ніж працює. Пул з'єднань (connection pool) тримає невелику кількість відкритих з'єднань і роздає їх запитам по черзі. Пул є в кожному драйвері (pg.Pool), але коли серверів багато, ставлять зовнішній пулер — PgBouncer: 20 серверів по 100 "віртуальних" з'єднань до PgBouncer, а він тримає 30 реальних до PostgreSQL.

# pgbouncer.ini — режим transaction: з'єднання повертається в пул після кожної транзакції
[databases]
shop = host=10.0.2.5 port=5432 dbname=shop

[pgbouncer]
listen_port = 6432
pool_mode = transaction       # найефективніший; але не працює з session-level фічами (SET, prepared statements по імені)
max_client_conn = 2000        # скільки клієнтів можуть підключитися до PgBouncer
default_pool_size = 30        # скільки реальних з'єднань до PostgreSQL на базу
reserve_pool_size = 5

Крок 1: read replicas

Типовий застосунок читає у 10–100 разів частіше, ніж пише. Реплікація (replication) — primary (головний) приймає всі записи і пересилає журнал змін (WAL) на одну чи кілька replica (копій), які приймають лише читання. Застосунок пише в primary, а SELECT розкидає по репліках.

Лаг реплікації (replication lag) — затримка між записом на primary і появою його на репліці. Зазвичай мілісекунди, але під навантаженням чи при довгих транзакціях — секунди й хвилини. Проблема "прочитав свій запис (read-your-writes)": користувач змінив аватар, сторінка перезавантажилась і показала старий. Рішення:

  • Після запису кілька секунд читати цього користувача з primary (запам'ятати timestamp останнього запису в сесії/cookie).
  • Читати "свої" дані завжди з primary, чужі — з реплік (профіль — primary, стрічка — репліка).
  • Повертати клієнту LSN (позицію в WAL) після запису і чекати, поки репліка його дожене (pg_wal_lsn_diff).

Синхронна vs асинхронна реплікація

Асинхронна: primary підтверджує COMMIT одразу і шле WAL "потім". Швидко; але якщо primary згорить до відправки, останні транзакції втрачені. Синхронна: primary чекає, поки хоча б одна репліка запише WAL на диск, і лише потім каже клієнту "готово". Нуль втрат, але кожен COMMIT довший на мережевий RTT, і якщо синхронна репліка недоступна — запис блокується. Компроміс, який використовують у продакшені: одна синхронна репліка в тому ж дата-центрі (для нуля втрат) + асинхронні в інших регіонах (для читання і disaster recovery).

Failover

Primary впав. Хтось має: помітити це, обрати нову primary серед реплік (ту, що найменше відстала), переключити на неї застосунки, і — критично важливо — не дати старій primary прокинутися і думати, що вона все ще головна (це називається split-brain, два "мозки"). Робити це руками о 3 ночі — погана ідея; для PostgreSQL є Patroni (використовує etcd/Consul для консенсусу, розділ 7), для хмар — RDS Multi-AZ, Cloud SQL HA. Час failover — від 10 секунд до хвилин; застосунок мусить це переживати: повторювати з'єднання, не тримати транзакцій відкритими надовго.

Підводні камені
  • Репліки не масштабують запис. Якщо ваша проблема — INSERT-и, репліки не допоможуть; навпаки, кожна репліка додає роботи primary. Потрібен шардінг.
  • Пулер + транзакційний режим ламає SET, LISTEN, advisory locks на рівні сесії і prepared statements по імені. Prisma/Drizzle треба конфігурувати відповідно (?pgbouncer=true, або prepared statements off).
  • Довгі транзакції блокують реплікацію і vacuum. Транзакція має жити мілісекунди, не секунди. Ніяких HTTP-викликів усередині транзакції.

5. Партиціонування і шардінг, consistent hashing

Коли одна таблиця не влазить на один диск або одна primary не витягує запис, дані ділять. Два терміни, які часто плутають:

  • Партиціонування (partitioning) — ділимо таблицю на частини в межах однієї БД. PostgreSQL робить це "з коробки": PARTITION BY RANGE (created_at) — окрема фізична таблиця на кожен місяць. Запити за один місяць читають одну партицію; старі партиції видаляються за мілісекунди (DROP TABLE замість DELETE мільйонів рядків). Транзакції і JOIN працюють як раніше.
  • Шардінг (sharding) — ділимо дані між різними серверами БД. Кожен сервер (шард) тримає свою частину і не знає про інші. Це горизонтальне масштабування запису, і ціна — втрата транзакцій і JOIN між шардами.

Ключ шардування

Ключ шардування (shard key) — поле, за яким визначаємо, на якому шарді живе рядок. Найважливіше рішення в шардінгу; змінити його потім майже неможливо. Дві стратегії:

  • Range (за діапазоном): користувачі з id 1–1M — шард 1, 1M–2M — шард 2. Плюс: діапазонні запити ефективні. Мінус: нові користувачі всі йдуть на останній шард — гарячий шард (hot shard).
  • Hash (за хешем): shard = hash(userId) % N. Плюс: рівномірно. Мінус: діапазонні запити розлітаються по всіх шардах, а зміна N перемішує майже всі ключі.

Саме остання проблема — "змінили кількість шардів із 4 на 5, і 80% даних треба перевезти" — привела до consistent hashing (узгодженого хешування).

Consistent hashing лежить в основі Amazon Dynamo, Cassandra, Riak, кешів на кшталт Memcached-клієнтів і балансувальників у CDN. У PostgreSQL-світі готове шардування дає Citus; у MongoDB — вбудований sharded cluster; Vitess шардує MySQL для YouTube і Slack.

Проблеми шардінгу, які треба знати наперед

  • Cross-shard запити: "топ-10 користувачів за витратами" — треба спитати кожен шард і злити результати в застосунку (scatter-gather). Повільно і складно; уникайте через денормалізацію або окрему аналітичну БД.
  • Hot shards: одна знаменитість із 50 млн підписників живе на шарді 7, і шард 7 горить. Рішення: виносити "гарячі" ключі окремо, або додатково дробити їх (key + random suffix).
  • Resharding: збільшити кількість шардів наживо — окрема інженерна задача (подвійний запис, фонове копіювання, перемикання). Плануйте більше шардів, ніж потрібно зараз (наприклад, 64 логічні шарди на 4 фізичних серверах — потім просто рознесіть).
  • Унікальність і транзакції: UNIQUE(email) працює лише в межах шарда; глобальні id генерують окремо (UUID v7, Snowflake ID).
  • Референсні дані (країни, валюти) копіюють на кожен шард.
Для просунутих

Обираючи ключ шардування, шукайте той, за яким 95% запитів можна виконати в межах одного шарда. Для SaaS це майже завжди tenantId (організація): усі дані клієнта разом, JOIN всередині клієнта працюють, ізоляція між клієнтами природна. Для соцмережі — userId, але стрічка друзів — це cross-shard запит, тому її будують окремо (fan-out on write у Redis). Instagram, Notion і Figma публікували детальні розповіді про свій шардінг PostgreSQL — усі три вибрали шардування за власником даних.
