Пояснення для п'ятирічного

Уяви, що тобі треба збудувати замок. Можна ліпити його з глини: кожну вежу, кожне віконце — руками, і якщо захочеш пересунути двері, доведеться ламати стіну. А можна взяти LEGO: готові блоки, які з'єднуються за правилами; вежу збираєш один раз і потім ставиш її хоч десять разів. React — це LEGO для інтерфейсів: ти описуєш блоки (компоненти) і кажеш, який вигляд вони мають при яких даних, а React сам переставляє деталі, коли дані змінюються. Next.js — це набір LEGO з інструкцією: уже є коробка, у якій розкладено, як робити сторінки, як їх завантажувати швидко і як частину роботи робити ще «на фабриці» (на сервері), щоб дитині (браузеру) дісталося менше збирати.

1. Навіщо фреймворк: проблема ручного DOM

У розділі 02 ми змінювали сторінку через document.querySelector і innerHTML. Для кнопки-лічильника цього достатньо. Але уявіть список із 200 нотаток, де можна редагувати, фільтрувати, позначати виконані і бачити лічильник невиконаних. Тепер кожна зміна даних — це ланцюжок питань: який елемент оновити? чи додано новий? чи змінився лічильник? а якщо фільтр активний? Дані живуть у змінних, вигляд — у DOM, і ви вручну синхронізуєте два світи. Через місяць у коді десять місць, де оновлюється лічильник, і три з них забувають про фільтр.

Фреймворк перевертає підхід: ви описуєте, який вигляд має інтерфейс для даного стану (декларативно), а не як крок за кроком дійти до нього (імперативно). Змінився стан → фреймворк сам обчислює, що саме в DOM треба змінити. Формула: UI = f(state).

Чому це важливо

Більшість багів інтерфейсу — це розсинхронізація: дані кажуть одне, екран показує інше. Декларативний підхід прибирає цілий клас таких багів, бо екран завжди є функцією від даних. Ви думаєте про стан, а не про DOM-операції.

2. React: компоненти, JSX, props, state

Компонент (component) — це JavaScript-функція, яка приймає props (властивості, вхідні дані) і повертає опис розмітки. JSX — синтаксис, схожий на HTML, який компілюється у виклики createElement. Це не рядок і не HTML — це об'єкти-описи.

// Note.jsx — компонент = функція від props
export function Note({ title, done, onToggle }) {
  // JSX: усередині фігурних дужок — будь-який JS-вираз
  return (
    <li className={done ? "note done" : "note"}>
      <input type="checkbox" checked={done} onChange={onToggle} />
      <span>{title}</span>
    </li>
  );
}

// Використання: props передаються як атрибути
<Note title="Купити молоко" done={false} onToggle={() => console.log("клік")} />

Props — тільки для читання. Компонент не може змінити свої props, як функція не може змінити аргументи у викликача. Дані «згори вниз».

State (стан) — пам'ять компонента, яка змінюється з часом і належить самому компоненту. Хук useState повертає поточне значення і функцію для зміни; виклик цієї функції каже React: «дані змінилися, перемалюй мене».

import { useState } from "react";

export function Counter() {
  const [count, setCount] = useState(0); // початкове значення 0

  return (
    <button onClick={() => setCount(c => c + 1)}>
      {/* функціональна форма: безпечна при кількох оновленнях підряд */}
      Натиснуто {count} разів
    </button>
  );
}

Правила хуків: викликати лише на верхньому рівні компонента (не в умовах і циклах) і лише в компонентах або інших хуках. Причина — React запам'ятовує хуки за порядком виклику.

3. Рендер, Virtual DOM і reconciliation

Що відбувається, коли ви викликаєте setCount?

  1. Тригер: React планує повторний рендер компонента (і всіх його нащадків).
  2. Рендер: React викликає вашу функцію знову й отримує нове дерево описів — Virtual DOM (легкі JS-об'єкти, не справжні DOM-вузли).
  3. Reconciliation (звірка): React порівнює нове дерево з попереднім (алгоритм diffing) і складає мінімальний список змін.
  4. Commit: тільки ці зміни застосовуються до справжнього DOM — найдорожчої частини.

Важливий наслідок: рендер компонента ≠ оновлення DOM. Функція може викликатися часто (це дешево), а DOM змінюється рідко. Друге правило: коли рендериться батько, за замовчуванням рендеряться всі діти — незалежно від того, чи змінилися їхні props. Звідси й оптимізації з розділу 10.

4. useEffect і його пастки; списки, форми, умовний рендер

useEffect: синхронізація із зовнішнім світом

Компонент має бути чистою функцією від props і state. Але іноді треба взаємодіяти з тим, що поза React: підписатися на WebSocket, змінити document.title, запустити таймер. Для цього — useEffect: «після того, як цей рендер потрапив на екран, виконай ось це; а коли я зникну або залежності зміняться — прибери за собою».

import { useEffect, useState } from "react";

export function OnlineStatus() {
  const [online, setOnline] = useState(navigator.onLine);

  useEffect(() => {
    const on = () => setOnline(true);
    const off = () => setOnline(false);
    window.addEventListener("online", on);
    window.addEventListener("offline", off);
    // cleanup: React викличе перед наступним запуском ефекту і при демонтажі
    return () => {
      window.removeEventListener("online", on);
      window.removeEventListener("offline", off);
    };
  }, []); // [] — залежностей нема: підписатися один раз

  return <span>{online ? "🟢 онлайн" : "🔴 офлайн"}</span>;
}

Пастки, у які потрапляють усі:

  • Неповний масив залежностей. Ефект «бачить» значення з того рендеру, в якому був створений (замикання). Якщо ви використали userId усередині, а в масив не додали — ефект працюватиме зі старим userId. Правило: усе, що використовується, — у залежностях. Лінтер react-hooks/exhaustive-deps — ваш друг, не ворог.
  • Об'єкт або функція в залежностях. Вони створюються заново при кожному рендері → ефект запускається щоразу. Виносьте константи назовні або мемоізуйте (useMemo/useCallback), або кладіть у залежності примітиви.
  • Гонка запитів. Ефект робить fetch для id=1, користувач швидко переключився на id=2; відповідь для 1 прийшла пізніше і перезаписала дані. Ліки — прапорець ignore у cleanup або AbortController. Ще краще — не робити fetch у useEffect взагалі, а використовувати TanStack Query (далі).
  • useEffect для похідних даних. Якщо fullName обчислюється з first і last — просто обчисліть у тілі компонента. Ефект + setState тут дає зайвий рендер і плутанину.
  • Подвійний запуск у Strict Mode — це навмисно, щоб перевірити, що cleanup написаний правильно. У продакшені так не буде.

Списки і ключі

{notes.map(note => (
  <Note key={note.id} {...note} />   // key — стабільний id, НЕ індекс масиву
))}

key каже React, який елемент є яким між рендерами. З індексом масиву при видаленні першого елемента всі решта «зсуваються»: React вирішить, що змінився вміст кожного, а не зник один — зайві оновлення DOM і, гірше, стан полів вводу «переїде» до сусідів.

Форми

export function NoteForm({ onSubmit }) {
  const [title, setTitle] = useState("");             // керований (controlled) input
  function handleSubmit(e) {
    e.preventDefault();                               // не перезавантажувати сторінку
    if (!title.trim()) return;
    onSubmit(title.trim());
    setTitle("");
  }
  return (
    <form onSubmit={handleSubmit}>
      <input value={title} onChange={e => setTitle(e.target.value)} placeholder="Нова нотатка" />
      <button disabled={!title.trim()}>Додати</button>
    </form>
  );
}

5. Потік даних: підйом стану і контекст

Два компоненти-брати мають бачити один і той самий стан? Стан треба підняти (lift state up) до найближчого спільного предка. Дані течуть вниз через props, події — вгору через callback-функції у props.

Коли дані потрібні на п'ять рівнів нижче, а проміжні компоненти їх просто «прокидають» (prop drilling), на допомогу приходить Context: предок «оголошує» значення, будь-який нащадок читає його напряму.

import { createContext, useContext, useState } from "react";

const ThemeContext = createContext("light");

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext value={{ theme, toggle: () => setTheme(t => t === "light" ? "dark" : "light") }}>
      {children}
    </ThemeContext>   // React 19: <Context> замість <Context.Provider>
  );
}

export function ThemeButton() {
  const { theme, toggle } = useContext(ThemeContext); // або use(ThemeContext) у React 19
  return <button onClick={toggle}>Тема: {theme}</button>;
}

Обмеження контексту: зміна значення перерендерює всіх споживачів. Для теми чи поточного користувача це чудово; для стану, що змінюється 60 разів на секунду, — ні.

6. Керування станом: локальний → Context → Zustand/Redux → TanStack Query

Перше питання, яке треба ставити: який це стан?

Тип стануПрикладІнструмент
Локальний UIвідкритий дропдаун, текст у поліuseState у компоненті
Спільний для піддеревавибрана вкладка у формі-майстріпідйом стану + props
Глобальний, рідко змінюванийтема, локаль, поточний користувачContext
Глобальний, часто змінюваний, складна логікакошик, редактор, граZustand / Redux Toolkit
Серверний (кеш даних з API)список нотаток, профіль, товариTanStack Query / SWR
Стан у URLфільтри, сторінка, пошукроутер, useSearchParams

Ключова ідея останніх років: серверний стан — це не стан, а кеш. Список нотаток не належить браузеру — він належить серверу, а у нас лише копія, яка може застаріти. Redux-стор із «списком нотаток» плюс ручними isLoading/error/refetch — це самописний кеш без інвалідації. TanStack Query робить це за вас.

Zustand: глобальний стан без церемоній

import { create } from "zustand";

export const useCart = create((set) => ({
  items: [],
  add: (product) => set(s => ({ items: [...s.items, product] })),
  clear: () => set({ items: [] }),
}));

// у компоненті: підписка лише на потрібний зріз → рендер тільки коли він змінився
const count = useCart(s => s.items.length);

Redux Toolkit — та сама ідея з більшою структурою (slices, reducers, devtools з time-travel), доречна у великих командах, де важлива однаковість.

TanStack Query: серверний стан як кеш

import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

const api = {
  list: () => fetch("/api/notes").then(r => r.ok ? r.json() : Promise.reject(new Error(r.statusText))),
  create: (title) => fetch("/api/notes", {
    method: "POST", headers: { "content-type": "application/json" }, body: JSON.stringify({ title }),
  }).then(r => r.json()),
};

export function Notes() {
  const qc = useQueryClient();
  const { data: notes = [], isPending, error } = useQuery({
    queryKey: ["notes"],          // ключ кешу: масив, можна з параметрами ["notes", { page }]
    queryFn: api.list,
    staleTime: 30_000,            // 30с вважаємо свіжими — без зайвих запитів
  });
  const add = useMutation({
    mutationFn: api.create,
    onSuccess: () => qc.invalidateQueries({ queryKey: ["notes"] }), // позначити застарілим → refetch
  });

  if (isPending) return <p>Завантаження…</p>;
  if (error) return <p>Помилка: {error.message}</p>;
  return (
    <>
      <NoteForm onSubmit={title => add.mutate(title)} />
      <ul>{notes.map(n => <li key={n.id}>{n.title}</li>)}</ul>
    </>
  );
}
Чому «fetch у useEffect» — антипатерн для реальних застосунків

Ручний fetch у ефекті не має кешу (кожен монтаж — новий запит), не дедуплікує (два компоненти — два однакових запити), не знає про гонки, не оновлюється при поверненні у вкладку, не має retry. Ви або напишете все це самі (і зробите гірше), або візьмете готове. Документація React прямо радить фреймворк або бібліотеку даних.

7. Роутинг і рендеринг: CSR, SSR, SSG, ISR

Роутинг (routing) — відповідність між URL і тим, що показано. У чистому React це React Router (createBrowserRouter), у Next.js — файлова система: файл app/notes/[id]/page.tsx = маршрут /notes/42.

8. Next.js App Router: Server і Client Components

Next.js 13+ (App Router) додає принципово нове: React Server Components (RSC). Компонент може виконуватися лише на сервері: він має доступ до бази, файлів, секретів, а його код не потрапляє в JS-бандл браузера. Результат передається браузеру як серіалізоване дерево.

Файлова структура

app/
├── layout.tsx          # кореневий layout: <html>, <body>, навігація — обгортає всі сторінки
├── page.tsx            # маршрут /
├── loading.tsx         # показується, поки page.tsx чекає дані (Suspense)
├── error.tsx           # межа помилок для цього сегмента ("use client")
├── notes/
│   ├── page.tsx        # /notes
│   ├── layout.tsx      # спільна обгортка для /notes/*
│   └── [id]/
│       └── page.tsx    # /notes/42 — params.id === "42"
├── api/
│   └── notes/route.ts  # Route Handler: GET/POST /api/notes
└── (marketing)/        # група маршрутів: не впливає на URL
    └── about/page.tsx  # /about
// app/notes/page.tsx — Server Component за замовчуванням (без "use client")
import { db } from "@/lib/db";
import { notes } from "@/lib/schema";
import { SearchBox } from "./search-box";
import { addNote } from "./actions";

export default async function NotesPage() {
  // async компонент: чекаємо дані прямо тут; секрети БД не потраплять у браузер
  const rows = await db.select().from(notes).orderBy(notes.createdAt);
  return (
    <main>
      <SearchBox />                       {/* клієнтський острів інтерактивності */}
      <form action={addNote}>              {/* Server Action: працює навіть без JS */}
        <input name="title" required />
        <button>Додати</button>
      </form>
      <ul>{rows.map(n => <li key={n.id}>{n.title}</li>)}</ul>
    </main>
  );
}

// app/notes/actions.ts — Server Action: функція, яку клієнт викликає як RPC
"use server";
import { revalidatePath } from "next/cache";

export async function addNote(formData: FormData) {
  const title = String(formData.get("title") ?? "").trim();
  if (!title) return;                          // валідація ЗАВЖДИ на сервері
  await db.insert(notes).values({ title });
  revalidatePath("/notes");                    // скинути кеш сторінки → свіжий список
}

// app/notes/search-box.tsx — Client Component
"use client";
import { useState } from "react";
import { useRouter } from "next/navigation";

export function SearchBox() {
  const [q, setQ] = useState("");
  const router = useRouter();
  return <input value={q} onChange={e => { setQ(e.target.value); router.replace(`/notes?q=${encodeURIComponent(e.target.value)}`); }} />;
}

Ще три файли, які роблять App Router зручним:

  • layout.tsx — обгортка, яка не перемонтовується при переході між дочірніми сторінками (навігація, сайдбар зберігають стан).
  • loading.tsx — автоматична межа Suspense: скелетон показується миттєво, поки сторінка чекає дані. Разом зі streaming SSR це дає «HTML частинами».
  • error.tsx — межа помилок: падіння одного сегмента не валить весь застосунок, є кнопка «спробувати ще».
Підводні камені App Router
  • Server Action — це публічний HTTP-endpoint. Валідуйте вхід і перевіряйте авторизацію всередині кожної action, як у звичайному API.
  • Не імпортуйте серверний модуль (з db, секретами) у файл із "use client" — він потрапить у бандл. Пакет server-only зробить це помилкою збірки.
  • Props від Server до Client Component мають бути серіалізовними: функції, класи, Date-об'єкти (у деяких версіях) — ні.
  • Кешування у Next.js змінювалося між версіями (13 → 14 → 15). Читайте документацію саме вашої версії — розділ «Caching», а не статтю дворічної давнини.
  • Не все має бути Server Component: якщо сторінка на 90% інтерактивна (редактор, дашборд з графіками), клієнтський підхід із TanStack Query — цілком нормально.

9. Стилізація: CSS Modules, Tailwind, shadcn/ui

  • CSS Modules (note.module.css → import s from "./note.module.css" → className={s.card}). Звичайний CSS, але класи автоматично унікальні — нема глобальних конфліктів. Найпростіший старт, підтримується Next.js без налаштувань.
  • Tailwind CSS — утилітарні класи прямо в JSX: className="flex gap-2 rounded-xl p-4 shadow". Не пишете CSS-файли, не вигадуєте назви; дизайн-система (відступи, кольори) вбудована. Спочатку виглядає як хаос, за тиждень — не хочеться назад. Розмір CSS у продакшені мінімальний, бо невикористані класи викидаються.
  • shadcn/ui — не бібліотека, а набір компонентів (кнопки, діалоги, таблиці) на Tailwind + Radix, які копіюються у ваш проєкт командою npx shadcn add button. Ви володієте кодом і змінюєте що завгодно. Доступність (a11y) — з коробки.

10. Продуктивність: memo, lazy, Core Web Vitals

Спершу правило: не оптимізуйте, поки не виміряли. React DevTools → Profiler покаже, що рендериться і скільки це коштує.

  • memo(Component) — пропустити рендер, якщо props не змінилися (порівняння поверхневе). Працює тільки якщо props стабільні — об'єкти й функції, створені в рендері батька, зламають memo; для них useMemo/useCallback. У React 19 з'явився React Compiler, який робить цю мемоізацію автоматично.
  • lazy + Suspense — розділення коду (code splitting): важкий компонент (редактор, графіки) завантажується окремим чанком лише коли потрібен. У Next.js — next/dynamic, а маршрути розділяються автоматично.
  • Віртуалізація списків (TanStack Virtual) — рендерити лише видимі 30 рядків із 10 000.
  • Зображення — next/image: автоматичні розміри, WebP/AVIF, lazy loading, без зсувів макета.
import { lazy, Suspense, memo } from "react";

const HeavyChart = lazy(() => import("./HeavyChart")); // окремий чанк

export const NoteRow = memo(function NoteRow({ note, onToggle }) {
  return <li onClick={() => onToggle(note.id)}>{note.title}</li>;
}); // перерендер лише коли note або onToggle змінилися

export function Dashboard({ showChart }) {
  return showChart
    ? <Suspense fallback={<p>Завантажуємо графік…</p>}><HeavyChart /></Suspense>
    : null;
}

Core Web Vitals

Google вимірює досвід користувача трьома метриками, і вони впливають на ранжування:

  • LCP (Largest Contentful Paint) — коли на екрані з'явився найбільший елемент (герой-картинка, заголовок). Ціль ≤ 2,5 с. Ліки: SSR/SSG, пріоритет для головного зображення, менше блокувального JS.
  • INP (Interaction to Next Paint) — затримка від кліку до відповіді екрана (замінила FID у 2024). Ціль ≤ 200 мс. Ліки: менше роботи в обробниках, useTransition для неважливих оновлень, не блокувати головний потік.
  • CLS (Cumulative Layout Shift) — наскільки «стрибає» макет під час завантаження. Ціль ≤ 0,1. Ліки: задавати розміри зображень і рекламних блоків, не вставляти контент над уже видимим.

Вимірюйте у Lighthouse (Chrome DevTools), PageSpeed Insights і, головне, у реальних користувачів (web-vitals бібліотека або Vercel Analytics).

Для просунутих

Ментальна модель, яка пояснює 90% «дивної» поведінки React: рендер — це знімок (snapshot). Кожен рендер має свої props, свій state, свої обробники подій і свої ефекти — всі вони бачать значення саме цього рендеру через замикання. setState не змінює змінну — він просить наступний знімок. Тому console.log(count) одразу після setCount(count + 1) покаже старе значення, а setTimeout у старому рендері побачить старий count. Прочитайте «A Complete Guide to useEffect» Дена Абрамова і «Why React Re-Renders» Джоша Комо — після них React перестає бути магією.

11. Інші фреймворки і практика

Одним абзацем про сусідів. Vue — теж компоненти, але з шаблонами в HTML-стилі та реактивністю «з коробки» (змінив змінну — оновилось); низький поріг входу, екосистема Nuxt. Svelte — компілятор: реактивність вирішується під час збірки, бандл крихітний, синтаксис найкоротший; SvelteKit — аналог Next. Angular — «усе включено» від Google: TypeScript, DI, RxJS, жорстка структура; популярний у корпоративних проєктах. Solid — виглядає як React, але без Virtual DOM: сигнали оновлюють DOM точково; найшвидший у бенчмарках. Ідеї перетікають між ними (сигнали тепер є в Angular і Vue), тож вивчивши один глибоко, інші освоїте за тиждень.

Практика: нотатки на React + TanStack Query

Використовуємо API нотаток із розділу 04 (GET/POST/PATCH/DELETE /api/notes). Створіть проєкт: npm create vite@latest notes -- --template react, потім npm i @tanstack/react-query.

// src/main.jsx
import { createRoot } from "react-dom/client";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { App } from "./App";

const queryClient = new QueryClient({
  defaultOptions: { queries: { staleTime: 10_000, retry: 1 } },
});
createRoot(document.getElementById("root")).render(
  <QueryClientProvider client={queryClient}><App /></QueryClientProvider>
);

// src/api.js — тонкий шар над fetch
const BASE = "http://localhost:3000/api/notes";
async function http(url, options) {
  const res = await fetch(url, { headers: { "content-type": "application/json" }, ...options });
  if (!res.ok) throw new Error(`${res.status} ${res.statusText}`);
  return res.status === 204 ? null : res.json();
}
export const notesApi = {
  list:   ()            => http(BASE),
  create: (title)       => http(BASE, { method: "POST", body: JSON.stringify({ title }) }),
  toggle: (id, done)    => http(`${BASE}/${id}`, { method: "PATCH", body: JSON.stringify({ done }) }),
  remove: (id)          => http(`${BASE}/${id}`, { method: "DELETE" }),
};

// src/App.jsx
import { useState } from "react";
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";
import { notesApi } from "./api";

export function App() {
  const qc = useQueryClient();
  const [filter, setFilter] = useState("all");                  // локальний UI-стан
  const notesQuery = useQuery({ queryKey: ["notes"], queryFn: notesApi.list });

  const invalidate = () => qc.invalidateQueries({ queryKey: ["notes"] });
  const create = useMutation({ mutationFn: notesApi.create, onSuccess: invalidate });
  const remove = useMutation({ mutationFn: notesApi.remove, onSuccess: invalidate });

  // Оптимістичне оновлення: змінюємо кеш одразу, відкочуємо при помилці
  const toggle = useMutation({
    mutationFn: ({ id, done }) => notesApi.toggle(id, done),
    onMutate: async ({ id, done }) => {
      await qc.cancelQueries({ queryKey: ["notes"] });           // не дати refetch перезаписати
      const prev = qc.getQueryData(["notes"]);
      qc.setQueryData(["notes"], old => old.map(n => n.id === id ? { ...n, done } : n));
      return { prev };                                            // контекст для відкату
    },
    onError: (_err, _vars, ctx) => qc.setQueryData(["notes"], ctx.prev),
    onSettled: invalidate,
  });

  if (notesQuery.isPending) return <p>Завантаження…</p>;
  if (notesQuery.isError) return <p>Помилка: {notesQuery.error.message} <button onClick={() => notesQuery.refetch()}>Повторити</button></p>;

  const visible = notesQuery.data.filter(n => filter === "all" ? true : filter === "done" ? n.done : !n.done);

  return (
    <main>
      <h1>Нотатки ({notesQuery.data.filter(n => !n.done).length} невиконаних)</h1>
      <form onSubmit={e => { e.preventDefault(); const f = e.currentTarget; create.mutate(f.title.value); f.reset(); }}>
        <input name="title" placeholder="Що зробити?" required />
        <button disabled={create.isPending}>{create.isPending ? "…" : "Додати"}</button>
      </form>
      <p>
        {["all", "active", "done"].map(f => (
          <button key={f} onClick={() => setFilter(f)} aria-pressed={filter === f}>{f}</button>
        ))}
      </p>
      <ul>
        {visible.map(n => (
          <li key={n.id}>
            <input type="checkbox" checked={n.done} onChange={e => toggle.mutate({ id: n.id, done: e.target.checked })} />
            <span style={{ textDecoration: n.done ? "line-through" : "none" }}>{n.title}</span>
            <button onClick={() => remove.mutate(n.id)} aria-label="Видалити">✕</button>
          </li>
        ))}
      </ul>
      {notesQuery.isFetching && <small>оновлюємо…</small>}
    </main>
  );
}

Часті помилки новачків у React
  • Мутація стану: notes.push(x); setNotes(notes) — React не побачить зміни (та сама ссилка). Завжди створюйте новий масив/об'єкт.
  • Виклик функції замість передачі: onClick={handle()} виконає одразу при рендері. Треба onClick={handle} або onClick={() => handle(id)}.
  • Стан у props без синхронізації: useState(props.value) бере значення лише при першому рендері.
  • Хук усередині if — «Rendered more hooks than during the previous render».
  • Ключ через Math.random() — новий ключ щоразу = React перестворює DOM для кожного елемента.

Перевір себе

Питання
1. Чим props відрізняються від state?

Props приходять ззовні і незмінні для компонента; state — внутрішня пам'ять, яку компонент змінює сам через setState, викликаючи перерендер.

2. Чи означає рендер компонента, що DOM оновився?

Ні. Рендер — це виклик функції і побудова Virtual DOM. DOM змінюється лише там, де diff знайшов різницю. Рендер може відбутися без жодної зміни DOM.

3. Чому не можна використовувати індекс масиву як key?

При вставці/видаленні елементів індекси зсуваються, React плутає елементи, робить зайві оновлення і «переносить» стан (наприклад, текст в input) між рядками.

4. Що таке серверний стан і чому його не варто класти в Redux?

Це кеш даних, які належать серверу і можуть застаріти. Йому потрібні інвалідація, дедуплікація, refetch, retry — усе це вже є в TanStack Query, а в Redux довелося б писати вручну.

5. Чим SSR відрізняється від SSG?

SSR генерує HTML на сервері при кожному запиті (свіжі, персоналізовані дані, потрібен сервер). SSG — один раз при збірці (найшвидше, з CDN, але дані застарівають до наступної збірки). ISR — компроміс із фоновим оновленням.

6. Що робить директива "use client"?

Позначає межу: цей модуль і всі його імпорти потрапляють у бандл браузера і можуть використовувати хуки та події. Без неї компонент у App Router — серверний і не надсилає JS клієнту.

7. Що таке hydration?

Процес, коли React у браузері «прикріплюється» до вже готового серверного HTML: будує своє дерево, вішає обробники подій і відновлює стан, не перемальовуючи розмітку.

8. Коли memo не допоможе?

Коли props — нові об'єкти чи функції при кожному рендері батька (поверхневе порівняння побачить різницю). Потрібні useMemo/useCallback або React Compiler.

Що запам'ятати

  • UI = f(state): описуємо вигляд для даних, React сам обчислює зміни DOM через Virtual DOM і diff.
  • Компонент — функція від props; state — його пам'ять через useState; дані вниз, події вгору.
  • useEffect — для синхронізації із зовнішнім світом, не для обчислень і не для fetch у реальних застосунках.
  • key — стабільний id; стан не мутуємо; хуки лише на верхньому рівні.
  • Питайте «який це стан?»: локальний → useState; глобальний → Context/Zustand; серверний → TanStack Query; фільтри → URL.
  • CSR/SSR/SSG/ISR — різні відповіді на «де і коли будувати HTML»; вибір залежить від свіжості даних, SEO і персоналізації.
  • У Next.js App Router компоненти серверні за замовчуванням; "use client" — межа для інтерактивності; Server Actions — публічні endpoint'и, валідуйте.
  • Оптимізація — після вимірювання: Profiler, memo/lazy, Core Web Vitals (LCP, INP, CLS).
