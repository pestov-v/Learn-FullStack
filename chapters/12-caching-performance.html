Кешування та продуктивність

Пояснення для п'ятирічного

У тебе є улюблені іграшки, з якими ти граєшся щодня, і ті, що дістаєш раз на місяць. Якби всі іграшки лежали в коморі на горищі, ти б щоразу бігав по сходах туди-сюди. Тому улюблені лежать у коробці біля ліжка — під рукою. Ця коробка — кеш (cache): маленьке швидке місце для того, що потрібно часто.

Але є підступ. Мама переклала машинку з коробки на горище, а ти цього не знаєш і шукаєш її біля ліжка. Або в коробці лежить стара зламана машинка, хоча на горищі вже нова. Це «застарілий кеш». Найважче у кешах — не покласти річ у коробку, а вчасно зрозуміти, що вона там уже не та.

1. Кеш простими словами

Кеш — це копія даних, збережена ближче до того, хто їх потребує, або в швидшому сховищі, ніж оригінал. Оригінал (source of truth) — база даних, файл, результат важкого обчислення. Кеш — його тимчасова копія в пам'яті, на диску браузера, на сервері CDN за сотні кілометрів від вашого дата-центру.

Три причини кешувати: швидкість (читання з оперативної пам'яті — наносекунди, з Redis по мережі — сотні мікросекунд, запит у Postgres — мілісекунди, HTTP до іншого континенту — сотні мілісекунд); зниження навантаження (якщо 10 000 користувачів дивляться одну й ту саму головну сторінку, база не повинна виконувати 10 000 однакових запитів); вартість (кожен виклик платного API чи хвилина CPU коштують грошей).

І одна велика ціна: неузгодженість (staleness). Кеш завжди трохи відстає від оригіналу. Уся інженерія кешування — це торгівля між свіжістю і швидкістю. Ключове питання перед кожним кешем: «Скільки секунд застарілості я можу собі дозволити для цих даних?» Для курсу валют на головній — хвилина нормально. Для балансу рахунку в момент оплати — нуль.

Чому це важливо

Кешування — найпотужніший важіль продуктивності в бекенді, і водночас джерело найзагадковіших багів: «користувач бачить старі дані», «після деплою досі стара версія», «у мене оновилося, а в нього ні». Розуміти, де саме сидять кеші й хто ними керує, — це різниця між «я пришвидшив у 10 разів» і «я створив баг, який неможливо відтворити».

2. Ієрархія кешів

У типовому fullstack-застосунку запит проходить крізь кілька шарів, і кожен може відповісти з кешу, не пускаючи запит далі. Чим ближче до користувача спрацював кеш, тим дешевше і швидше.

  1. Браузер — HTTP-кеш на диску (керується заголовками відповіді), кеш у пам'яті вкладки, кеш стану (TanStack Query, SWR), Service Worker.
  2. CDN — мережа серверів по світу; кешує статичні файли і, за бажанням, HTML/API-відповіді.
  3. Reverse proxy — nginx або Varnish перед застосунком можуть кешувати відповіді за тими самими HTTP-правилами.
  4. Application cache — Redis або пам'ять процесу: результати запитів, сесії, обчислення.
  5. База даних — Postgres тримає гарячі сторінки таблиць у shared_buffers, а ОС — у page cache; правильно налаштована база рідко читає з диска.
  6. Диск — куди запит доходить лише при промаху всіх рівнів.

3. HTTP-кешування: Cache-Control, ETag, 304

HTTP-кеш описано у RFC 9111, і його поведінка визначається заголовками відповіді. Це найдешевший кеш, бо ним керує один рядок, а працює він у браузері, у CDN і в проксі одночасно.

Важлива тонкість: no-cache не означає «не кешувати» — це означає «кешувати, але завжди питати сервер, чи актуально». «Не кешувати» — це no-store. Ця плутанина в назвах — джерело половини помилок з HTTP-кешем.

Умовні запити: ETag і Last-Modified

Коли відповідь застаріла (або стоїть no-cache), браузер не викидає її, а надсилає умовний запит (conditional request): «у мене є версія з таким-то ETag, вона ще актуальна?» ETag (entity tag) — це рядок-відбиток вмісту, зазвичай хеш. Якщо на сервері та сама версія — він відповідає 304 Not Modified без тіла, і браузер використовує свою копію. Економія — весь обсяг тіла відповіді.

// Express: ETag для JSON-відповіді вручну (Express має вбудований etag для res.send,
// але явний код показує механізм)
import { createHash } from "node:crypto";

app.get("/api/notes", async (req, res) => {
  const notes = await listNotes();
  const body = JSON.stringify(notes);
  // Слабкий ETag (W/) — «семантично той самий», достатньо для API
  const etag = `W/"${createHash("sha1").update(body).digest("base64url")}"`;

  res.set("ETag", etag);
  res.set("Cache-Control", "private, no-cache");   // кешувати, але завжди перевіряти

  // Браузер надіслав хеш своєї копії — і він збігається
  if (req.get("If-None-Match") === etag) {
    return res.status(304).end();                  // без тіла
  }
  res.type("json").send(body);
});

Last-Modified / If-Modified-Since — старіший механізм на основі дати з точністю до секунди. ETag точніший і працює для згенерованого контенту, де «дати зміни» немає.

Immutable і хеш у назві файлу

Найкраща стратегія для статики (JS, CSS, шрифти, зображення): бандлер додає хеш вмісту до імені файлу (app.3f9a2c1d.js), а сервер віддає його з Cache-Control: public, max-age=31536000, immutable (рік). Файл кешується назавжди — і це безпечно, бо коли вміст зміниться, зміниться і хеш, і HTML посилатиметься на новий URL. Сам HTML при цьому — no-cache, щоб завжди підхоплювати нові імена файлів. Vite, Next.js і Webpack роблять хешування за замовчуванням.

// Express: різні правила для різних типів
import express from "express";

app.use("/assets", express.static("dist/assets", {
  immutable: true,
  maxAge: "1y",           // Cache-Control: public, max-age=31536000, immutable
}));

app.get("*", (req, res) => {
  res.set("Cache-Control", "no-cache");           // HTML завжди перевіряється
  res.sendFile("dist/index.html", { root: "." });
});
Підводні камені
  • Vary. Якщо відповідь залежить від заголовка запиту (мова через Accept-Language, стиснення через Accept-Encoding), потрібно вказати Vary: Accept-Language — інакше CDN віддасть українську версію англомовному користувачу.
  • Персональні дані з public. Відповідь «мої нотатки» з public, max-age=60 потрапляє у CDN — і наступний користувач бачить чужі нотатки. Для всього, що залежить від cookie/токена, — private або no-store.
  • Довгий max-age без хешу в імені. style.css з max-age=86400 — і після деплою користувачі добу бачать старі стилі. Або хеш в імені, або короткий max-age.
  • Дефолти Express. res.json() сам ставить ETag, але не Cache-Control; без нього браузери застосовують евристичний кеш, і поведінка непередбачувана. Завжди задавайте явно.

4. CDN: кеш на краю мережі

Мережа доставки контенту (Content Delivery Network, CDN) — це сотні серверів («edge-нод», точок присутності, PoP) по всьому світу. Користувач з Києва йде на найближчу ноду у Варшаві або Франкфурті, а не на ваш сервер у Вірджинії. Якщо нода має свіжу копію — відповідає за 10–20 мс. Якщо ні — йде до вашого «оріджину» (origin), зберігає відповідь і віддає її наступним.

Що кешувати у CDN: усю статику (з immutable), зображення, публічні сторінки і API-відповіді, які однакові для всіх (список товарів, стаття блогу) — з s-maxage і stale-while-revalidate. Що не кешувати: персоналізовані відповіді, POST/PUT, усе з Set-Cookie.

Purge (очищення) — коли треба оновити кеш до закінчення TTL: після публікації статті ви викликаєте API CDN «забудь /blog/my-post» (або за тегом: Cloudflare Cache-Tag, Fastly Surrogate-Key). Це подієва інвалідація, про яку буде далі. Сучасні CDN (Cloudflare, Fastly, Vercel Edge, AWS CloudFront) також виконують код на edge — маршрутизацію, A/B-тести, автентифікацію — але це вже поза кешуванням.

5. Серверний кеш: патерни і Redis

Коли HTTP-кеш не підходить (дані персональні, змінюються часто, або потрібен кеш між запитом до бази і відповіддю), кешують на сервері. Є чотири класичні патерни, які відрізняються тим, хто і коли пише в кеш.

  • Cache-aside (lazy loading) — застосунок спершу дивиться в кеш; при промаху читає з бази і кладе в кеш. Кешується лише те, що справді запитували. Найпоширеніший патерн для Redis.
  • Read-through — те саме, але логіка «при промаху сходи в базу» захована у бібліотеці кешу. Код застосунку простіший.
  • Write-through — кожен запис іде і в кеш, і в базу синхронно. Кеш ніколи не застарілий, але записи повільніші, і кешується все підряд, навіть те, що ніхто не читає.
  • Write-behind — запис у кеш, а в базу — асинхронно пачками. Дуже швидко, але якщо кеш впаде до синхронізації — дані втрачено. Для лічильників переглядів годиться, для платежів — ні.
// src/cache.ts — cache-aside на Redis з ioredis
import Redis from "ioredis";
import { config } from "./config.js";

export const redis = new Redis(config.REDIS_URL);

/**
 * Читає значення з кешу; при промаху викликає loader, зберігає результат з TTL.
 * @param key   ключ у Redis, напр. "notes:user:42"
 * @param ttlSec час життя в секундах
 * @param loader функція, що дістає дані з джерела істини
 */
export async function cached<T>(key: string, ttlSec: number, loader: () => Promise<T>): Promise<T> {
  const hit = await redis.get(key);
  if (hit !== null) {
    return JSON.parse(hit) as T;               // HIT — база не задіяна
  }

  const value = await loader();                // MISS — йдемо в базу
  // Кладемо в кеш. Джитер ±10 % до TTL — щоб ключі не протухали всі одночасно
  const jitter = Math.floor(ttlSec * (0.9 + Math.random() * 0.2));
  await redis.set(key, JSON.stringify(value), "EX", jitter);
  return value;
}

// src/notes/service.ts — використання
export async function listNotesForUser(userId: number) {
  return cached(`notes:user:${userId}`, 60, () =>
    db.select().from(notes).where(eq(notes.userId, userId)).orderBy(desc(notes.createdAt)),
  );
}

export async function createNote(userId: number, data: NewNote) {
  const [note] = await db.insert(notes).values({ ...data, userId }).returning();
  // Подієва інвалідація: після запису прибираємо застарілий список
  await redis.del(`notes:user:${userId}`);
  return note;
}

Кілька правил гарного ключа: простір імен через двокрапку (notes:user:42), версія схеми у ключі, якщо формат даних змінюється (v2:notes:user:42) — тоді після деплою старий кеш просто ігнорується, і жоден null не зламає парсинг. І завжди TTL: ключ без TTL — витік пам'яті в Redis.

Пам'ять процесу чи Redis?

Кеш у пам'яті Node (Map, lru-cache) — найшвидший (наносекунди) і не потребує мережі. Але він локальний для одного процесу: при двох репліках у кожної свій кеш, і після інвалідації в одній друга віддає старе. Redis — спільний для всіх реплік, переживає перезапуск застосунку, дає атомарні операції і TTL. Типовий вибір: Redis для всього спільного; пам'ять — для дрібних незмінних довідників (список країн, конфіг) або як перший рівень перед Redis.

6. Інвалідація і cache stampede

Жарт Філа Карлтона, який Мартін Фаулер зробив відомим: «У комп'ютерних науках є лише дві складні проблеми: інвалідація кешу і найменування речей». Покласти в кеш легко. Складно — дізнатися, коли копія стала неправдивою.

TTL проти подієвої інвалідації

TTL (time-to-live) — просто: кеш живе N секунд і вмирає. Плюс — нічого не треба відстежувати, застарілість обмежена N. Мінус — протягом N секунд користувач може бачити старе, і навпаки, при рідких змінах ви даремно перечитуєте базу щоN секунд.

Подієва (event-driven) — при кожній зміні даних код явно видаляє або оновлює відповідні ключі (як redis.del у прикладі вище). Плюс — свіжість одразу. Мінус — треба знати всі ключі, що залежать від запису (нотатка входить у список користувача, у пошук, у стрічку тегів...), і не пропустити жодного шляху зміни (міграція, адмінка, фоновий воркер).

На практиці поєднують: подієва інвалідація для головних шляхів плюс TTL як страховка на випадок, якщо якийсь шлях пропустили. Для складних залежностей використовують теги: кожен ключ позначають тегами (user:42, note:7), а інвалідація йде за тегом — так працюють Next.js revalidateTag і Cloudflare Cache-Tag.

Cache stampede (thundering herd)

Сценарій: популярний ключ протух. У цю ж мілісекунду 500 запитів одночасно бачать промах і всі 500 біжать у базу з одним і тим самим важким запитом. База захлинається, латентність злітає, деякі запити падають за таймаутом — і кеш так і не заповнюється. Це «тиснява біля каси» (stampede) або «гуркіт стада» (thundering herd).

// cache-aside з замком проти stampede
export async function cachedWithLock<T>(key: string, ttlSec: number, loader: () => Promise<T>): Promise<T> {
  const hit = await redis.get(key);
  if (hit !== null) return JSON.parse(hit) as T;

  const lockKey = `${key}:lock`;
  // SET NX EX — атомарно: встановити, лише якщо ключа немає, з таймаутом 10 с
  const gotLock = await redis.set(lockKey, "1", "EX", 10, "NX");

  if (gotLock) {
    try {
      const value = await loader();
      await redis.set(key, JSON.stringify(value), "EX", ttlSec);
      return value;
    } finally {
      await redis.del(lockKey);
    }
  }

  // Замок у когось іншого: трохи чекаємо і пробуємо кеш знову
  for (let i = 0; i < 20; i++) {
    await new Promise((r) => setTimeout(r, 50));
    const retry = await redis.get(key);
    if (retry !== null) return JSON.parse(retry) as T;
  }
  return loader();   // так і не дочекалися — йдемо в базу самі (краще, ніж помилка)
}

У межах одного процесу Node простіший варіант — тримати Map<key, Promise> запитів «у польоті» і повертати той самий проміс усім, хто спитав про той самий ключ (патерн single-flight, або dedupe). Це те, що робить TanStack Query на фронтенді і React.cache у Server Components.

7. Кеш на рівні бази даних

Postgres кешує сам: shared_buffers (зазвичай 25 % RAM) тримає гарячі сторінки таблиць та індексів, а ОС додає свій page cache. Тому «повторний запит швидший» — це не магія, а сторінки в пам'яті. EXPLAIN (ANALYZE, BUFFERS) показує shared hit проти read — скільки сторінок узято з кешу, а скільки з диска.

Але Postgres не кешує результати запитів (на відміну від старого MySQL query cache). Два однакових SELECT виконуються двічі — швидко, бо дані в пам'яті, але з повним плануванням і виконанням. Для важких агрегацій (звіт за місяць, топ-100, статистика) є матеріалізовані в'юшки (materialized views) — збережений результат запиту, який оновлюють за розкладом:

-- Важкий запит: статистика нотаток по користувачах
CREATE MATERIALIZED VIEW user_note_stats AS
SELECT user_id,
       count(*)                          AS total,
       count(*) FILTER (WHERE archived)  AS archived,
       max(created_at)                   AS last_note_at
FROM notes
GROUP BY user_id;

-- Індекс на матеріалізованій в'юшці — можна, як на таблиці
CREATE UNIQUE INDEX ON user_note_stats (user_id);

-- Оновлення (за cron або після пачки записів).
-- CONCURRENTLY не блокує читання, але потребує унікального індексу
REFRESH MATERIALIZED VIEW CONCURRENTLY user_note_stats;

-- Читання — миттєве, це просто таблиця
SELECT * FROM user_note_stats WHERE user_id = 42;

Матеріалізована в'юшка — це кеш всередині бази з тими самими компромісами: застаріває до наступного REFRESH, займає місце, потребує стратегії оновлення. Але вона транзакційно узгоджена з рештою бази, і для аналітичних панелей це часто найпростіше рішення. Також існує підготовлене планування: PREPARE/prepared statements кешують план запиту (не результат) — ORM і драйвери (pg, Drizzle) роблять це автоматично для повторюваних запитів.

8. Кеш на фронтенді: TanStack Query і Next.js

На клієнті кеш вирішує іншу проблему: не «розвантажити базу», а «не показувати спінер, коли дані вже є». TanStack Query (колишній React Query) — стандарт де-факто для серверного стану в React. Кожен запит має ключ, кешується в пам'яті, і бібліотека керує свіжістю за принципом stale-while-revalidate: показує те, що є, і оновлює у фоні.

// features/notes/api.ts
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

export function useNotes() {
  return useQuery({
    queryKey: ["notes"],                        // ключ кешу — як у Redis
    queryFn: () => fetch("/api/notes").then((r) => r.json()),
    staleTime: 30_000,        // 30 с вважати свіжими: повторний монтаж не робить запит
    gcTime: 5 * 60_000,       // 5 хв тримати в пам'яті після того, як ніхто не використовує
    // За замовчуванням: refetch при фокусі вікна і відновленні мережі
  });
}

export function useCreateNote() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (data: { title: string }) =>
      fetch("/api/notes", { method: "POST", body: JSON.stringify(data),
        headers: { "Content-Type": "application/json" } }).then((r) => r.json()),
    // Подієва інвалідація на клієнті: позначити ["notes"] застарілим → refetch
    onSuccess: () => qc.invalidateQueries({ queryKey: ["notes"] }),
  });
}

Зверніть увагу на паралель з Redis: ключ, TTL (staleTime), інвалідація після мутації. Ті самі ідеї — інший шар. Плюс дедуплікація: десять компонентів з useNotes() роблять один мережевий запит.

У Next.js App Router кешування вбудоване в fetch на сервері та в маршрутизатор. Механізм змінювався між версіями (перевіряйте документацію вашої версії у node_modules/next/dist/docs/), але концепції стабільні: Data Cache — результат fetch на сервері з next: { revalidate: 60 } (TTL) або next: { tags: ["notes"] } плюс revalidateTag("notes") у Server Action (подієва інвалідація); Full Route Cache — статично відрендерені сторінки; Router Cache — кеш переходів у браузері. Ще раз ті самі два підходи: час або подія.

// app/notes/page.tsx (Server Component)
export default async function NotesPage() {
  const res = await fetch("https://api.example.com/notes", {
    next: { revalidate: 60, tags: ["notes"] },   // TTL 60 с + тег для подієвої інвалідації
  });
  const notes = await res.json();
  return <NotesList notes={notes} />;
}

// app/notes/actions.ts
"use server";
import { revalidateTag } from "next/cache";

export async function createNote(formData: FormData) {
  await fetch("https://api.example.com/notes", { method: "POST", body: formData });
  revalidateTag("notes");   // усі fetch з цим тегом перечитаються при наступному запиті
}

9. Вимірювання: перцентилі, профілювання, EXPLAIN, N+1

Оптимізувати без вимірювання — це вгадувати. А вимірювати неправильно — гірше, ніж не вимірювати, бо дає хибну впевненість.

Чому не середнє: p50, p95, p99

Уявіть 100 запитів: 99 виконались за 10 мс, один — за 5000 мс. Середнє — 60 мс. «Непогано». Але один зі ста користувачів чекав 5 секунд. А якщо сторінка робить 10 API-запитів, шанс, що хоча б один потрапить у «повільний хвіст», — близько 10 %. Середнє ховає хвіст, а користувачі живуть саме в хвості.

Тому латентність описують перцентилями: p50 (медіана) — половина запитів швидша за це; p95 — 95 % швидші, 5 % повільніші; p99 — лише 1 % повільніший. SLO (цільовий рівень сервісу) формулюють як «p99 латентності GET /api/notes < 300 мс». Брендан Грегг наголошує: дивіться на розподіл (гістограму), а не на одне число — бімодальний розподіл (половина 5 мс, половина 500 мс — кеш хіт/міс) середнім і навіть медіаною не побачити.

# autocannon — навантажувальний тест з перцентилями з коробки
npx autocannon -c 50 -d 20 http://localhost:3000/api/notes
# Latency: p50 12 ms · p97.5 48 ms · p99 210 ms · max 1.2 s
# Requests/sec (throughput): 3 800
# Якщо p99 у 20 разів більший за p50 — шукайте, що іноді відбувається: GC, промах кешу, lock у БД

Пропускна здатність (throughput) — запитів за секунду, які система витримує без деградації латентності. Латентність і throughput пов'язані: при наближенні до межі латентність зростає експоненційно (черги). Тестуйте під навантаженням, близьким до реального, а не одним curl.

SELECT * FROM notes WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

--         Buffers: shared hit=2 100    ← перечитали 2100 сторінок (16 МБ) заради 20 рядків

Ключові рядки у виводі: Seq Scan на великій таблиці — майже завжди відсутній індекс; rows= estimated проти actual — велика різниця означає застарілу статистику (ANALYZE notes); Buffers: read — читання з диска, тобто дані не в кеші; Sort Method: external merge — сортування не влізло у work_mem. Сайт use-the-index-luke.com пояснює індекси глибше, ніж будь-яка документація ORM.

N+1

Найпоширеніша проблема продуктивності в коді з ORM: один запит за списком, а потім по одному запиту на кожен елемент.

// ПОГАНО: N+1 — виглядає невинно
const notes = await db.select().from(notesTable);
for (const note of notes) {
  note.author = await db.select().from(users).where(eq(users.id, note.userId));  // ×N
}

// ДОБРЕ 1: JOIN — один запит
const rows = await db
  .select({ note: notesTable, author: users })
  .from(notesTable)
  .innerJoin(users, eq(users.id, notesTable.userId));

// ДОБРЕ 2: batching — два запити, зручно коли JOIN незручний (GraphQL, різні джерела)
const notes = await db.select().from(notesTable);
const ids = [...new Set(notes.map((n) => n.userId))];
const authors = await db.select().from(users).where(inArray(users.id, ids));
const byId = new Map(authors.map((u) => [u.id, u]));
const result = notes.map((n) => ({ ...n, author: byId.get(n.userId) }));

// Drizzle relational queries роблять batching самі:
// db.query.notes.findMany({ with: { author: true } })

Як помітити N+1: увімкніть логування запитів (logger: true у Drizzle, log: ["query"] у Prisma) і подивіться на один HTTP-запит — якщо бачите 101 однаковий SQL з різними id, ось воно. У GraphQL це системна проблема, тому там стандарт — DataLoader, який збирає всі load(id) за один тік event loop в один IN-запит.

З'єднання, стиснення, HTTP/2

Пул з'єднань (connection pooling). Відкриття TCP-з'єднання і автентифікація в Postgres коштують 20–50 мс і пам'ять на бекенді. Тому драйвер тримає пул готових з'єднань (pg.Pool, max: 10–20) і перевикористовує їх. При serverless чи багатьох репліках з'єднань стає забагато — тоді ставлять зовнішній пулер (PgBouncer, Supavisor, Neon pooler).

Стиснення. Текстові відповіді (JSON, HTML, JS) стискаються у 5–10 разів. Brotli трохи кращий за gzip для статики (стискати заздалегідь при збірці), gzip швидший для динаміки. Робити це краще на reverse proxy (Caddy робить автоматично), а не в Node.

Keep-alive і HTTP/2. HTTP/1.1 keep-alive перевикористовує TCP-з'єднання між запитами (заощаджує рукостискання). HTTP/2 мультиплексує багато запитів в одному з'єднанні і стискає заголовки — особливо помітно для сторінок з десятками ресурсів. Вмикається на proxy (Caddy — за замовчуванням, nginx — listen 443 ssl http2). Для вихідних запитів з Node до інших сервісів — new Agent({ keepAlive: true }) або undici, який робить це сам.

Спробуй сам: пришвидшити API нотаток у 10 разів
  1. Заповніть базу: 1 000 користувачів, 200 000 нотаток (скрипт з faker, вставка пачками по 1 000).
  2. Зробіть GET /api/notes?userId=42 з автором кожної нотатки навмисно через N+1. Виміряйте autocannon: запишіть p50, p99, RPS.
  3. Увімкніть логування SQL і порахуйте запити на один HTTP-виклик.
  4. Замініть на JOIN. Виміряйте знову. Потім EXPLAIN ANALYZE — знайдіть Seq Scan, додайте індекс (user_id, created_at DESC). Виміряйте.
  5. Додайте cache-aside у Redis на 60 с з інвалідацією при POST. Виміряйте. Порівняйте p50 і p99 — p99 має впасти найбільше.
  6. Додайте ETag і Cache-Control: private, no-cache. У DevTools перевірте 304 при повторному запиті.
  7. Складіть таблицю: етап → p50 → p99 → RPS. Це і є ваш звіт про продуктивність.

10. Фронтенд-продуктивність коротко

Найшвидший API не врятує сторінку, яка вантажить 3 МБ JavaScript. Кілька головних важелів:

  • Розмір бандла. Перевіряйте, що потрапляє в бандл (vite-bundle-visualizer, @next/bundle-analyzer). Типові винуватці: moment.js замість date-fns або Temporal, lodash цілком замість окремих функцій, іконки всі одразу. Tree-shaking працює лише з ES-модулями.
  • Розділення коду і lazy loading. React.lazy(() => import("./HeavyChart")) + Suspense: важкий компонент вантажиться, коли справді потрібен. Next.js робить це по маршрутах автоматично; next/dynamic — для компонентів.
  • Зображення. Найбільша частина ваги більшості сторінок. WebP/AVIF замість JPEG/PNG (у 2–3 рази менші), srcset/sizes для різних екранів, loading="lazy" для того, що нижче згину, явні width/height проти стрибків верстки. next/image робить усе це.
  • Шрифти. font-display: swap, підмножини (subset) лише потрібних символів, preload для головного шрифту. next/font — self-hosting без запитів до Google.
  • Критичний шлях. Блокуючі скрипти в <head> без defer, CSS на 500 КБ, третій сторони (аналітика, чати) — усе, що стоїть між HTML і першим рендером.

Lighthouse (у Chrome DevTools або npx lighthouse URL) дає оцінку і конкретний список проблем. Метрики Core Web Vitals: LCP (Largest Contentful Paint — коли з'явився головний контент, ціль < 2,5 с), INP (Interaction to Next Paint — відгук на клік, < 200 мс), CLS (Cumulative Layout Shift — стрибки верстки, < 0,1). Важливо: Lighthouse — лабораторні дані на вашому ноутбуці; реальні користувачі з телефонами в метро дають польові дані (CrUX, web-vitals бібліотека) — саме вони враховуються Google і саме на них треба дивитися.

Для просунутих

Наступний рівень: Service Worker з Workbox — програмований кеш у браузері, офлайн-режим, стратегії cache-first/network-first на рівні URL; ISR (Incremental Static Regeneration) — статичні сторінки, які перегенеруються у фоні за TTL, поєднання швидкості статики зі свіжістю; Edge caching API з ключем за користувачем через Vary: Cookie на Fastly/Cloudflare Workers; кеш з версіонуванням у ключі замість інвалідації: notes:user:42:v{updatedAt} — старі ключі просто протухають за TTL, а промахів через гонки не буває; probabilistic early expiration (алгоритм XFetch з paper «Optimal Probabilistic Cache Stampede Prevention») — елегантне рішення stampede без замків; і continuous profiling у продакшені (Pyroscope, Datadog Profiler), бо профіль під autocannon і профіль під реальними користувачами — різні речі.

Перевір себе

Питання
1. Чим no-cache відрізняється від no-store?

no-cache дозволяє зберігати відповідь, але вимагає перевірити її актуальність у сервера перед кожним використанням (умовний запит з ETag → 304). no-store забороняє зберігати взагалі. «Не кешувати» — це no-store.

2. Як працює зв'язка ETag + 304?

Сервер віддає відповідь з ETag (хеш вмісту). Наступного разу браузер надсилає If-None-Match з цим хешем. Якщо вміст не змінився, сервер відповідає 304 Not Modified без тіла, і браузер використовує свою копію — заощаджуючи трафік.

3. Чому статику можна кешувати на рік з immutable?

Бо в імені файлу є хеш вмісту (app.3f9a2c.js). Зміна вмісту → новий хеш → новий URL. Старий файл за старим URL справді ніколи не зміниться, тож його безпечно тримати назавжди. HTML, який посилається на файли, при цьому має бути no-cache.

4. Що таке cache stampede і як його лікують?

Коли популярний ключ протухає і сотні запитів одночасно бачать промах і біжать у базу з одним запитом. Ліки: замок (лише один перераховує, решта чекають або беруть stale), early refresh (оновлення у фоні до закінчення TTL), jitter (випадковий TTL, щоб ключі не протухали разом).

5. Чому середня латентність — погана метрика?

Вона ховає хвіст: 99 запитів по 10 мс і один по 5 с дають середнє 60 мс, хоча один зі ста користувачів чекав 5 секунд. Перцентилі (p95, p99) показують, що відчуває «найнещасніша» частина користувачів, а гістограма — форму розподілу.

6. Що таке N+1 і як його помітити?

Один запит за списком і по одному запиту на кожен елемент списку — 1 + N. Помітити: увімкнути логування SQL і подивитися на один HTTP-запит — багато однакових запитів з різними id. Лікувати: JOIN або batching через IN (DataLoader).

7. Cache-aside чи write-through для списку нотаток користувача?

Cache-aside: списки читаються набагато частіше, ніж змінюються, і кешувати варто лише те, що справді запитують. При записі — інвалідація ключа списку. Write-through виправданий, коли після запису дані майже гарантовано одразу читатимуть, і промах неприпустимий.

8. Навіщо Vary?

Щоб кеш (особливо спільний — CDN) розрізняв версії відповіді, які залежать від заголовка запиту: мова, стиснення, cookie. Без Vary: Accept-Language CDN віддасть одну мову всім.

Що запам'ятати

  • Кеш — копія ближче або швидше; ціна — застарілість. Перед кожним кешем питайте: «скільки секунд застарілості прийнятно?»
  • Шари: браузер → CDN → proxy → Redis → буфери БД → диск. Чим раніше хіт, тим дешевше.
  • Cache-Control керує HTTP-кешем: max-age/s-maxage — TTL, no-cache — перевіряти, no-store — не зберігати, private — для персонального, stale-while-revalidate — миттєво + оновити у фоні.
  • ETag + If-None-Match → 304 економить тіло відповіді; хеш в імені + immutable — кеш статики назавжди.
  • Серверні патерни: cache-aside (найпоширеніший), read-through, write-through, write-behind. Ключ з простором імен, завжди TTL, jitter.
  • Інвалідація: TTL (просто, обмежена застарілість) + подієва (свіжо, треба знати всі ключі) + теги. Stampede лікують замком, early refresh, jitter.
  • Вимірюйте перцентилями (p50/p95/p99), не середнім; профілюйте Node (--cpu-prof, Clinic), читайте EXPLAIN ANALYZE, шукайте N+1 у логах SQL.
  • Пул з'єднань, стиснення на proxy, HTTP/2, keep-alive — дешеві перемоги; на фронтенді — бандл, lazy, зображення, Lighthouse і польові Web Vitals.
