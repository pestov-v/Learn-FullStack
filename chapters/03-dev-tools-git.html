Пояснення для п'ятирічного

Уяви, що ти будуєш замок із LEGO. Термінал — це коли замість того, щоб тицяти пальцем у деталі, ти кажеш помічнику словами: «дай червону цеглинку», «покажи, що в коробці». Спочатку незвично, але потім швидше, ніж мишкою. npm — це магазин готових наборів LEGO: замість того щоб ліпити колесо самому, береш готове. Git — це чарівний фотоапарат: після кожного кроку ти робиш знімок замку, і якщо щось зламав — можна повернутись до будь-якого знімка. А ще можна будувати замок удвох, кожен свою вежу, і потім з'єднати. GitHub — це полиця в інтернеті, куди ви обоє кладете свої знімки.

1. Термінал: розмова з комп'ютером текстом

Термінал (terminal) — це вікно, в яке ви пишете команди, а комп'ютер відповідає текстом. Програма, яка розуміє команди, називається оболонкою (shell): на macOS і Linux це зазвичай zsh або bash, на Windows — PowerShell, а краще встановити WSL (Windows Subsystem for Linux) або Git Bash, щоб команди збігались із рештою світу.

Навіщо це, якщо є мишка? Бо всі інструменти розробника — npm, git, docker, компілятори — живуть у терміналі. Мишкою не запустиш тести і не задеплоїш сервер. А ще команди можна записати у файл і повторювати автоматично.

Термінал завжди «стоїть» у якійсь теці — це поточна директорія (working directory). Більшість команд працюють відносно неї:

pwd                     # де я? (print working directory) → /Users/you/projects
ls                      # що тут лежить? (list)
ls -la                  # детально, включно з прихованими файлами (починаються з крапки)
cd projects             # зайти в теку (change directory)
cd ..                   # на рівень вище
cd ~                    # у домашню теку
cd -                    # туди, де був до цього

mkdir my-app            # створити теку
touch index.html        # створити порожній файл
cat package.json        # показати вміст файлу
head -n 20 app.log      # перші 20 рядків
tail -f app.log         # «стежити» за файлом — нові рядки з'являються живцем
cp a.txt b.txt          # скопіювати
mv old.txt new.txt      # перейменувати або перемістити
rm file.txt             # видалити файл (без кошика! назавжди)
rm -rf node_modules     # видалити теку рекурсивно і без питань — обережно

Три суперсили: grep, | і >

grep шукає рядки за шаблоном. Конвеєр (pipe) | передає вивід однієї команди на вхід іншій — як труба, по якій вода тече з крана в чайник. Перенаправлення > записує вивід у файл замість екрана (>> — дописує в кінець).

# Знайти всі рядки з "TODO" у файлах .js у поточній теці і підтеках
grep -rn "TODO" --include="*.js" .

# Конвеєр: показати вміст → відфільтрувати → порахувати рядки
cat app.log | grep "ERROR" | wc -l

# Хто слухає порти? Відфільтрувати тільки node
lsof -i -P | grep node

# Записати результат у файл
ls -la > files.txt
echo "нове" >> notes.txt

# Історія команд і пошук по ній (Ctrl+R у більшості оболонок)
history | grep "git commit"
Чому це важливо

Термінал — це спільна мова всіх інструментів. Кожна інструкція в документації, кожен CI-скрипт, кожен деплой — це команди. Хто не володіє терміналом, той копіює команди «наосліп» і не може зрозуміти, чому не спрацювало. Годину, вкладену в базові команди зараз, ви відіб'єте за перший тиждень.

Спробуй сам
  1. Відкрий термінал. Виконай pwd, потім mkdir -p ~/projects/playground && cd ~/projects/playground.
  2. Створи файл: echo "рядок 1" > test.txt, допиши: echo "рядок 2" >> test.txt, подивись: cat test.txt.
  3. Порахуй файли у своїй домашній теці: ls ~ | wc -l.
  4. Знайди, де лежить node: which node. Якщо порожньо — час встановити (наступна секція).
  5. Натисни Tab посеред набору назви файлу — оболонка доповнить. Натисни стрілку вгору — попередня команда.

2. Редактор: VS Code

Код можна писати в Блокноті, але VS Code (Visual Studio Code) — безкоштовний редактор від Microsoft, який став стандартом: підсвічує синтаксис, підказує імена функцій, показує помилки до запуску, має вбудований термінал і Git. Встановлюється з code.visualstudio.com. Після встановлення додайте команду code у термінал (Cmd+Shift+P → «Shell Command: Install 'code' command in PATH»), тоді code . відкриє поточну теку.

Розширення, з яких варто почати:

  • ESLint і Prettier — підкреслюють помилки і форматують код при збереженні (про них у секції 8).
  • GitLens — показує, хто і коли змінив кожен рядок, прямо в редакторі.
  • Error Lens — виводить текст помилки поряд із рядком, а не тільки червону хвильку.
  • Live Server — відкриває HTML-файл через локальний сервер із автооновленням (потрібно для fetch, бо file:// має обмеження).
  • Path Intellisense — автодоповнення шляхів до файлів у імпортах.

Гарячі клавіші, які економлять години: Cmd/Ctrl+P — швидко відкрити файл за назвою; Cmd/Ctrl+Shift+P — палітра команд; Cmd/Ctrl+D — виділити наступне таке саме слово (мультикурсор); Cmd/Ctrl+` — термінал; F2 — перейменувати змінну скрізь; Alt+↑/↓ — перемістити рядок.

3. Node.js, npm, pnpm і package.json

Node.js — це середовище, яке дозволяє запускати JavaScript поза браузером: на сервері, у терміналі, у скриптах збірки. Той самий двигун V8, що в Chrome, але замість document і window — доступ до файлів, мережі, процесів. Встановлюйте LTS-версію (зараз 20 або 22) через nodejs.org або менеджер версій nvm / fnm, щоб перемикатись між версіями для різних проєктів.

node --version         # v22.x.x
npm --version          # 10.x.x

# Запустити файл
echo 'console.log("Привіт з Node!")' > hello.js
node hello.js

# REPL — інтерактивна консоль
node
> 2 + 2
4
> .exit

npm — магазин готових деталей

npm (Node Package Manager) — це реєстр із понад двома мільйонами готових бібліотек (пакетів) і команда для їх встановлення. Хочете HTTP-сервер — express; дати — date-fns; перевірка даних — zod. pnpm — швидша альтернатива з тими самими командами: зберігає кожен пакет один раз на диску і робить посилання, тому node_modules не важить гігабайти. Команди майже ідентичні, у прикладах будемо показувати обидва.

package.json — паспорт проєкту

mkdir my-app && cd my-app
npm init -y            # або pnpm init — створює package.json з відповідями «так» на все
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",                  // дозволяє import/export (ES modules)
  "scripts": {
    "dev": "node --watch server.js", // npm run dev — перезапуск при зміні файлів
    "start": "node server.js",       // npm start (без run — для start і test)
    "test": "node --test",
    "lint": "eslint .",
    "format": "prettier --write ."
  },
  "dependencies": {
    "express": "^5.1.0"              // потрібно в продакшені
  },
  "devDependencies": {
    "eslint": "^9.0.0",              // потрібно тільки під час розробки
    "prettier": "^3.3.0"
  }
}
  • dependencies — те, без чого програма не працює у продакшені (фреймворк, драйвер БД).
  • devDependencies — інструменти розробки: лінтери, тести, TypeScript, збірка. На сервер їх не ставлять (npm install --omit=dev).
  • scripts — ярлики для команд. npm run dev запускає те, що записано в dev. Так усі в команді запускають проєкт однаково, не пам'ятаючи довгих команд.
npm install express          # pnpm add express       → у dependencies
npm install -D eslint        # pnpm add -D eslint     → у devDependencies
npm uninstall express        # pnpm remove express
npm install                  # pnpm install — встановити все з package.json (після клонування)
npm run dev                  # pnpm dev
npx eslint .                 # pnpm exec eslint . — запустити бінарник пакета без глобального встановлення
npm outdated                 # що застаріло
npm audit                    # відомі вразливості

node_modules і lock-файли

Після npm install з'являється тека node_modules — туди фізично складаються пакети і всі їхні залежності (express тягне ще ~60 пакетів). Її ніколи не комітять у Git: вона величезна і повністю відновлюється з package.json. А от package-lock.json (або pnpm-lock.yaml) — комітять обов'язково. Він фіксує точні версії всього дерева залежностей, щоб у колеги і на сервері встановилось те саме, що у вас. Команда npm ci (clean install) ставить рівно те, що в lock-файлі, і використовується в CI.

Semver: що означає ^ і ~

Версії пакетів пишуться за семантичним версіонуванням (semver): MAJOR.MINOR.PATCH, наприклад 5.1.3. Кожне число — це обіцянка:

Без префікса ("5.1.3") — рівно ця версія. З ^0.x.y поведінка особлива: для нульових мажорів «ламаючим» вважається MINOR, тому ^0.3.1 дозволить тільки 0.3.x. Це чесно: пакет до 1.0 сам каже «я ще нестабільний».

Підводні камені
  • Помилка Cannot use import statement outside a module — забули "type": "module" у package.json або використовуйте розширення .mjs.
  • «У мене працює, у колеги ні» — хтось не закомітив lock-файл або в різних версіях Node. Додайте "engines": {"node": ">=20"} і файл .nvmrc.
  • npm install глобально (-g) — майже ніколи не потрібен. Використовуйте npx.
  • Не встановлюйте пакети з підозрілими назвами-«друкарськими помилками» (expres, lodahs) — це typosquatting, спосіб підсунути шкідливий код.

4. Git: машина часу для коду

Git — система керування версіями (version control system). Вона вирішує дві проблеми, з якими стикається кожен, хто пише код довше за день:

  1. «Учора все працювало». Git зберігає знімки (коміти, commits) усього проєкту. Можна подивитись, що саме змінилось, і повернутись до будь-якого знімка. Це не «Ctrl+Z»: це повна історія з поясненнями, чому було зроблено кожну зміну.
  2. «Ми обоє правили один файл». Двоє (або двадцять) людей працюють над одним проєктом одночасно, кожен у своїй гілці, і Git уміє акуратно з'єднувати їхні зміни.

Git — це розподілена система: у кожного розробника повна копія всієї історії на своєму комп'ютері. GitHub чи GitLab — просто «полиця», де лежить ще одна копія, зручна для обміну.

Три зони

Найважливіша ментальна модель Git — три зони, через які проходить кожна зміна:

Навіщо staging? Щоб коміт був осмисленим. Ви поправили три файли: два — виправлення бага, один — новий стиль кнопки. Можна додати в staging тільки перші два і закомітити «fix: ...», потім третій — «style: ...». Історія стає читабельною.

Базові команди

# Один раз на комп'ютері — хто автор комітів
git config --global user.name "Ім'я Прізвище"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

# Почати відстежувати проєкт
cd my-app
git init                        # створює приховану теку .git

git status                      # що змінилось, що в staging, у якій гілці
git add index.html              # покласти файл у staging
git add .                       # усі зміни в поточній теці
git commit -m "feat: додати сторінку списку справ"   # зробити знімок

git log --oneline --graph       # історія коротко
git diff                        # що я змінив і ще не додав
git diff --staged               # що піде в наступний коміт
git show HEAD                   # показати останній коміт повністью

# Відкотити
git restore index.html          # скасувати незакомічені зміни у файлі
git restore --staged index.html # прибрати зі staging (файл не чіпає)
git revert HEAD                 # створити новий коміт, що скасовує останній — безпечно для спільної історії

Кожен коміт має хеш — 40 символів на кшталт a1b2c3d... (зазвичай показують перші 7). Це його ім'я; за ним можна повернутись у будь-який момент історії. HEAD — вказівник на «де я зараз», зазвичай на останньому коміті поточної гілки.

Чому це важливо

Git — це єдиний інструмент, яким користуються 100% команд, незалежно від мови і стеку. Без нього не буває pull request, code review, CI/CD і деплою. Співбесіда на будь-яку junior-позицію включає питання про Git. Але головне — він дає сміливість експериментувати: зламали — повернулись.

5. Гілки, merge і rebase

Гілка (branch) — це паралельна лінія історії. Технічно це просто рухомий вказівник на коміт, тому створення гілки миттєве і безкоштовне. Правило: main завжди робочий, кожна фіча чи виправлення — в окремій гілці.

git branch                          # список гілок, * — поточна
git switch -c feature/login         # створити і перейти (старий синтаксис: checkout -b)
# ... робите коміти ...
git switch main                     # повернутись
git merge feature/login             # влити гілку в main
git branch -d feature/login         # видалити гілку після злиття

Merge створює «злиття» з двома батьками — чесно показує, що робота йшла паралельно. Rebase бере ваші коміти і «пересаджує» їх на вершину іншої гілки, ніби ви почали роботу пізніше. Історія стає лінійною і читабельною, але коміти отримують нові хеші. Звідси залізне правило: ніколи не робіть rebase гілки, яку вже хтось інший забрав до себе — у нього залишаться старі хеші, і при наступному злитті буде хаос.

Типова практика: перед відкриттям pull request оновити свою гілку на свіжий main через git rebase main (це ваші локальні коміти — можна), а сам PR вливати через merge (або squash-merge, коли всі коміти гілки стискаються в один).

Конфлікти

Якщо ви і колега змінили той самий рядок того самого файлу, Git не знає, чиє правильне, і зупиняється з конфліктом (conflict). У файлі з'являються маркери:

function greet() {
<<<<<<< HEAD
  return "Привіт, світе!";        // ваша версія (поточна гілка)
=======
  return "Вітаю, користувачу!";  // версія з гілки, яку зливаєте
>>>>>>> feature/greeting
}

Розв'язати конфлікт означає: відкрити файл, залишити правильний варіант (або скомбінувати), прибрати всі маркери <<<<<<<, =======, >>>>>>>, потім git add файл і git commit (або git rebase --continue, якщо це був rebase). VS Code показує кнопки «Accept Current / Incoming / Both» прямо над конфліктом. Якщо все пішло не так — git merge --abort або git rebase --abort повертає все, як було.

Підводні камені
  • git push --force на спільну гілку перезаписує чужу роботу. Якщо вже дуже треба — --force-with-lease: він відмовиться, якщо хтось запушив після вас.
  • Закомітили у main замість гілки: git switch -c feature/x (гілка створиться з поточними комітами), потім git switch main && git reset --hard origin/main.
  • Закомітили пароль. Просто видалити файл наступним комітом не допоможе — він в історії. Вважайте секрет скомпрометованим, змініть його, а історію чистіть через git filter-repo.
  • Величезні коміти «зробив усе» — неможливо ревʼювати і неможливо відкотити частину. Комітьте маленькими логічними кроками.

6. GitHub, pull request і командний потік

GitHub (і GitLab, Bitbucket) — сервіс, що хостить Git-репозиторії і додає командну роботу зверху: pull request (PR), обговорення, автоматичні перевірки (CI), issue-трекер. Створіть акаунт на github.com і налаштуйте SSH-ключ або gh auth login через GitHub CLI, щоб не вводити пароль щоразу.

# Прив'язати локальний репозиторій до GitHub (після створення там порожнього репо)
git remote add origin git@github.com:you/my-app.git
git push -u origin main         # -u запам'ятає зв'язок; далі просто git push

# Забрати чужий проєкт
git clone git@github.com:you/my-app.git
cd my-app && npm install

# Синхронізуватись
git fetch                       # завантажити зміни, не чіпаючи мої файли
git pull                        # fetch + merge у поточну гілку
git pull --rebase               # fetch + rebase — чистіша історія

Типовий робочий потік команди

Code review — це не екзамен, а спільне читання коду: колега шукає баги, пропонує простіші рішення, ділиться знанням про кодову базу. Гарний PR — маленький (до ~300 рядків), з описом «що і навіщо», зі скріншотом, якщо є UI. Гарний ревʼюер — коментує конкретно, пояснює «чому», відрізняє «обов'язково» від «на ваш розсуд» (nit:).

Гарні повідомлення комітів

Коміт «fix» через півроку нічого не скаже. Стандарт Conventional Commits задає формат: тип(область): короткий опис. Типи: feat (нова функція), fix (виправлення), docs, style (форматування), refactor, test, chore (службове: залежності, конфіги). Опис — у наказовому способі, без крапки в кінці, до 72 символів. Детальніше — в тілі після порожнього рядка.

feat(cart): додати кнопку «Очистити кошик»

Користувачі просили спосіб швидко прибрати всі товари.
Кнопка показується тільки якщо кошик не порожній.

Closes #42

Такий формат читається людьми і машинами: з нього автоматично генерують changelog і визначають наступну версію за semver (feat → MINOR, fix → PATCH, feat!: або BREAKING CHANGE → MAJOR).

Спробуй сам
  1. Візьми проєкт «список справ» з розділу 02. У його теці: git init, git add ., git commit -m "feat: початковий список справ".
  2. Створи гілку git switch -c feat/clear-done, додай кнопку «Очистити виконані», закоміть із правильним повідомленням.
  3. Повернись у main, зміни колір кнопки «Додати» у CSS, закоміть. Тепер git merge feat/clear-done. Конфлікту не буде — різні файли. Подивись git log --oneline --graph.
  4. Тепер створи конфлікт навмисно: у двох гілках зміни один і той самий рядок заголовка <h1>. Злий і розв'яжи конфлікт руками.
  5. Створи репозиторій на GitHub, запуш, відкрий Pull Request із нової гілки у main і злий його через інтерфейс.
  6. Пройди перші 2 рівні на learngitbranching.js.org — це візуальний тренажер гілок.

7. Секрети, .env і .gitignore

Ваш код рано чи пізно потребуватиме пароль від бази даних, ключ платіжної системи, токен API. Ніколи не пишіть їх у коді і ніколи не комітьте. Репозиторій може стати публічним, його бачить уся команда, підрядники, і боти сканують GitHub на витоки ключів за секунди після пушу.

Стандарт — файл .env у корені проєкту: рядки КЛЮЧ=значення, які читаються як змінні середовища (environment variables). Node 20+ уміє читати його без бібліотек через прапорець --env-file:

# .env — НЕ комітити
DATABASE_URL=postgres://user:secret@localhost:5432/app
STRIPE_SECRET_KEY=sk_test_abc123
PORT=3000
# .env.example — комітити: ті самі ключі, але без значень, як документація
DATABASE_URL=
STRIPE_SECRET_KEY=
PORT=3000
// server.js — запуск: node --env-file=.env server.js
const port = process.env.PORT ?? 3000;
const dbUrl = process.env.DATABASE_URL;

if (!dbUrl) {
  throw new Error("DATABASE_URL не задано. Скопіюйте .env.example у .env");
}
console.log(`Сервер на порту ${port}`);

На сервері чи в CI ці змінні задаються в панелі хостингу або в налаштуваннях GitHub Actions (Secrets) — файл .env там не потрібен.

.gitignore

Файл .gitignore у корені проєкту перелічує, що Git має ігнорувати. Мінімальний набір для Node-проєкту:

# залежності — відновлюються з package.json
node_modules/

# секрети
.env
.env.*
!.env.example

# збірка
dist/
build/
.next/

# логи і системне сміття
*.log
.DS_Store
Thumbs.db

# редактор
.vscode/*
!.vscode/extensions.json
.idea/

Якщо файл уже закомічений, додавання в .gitignore його не прибере: виконайте git rm --cached .env, потім закомітьте. Готові шаблони для будь-якої мови є на github.com/github/gitignore.

Чому це важливо

Витік одного ключа AWS у публічний репозиторій — це реальні рахунки на тисячі доларів за майнінг криптовалюти на ваших серверах протягом ночі. Це трапляється щодня. Розділення коду і конфігурації (12-factor app, принцип «Config») — не педантизм, а страховка.

8. Лінтери, форматери і TypeScript

ESLint — знаходить помилки до запуску

Лінтер (linter) читає код і шукає підозрілі місця: невикористана змінна, == замість ===, забутий await, недосяжний код. Це як перевірка орфографії в тексті. ESLint — стандарт для JavaScript і TypeScript.

npm init @eslint/config@latest      # інтерактивно створить eslint.config.js
npx eslint .                        # перевірити все
npx eslint . --fix                  # виправити те, що вміє
// eslint.config.js (flat config, ESLint 9+)
import js from "@eslint/js";
import globals from "globals";

export default [
  js.configs.recommended,             // набір розумних правил за замовчуванням
  {
    languageOptions: { globals: { ...globals.browser, ...globals.node } },
    rules: {
      "no-unused-vars": "warn",       // попереджати, а не падати
      "eqeqeq": "error",              // тільки ===
    },
  },
];

Prettier — форматує, щоб не сперечатись

Форматер (formatter) переписує код за єдиними правилами: відступи, лапки, крапки з комою, довжина рядка. Суперечки «таби чи пробіли» зникають: команда обирає конфіг один раз, і Prettier форматує при збереженні. Він не шукає помилок — тільки вигляд.

npm install -D prettier
echo '{ "semi": true, "singleQuote": false, "printWidth": 100 }' > .prettierrc
npx prettier --write .              # відформатувати все
npx prettier --check .              # перевірити (для CI)

У VS Code: встановіть розширення Prettier, у налаштуваннях увімкніть "editor.formatOnSave": true і "editor.defaultFormatter": "esbenp.prettier-vscode". Щоб ESLint не сварився з Prettier за форматування, додайте eslint-config-prettier, який вимикає конфліктні правила. Часто обидва запускають перед комітом через git hooks (пакети husky + lint-staged), щоб поганий код фізично не потрапив у репозиторій.

TypeScript — навіщо типи

JavaScript дозволяє написати user.nmae замість user.name, і ви дізнаєтесь про помилку тільки коли користувач побачить undefined на екрані. TypeScript — це JavaScript плюс типи (types): ви описуєте, якої форми дані, і компілятор перевіряє це до запуску. Аналогія: розетки. У JS будь-яку вилку можна встромити в будь-яку розетку, і іноді щось вибухає. TypeScript робить вилки різної форми — не та не влізе фізично, і ви побачите це ще в редакторі, а не в продакшені о третій ночі.

// Описуємо форму даних
type Todo = {
  id: number;
  text: string;
  done: boolean;
  dueDate?: Date;          // ? — необов'язкове поле
};

// Функція каже, що приймає і що повертає
function toggle(todo: Todo): Todo {
  return { ...todo, done: !todo.done };
}

const t: Todo = { id: 1, text: "Вивчити TS", done: false };
toggle(t);                 // ✓
toggle({ id: 2 });         // ✗ Помилка: бракує text і done
t.nmae;                    // ✗ Помилка: Property 'nmae' does not exist. Did you mean 'name'?

// Об'єднання типів: значення може бути одним із варіантів
type Status = "idle" | "loading" | "error";
let s: Status = "loading";
s = "done";                // ✗ Помилка: "done" не входить у Status

// Дженерики: функція, що працює з будь-яким типом, не втрачаючи його
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}
const n = first([1, 2, 3]);      // n: number | undefined
const w = first(["a", "b"]);     // w: string | undefined
npm install -D typescript
npx tsc --init                    # створює tsconfig.json
npx tsc --noEmit                  # тільки перевірити типи, нічого не генерувати
node --experimental-strip-types app.ts   # Node 22+: запустити .ts напряму (тільки прості типи)

Головна цінність TypeScript — не «зловити описку», а документація, що не бреше: коли ви бачите function save(user: User), ви точно знаєте, що передати, і редактор підкаже поля. У великих проєктах це економить більше часу, ніж витрачається на написання типів. Далі в посібнику весь код буде на TypeScript.

Для просунутих

Усі інструменти цього розділу складаються в один конвеєр якості: husky запускає lint-staged перед комітом → той проганяє Prettier і ESLint тільки по змінених файлах → CI на GitHub Actions запускає tsc --noEmit, eslint, тести на кожен PR → merge заблоковано, поки перевірки червоні. Це називається «shift left» — ловити проблеми якомога раніше, де вони найдешевші. Налаштування цього конвеєра — тема розділу 11, але вже зараз варто увімкнути formatOnSave і додати скрипт "check": "tsc --noEmit && eslint . && prettier --check ." у package.json.

Перевір себе

Питання
1. Що робить команда cat app.log | grep ERROR | wc -l?

Виводить файл, залишає тільки рядки з «ERROR», рахує їх кількість. Три команди з'єднані конвеєром: вивід кожної — вхід наступної.

2. Чим dependencies відрізняються від devDependencies?

dependencies потрібні для роботи програми у продакшені (express, драйвер БД). devDependencies — тільки під час розробки (eslint, prettier, typescript, тести); на сервер їх не ставлять.

3. Що дозволить встановити "^4.2.1", а що — "~4.2.1"?

^ — будь-яку 4.x.y від 4.2.1 і вище (4.2.9, 4.7.0), але не 5.0.0. ~ — тільки 4.2.x (4.2.9), але не 4.3.0.

4. Навіщо комітити lock-файл, якщо є package.json?

package.json задає діапазони; lock-файл фіксує точні версії всього дерева залежностей, тому у всіх встановлюється однакове. Без нього «у мене працює, у тебе ні».

5. Назвіть три зони Git і команди переходу між ними.

Робоча тека → (git add) → staging → (git commit) → локальний репозиторій → (git push) → віддалений. Назад: fetch/pull, checkout/restore.

6. Коли merge, а коли rebase?

Rebase — для своїх локальних комітів, щоб оновити гілку на свіжий main і мати лінійну історію. Merge — для всього, що вже запушили і бачили інші, бо rebase переписує хеші.

7. Як розв'язати конфлікт?

Відкрити файл, обрати правильний варіант між маркерами <<<<<<< / ======= / >>>>>>>, видалити маркери, git add файл, git commit (або rebase --continue). Скасувати — merge --abort.

8. Що робити, якщо випадково закомітили .env з паролем?

Вважати пароль скомпрометованим і змінити його негайно; додати .env у .gitignore; git rm --cached .env; за потреби вичистити історію через git filter-repo. Просто видалити файл наступним комітом недостатньо — він в історії.

9. Чим ESLint відрізняється від Prettier?

ESLint шукає помилки і підозрілі патерни в логіці (невикористані змінні, ==). Prettier тільки форматує вигляд (відступи, лапки). Використовують обидва разом з eslint-config-prettier.

10. Що дає TypeScript, якщо в браузер усе одно потрапляє JavaScript?

Перевірку форми даних до запуску, автодоповнення і документацію, що не застаріває. Помилки типу «немає такого поля» ловляться в редакторі, а не в користувача.

Що запам'ятати

  • Термінал — спільна мова інструментів: pwd, ls, cd, mkdir, cat, grep, конвеєр |, перенаправлення >.
  • Node.js запускає JS поза браузером; npm/pnpm ставлять пакети; package.json — паспорт проєкту зі scripts.
  • dependencies для продакшену, devDependencies для розробки; node_modules не комітять, lock-файл — обов'язково.
  • Semver MAJOR.MINOR.PATCH: ^ дозволяє MINOR і PATCH, ~ — тільки PATCH.
  • Git: робоча тека → add → staging → commit → репозиторій → push → remote. git status — ваш компас.
  • Кожна задача — в окремій гілці; merge зберігає історію, rebase випрямляє; rebase тільки для незапушених комітів.
  • Конфлікт — це нормально: обрати варіант, прибрати маркери, add, commit.
  • GitHub Flow: гілка → PR → CI + ревʼю → merge → деплой. Маленькі PR, Conventional Commits.
  • Секрети в .env, .env у .gitignore, .env.example у репозиторії.
  • ESLint ловить помилки, Prettier форматує, TypeScript перевіряє типи — усі три до запуску коду.
