У минулому розділі ми складали речі в шафу з підписаними шухлядами, де у кожній шухляді картки одного розміру — це SQL. Але не все зручно класти в однакові картки. Кулінарний рецепт з інгредієнтами, кроками і фото зручніше тримати як одну товсту папку — це MongoDB, документна база. А є речі, які треба діставати миттєво, як цукерки з кишені: «скільки людей зараз онлайн», «чи вже заходив цей гість хвилину тому» — це Redis, база в оперативній пам'яті. А пошук слова у всіх книжках бібліотеки зручно робити за окремим покажчиком слів — це Elasticsearch. NoSQL — це не «краще за шафу», а інші місця для інших речей. Дорослі інженери використовують шафу, папки, кишеню і покажчик разом.

1. Що таке NoSQL і чому воно з'явилось

NoSQL — це не одна технологія, а парасолькова назва для баз даних, які не є класичними реляційними. Спершу термін означав «No SQL» — без мови SQL, а згодом його переосмислили як «Not Only SQL» — не тільки SQL. Це важливий нюанс: NoSQL з'явився не замість реляційних баз, а поруч із ними.

Реляційні бази проєктувалися у 1970–80-х для одного великого сервера. У середині 2000-х Google, Amazon і Facebook зіткнулися з двома проблемами, які не вирішувалися «купити сервер потужніший»:

  1. Масштаб. Дані перестали вміщатися на одну машину. Розкласти реляційну базу зі зв'язками й транзакціями по сотні серверів (горизонтальне масштабування, sharding) — надзвичайно складно: JOIN між таблицями на різних машинах повільний, транзакції через мережу — ще повільніші. Google написав Bigtable, Amazon — Dynamo, і обидві системи свідомо відмовилися від JOIN і глобальних транзакцій заради розподілу по тисячах вузлів.
  2. Гнучкість схеми. У реляційній базі кожна колонка оголошена заздалегідь. Коли продукт змінюється щотижня, а в кожного користувача «профіль» із різним набором полів, суворі міграції стають гальмом. Документні бази дозволили зберігати об'єкти «як є» — у форматі, дуже схожому на JSON.

До цього додалась третя причина, приземленіша: швидкість для окремих задач. Кеш, лічильники, сесії, черги — для них не потрібні ні таблиці, ні транзакції, потрібна лише мілісекундна відповідь. Так з'явився Redis. І четверта: повнотекстовий пошук, де реляційна база з LIKE '%слово%' безнадійно повільна, — Elasticsearch.

Чому це важливо

Найчастіша помилка джуніора — думати, що NoSQL «сучасніший» і тому кращий, або навпаки — що це «іграшка без транзакцій». Насправді вибір бази — це вибір компромісу: що ви віддаєте (зв'язки, транзакції, суворість) і що отримуєте (масштаб, гнучкість, швидкість). Розуміння цих компромісів відрізняє інженера від людини, яка копіює стек із туторіалу.

2. Типи NoSQL-баз: таксономія

NoSQL-бази групують за тим, як вони зберігають дані. П'ять основних сімейств:

Коротко про кожне:

  • Документні (document stores). Одиниця зберігання — документ, тобто вкладена структура «ключ-значення», практично JSON. Документи групуються в колекції. Різні документи однієї колекції можуть мати різні поля. Найпопулярніша — MongoDB.
  • Ключ-значення (key-value). Найпростіша модель: за ключем-рядком лежить значення. Максимально швидко, бо база не розуміє структуру значення (або розуміє мінімально). Redis — в оперативній пам'яті, надшвидкий; DynamoDB — керований сервіс AWS з безмежним масштабом на диску.
  • Колонкові (wide-column). Виглядають як таблиці, але кожен рядок може мати свій набір колонок, а дані зберігаються по колонках і розподіляються по вузлах за ключем партиції. Cassandra витримує мільйони записів на секунду, ціною обмежених запитів (немає JOIN, фільтрувати можна лише за ключем).
  • Графові (graph). Зберігають вузли (люди, товари) і ребра (дружить, купив). Запит «друзі друзів, які купили те, що купив я» у SQL — п'ять JOIN, у Neo4j — один рядок мовою Cypher.
  • Пошукові (search engines). Будують інвертований індекс: для кожного слова — список документів, де воно є. Elasticsearch робить повнотекстовий пошук з морфологією, одруками, фасетами й ранжуванням, що неможливо в SQL з LIKE.

Є ще часові ряди (InfluxDB, TimescaleDB — останній є розширенням Postgres) і векторні (Pinecone, pgvector) для AI-подібності, але їх зазвичай розглядають як спеціалізації колонкових або реляційних.

3. MongoDB: документи, колекції, CRUD

Документи, колекції, BSON

У MongoDB замість таблиці — колекція (collection), замість рядка — документ (document), замість колонок — поля (fields), які можуть бути вкладеними об'єктами та масивами. Документ зберігається у форматі BSON (Binary JSON) — бінарному JSON з додатковими типами: ObjectId, Date, Decimal128, бінарні дані. Ідентифікатор _id створюється автоматично і є первинним ключем.

// Один документ у колекції "posts". Зверніть увагу: автор і теги ВБУДОВАНІ прямо в документ
{
  _id: ObjectId("66e0a1b2c3d4e5f6a7b8c9d0"),
  title: "Про котів",
  slug: "pro-kotiv",
  body: "Коти — це...",
  author: { id: ObjectId("..."), name: "Анна" },       // вкладений об'єкт
  tags: ["коти", "тварини"],                            // масив
  comments: [                                           // масив вкладених документів
    { userName: "Богдан", body: "Клас!", createdAt: ISODate("2026-09-01T10:00:00Z") }
  ],
  stats: { views: 1520, likes: 42 },
  published: true,
  createdAt: ISODate("2026-08-30T08:00:00Z")
}

Один документ = усе, що потрібно для сторінки поста. Один запит замість п'яти JOIN. Це головна перевага документної моделі: дані зберігаються так, як застосунок їх читає.

// src/mongo.mjs
import { MongoClient, ObjectId } from "mongodb";

const client = new MongoClient(process.env.MONGO_URL ?? "mongodb://localhost:27017");
await client.connect();                       // драйвер сам тримає пул з'єднань
const db = client.db("blog");
const posts = db.collection("posts");         // колекція створюється при першому записі

// CREATE
const { insertedId } = await posts.insertOne({
  title: "Про котів",
  slug: "pro-kotiv",
  author: { name: "Анна" },
  tags: ["коти"],
  comments: [],
  stats: { views: 0, likes: 0 },
  published: true,
  createdAt: new Date(),
});

// READ — фільтр як об'єкт, проєкція обирає поля (як SELECT конкретних колонок)
const published = await posts
  .find({ published: true, tags: "коти" })              // "коти" є в масиві tags
  .project({ title: 1, slug: 1, "author.name": 1 })      // 1 = включити
  .sort({ createdAt: -1 })                               // -1 = за спаданням
  .limit(10)
  .toArray();

const one = await posts.findOne({ _id: new ObjectId(insertedId) });

// UPDATE — оператори: $set, $inc, $push, $pull, $unset ...
await posts.updateOne(
  { _id: insertedId },
  {
    $inc: { "stats.views": 1 },                                          // атомарно +1
    $push: { comments: { userName: "Богдан", body: "Клас!", createdAt: new Date() } },
    $set: { updatedAt: new Date() },
  }
);

// Оператори порівняння у фільтрах: $gt, $gte, $lt, $in, $regex, $exists
const recent = await posts.find({ createdAt: { $gte: new Date(Date.now() - 7 * 86400e3) } }).toArray();

// DELETE
await posts.deleteOne({ _id: insertedId });

// Індекси — така сама необхідність, як у Postgres
await posts.createIndex({ slug: 1 }, { unique: true });
await posts.createIndex({ published: 1, createdAt: -1 });   // складений під запит вище
await posts.createIndex({ title: "text", body: "text" });   // простий повнотекстовий

Популярна обгортка над драйвером — Mongoose. Вона додає схеми (так, у «безсхемній» базі!) з валідацією типів, хуками, віртуальними полями і зручнішим API. Більшість команд використовує саме Mongoose: гнучкість Mongo без хаосу.

// Mongoose: схема на рівні застосунку
import mongoose from "mongoose";

const postSchema = new mongoose.Schema({
  title: { type: String, required: true, trim: true, maxlength: 200 },
  slug:  { type: String, required: true, unique: true },
  author: { name: { type: String, required: true } },
  tags: [String],
  stats: { views: { type: Number, default: 0 } },
  published: { type: Boolean, default: false },
}, { timestamps: true });                  // автоматично createdAt / updatedAt

const Post = mongoose.model("Post", postSchema);
await Post.create({ title: "Про SQL", slug: "pro-sql", author: { name: "Богдан" } });
const list = await Post.find({ published: true }).sort("-createdAt").limit(10).lean();

Embedding чи referencing: головне рішення при моделюванні

У SQL ви завжди розкладаєте дані по таблицях і з'єднуєте JOIN. У MongoDB щоразу є вибір: вбудувати (embed) пов'язані дані всередину документа або посилатись (reference) на них за _id, як зовнішнім ключем.

Aggregation pipeline коротко

Аналог GROUP BY/JOIN/підзапитів у MongoDB — конвеєр агрегації: масив етапів, кожен з яких трансформує потік документів і передає далі (та сама ідея, що middleware в Express).

// Скільки постів і переглядів у кожного тега, топ-5
const topTags = await posts.aggregate([
  { $match: { published: true } },                       // як WHERE
  { $unwind: "$tags" },                                  // розгорнути масив: один документ на тег
  { $group: { _id: "$tags", posts: { $sum: 1 }, views: { $sum: "$stats.views" } } }, // як GROUP BY
  { $sort: { views: -1 } },
  { $limit: 5 },
  { $project: { _id: 0, tag: "$_id", posts: 1, views: 1 } }, // як SELECT з перейменуванням
]).toArray();

// $lookup — "JOIN" з іншою колекцією (для referencing)
const withAuthors = await posts.aggregate([
  { $lookup: { from: "users", localField: "authorId", foreignField: "_id", as: "author" } },
  { $unwind: "$author" },
]).toArray();

4. Redis: структури даних, кеш, rate limiter, pub/sub

Redis (REmote DIctionary Server) — сервер структур даних в оперативній пам'яті. Усе лежить у RAM, тому читання і запис займають десятки мікросекунд; Redis обробляє 100 000+ операцій на секунду на одному ядрі. Дані можна періодично скидати на диск (RDB-знімки, AOF-журнал), але основний сценарій — дані, які можна втратити або відновити: кеш, сесії, лічильники, черги, блокування.

На відміну від «простого» key-value, значення в Redis мають типи, і для кожного є свої атомарні команди:

СтруктураЩо цеКомандиДля чого
StringРядок або число до 512 МБSET, GET, INCR, SETEXКеш JSON, лічильники, флаги
HashОб'єкт: поле → значенняHSET, HGET, HGETALL, HINCRBYСесія користувача, профіль, конфіг
ListДвобічна чергаLPUSH, RPOP, BRPOP, LRANGEПрості черги задач, останні N подій
SetМножина унікальних рядківSADD, SISMEMBER, SINTERУнікальні відвідувачі, теги, «хто лайкнув»
Sorted SetМножина з числовим score, відсортованаZADD, ZRANGE, ZREVRANK, ZINCRBYРейтинги, таблиці лідерів, відкладені задачі
StreamЖурнал подій з групами споживачівXADD, XREADGROUPНадійні черги, event sourcing (розділ 13)

Ключова функція — TTL (time to live, час життя): будь-якому ключу можна сказати «зникни через N секунд». Redis сам видалить його. Це те, що робить Redis ідеальним кешем: не треба писати код «очистити застарілі дані».

Кеш (cache-aside) у Node.js із ioredis

docker run --name redis -p 6379:6379 -d redis:7
npm install ioredis
// src/redis.mjs
import Redis from "ioredis";
export const redis = new Redis(process.env.REDIS_URL ?? "redis://localhost:6379");

// src/services/posts.service.mjs — кеш поверх репозиторію з розділу 05
import { redis } from "../redis.mjs";
import { postsRepository } from "../repositories/posts.repository.mjs";

const TTL_SECONDS = 60;

export async function getPost(id) {
  const key = `post:${id}`;

  // 1. Спробувати кеш
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);          // HIT

  // 2. Промах — читаємо базу
  const post = await postsRepository.findById(id); // MISS
  if (!post) return null;

  // 3. Кладемо в кеш із TTL (EX = секунди). Redis сам видалить через хвилину.
  await redis.set(key, JSON.stringify(post), "EX", TTL_SECONDS);
  return post;
}

export async function updatePost(id, data) {
  const post = await postsRepository.update(id, data);
  await redis.del(`post:${id}`);                   // інвалідація: наступне читання піде в базу
  return post;
}

Rate limiter: не більше N запитів на хвилину

Захист від зловживань (брутфорс паролів, спам, скрейпінг) — обмеження кількості запитів з однієї IP-адреси або від одного користувача. Redis для цього ідеальний: атомарний INCR + TTL.

// src/middleware/rateLimit.mjs — фіксоване вікно: 100 запитів на 60 секунд
import { redis } from "../redis.mjs";

export function rateLimit({ limit = 100, windowSec = 60 } = {}) {
  return async (req, res, next) => {
    const key = `rl:${req.ip}:${Math.floor(Date.now() / 1000 / windowSec)}`; // ключ на вікно

    // MULTI/EXEC — кілька команд виконуються атомарно, як мінітранзакція
    const [[, count]] = await redis.multi()
      .incr(key)                 // +1, повертає нове значення (створює ключ = 1, якщо не було)
      .expire(key, windowSec)    // TTL, щоб ключ сам зник після вікна
      .exec();

    res.setHeader("X-RateLimit-Limit", limit);
    res.setHeader("X-RateLimit-Remaining", Math.max(0, limit - count));

    if (count > limit) {
      return res.status(429).json({ error: "Забагато запитів, спробуйте за хвилину" });
    }
    next();
  };
}

// app.mjs
app.use("/auth/login", rateLimit({ limit: 5, windowSec: 60 }));  // жорстко для логіну
app.use(rateLimit({ limit: 300, windowSec: 60 }));                // м'яко для всього

Чому не просто об'єкт у пам'яті Node? Бо з двома екземплярами сервера у кожного був би свій лічильник, і ліміт фактично подвоївся б. Redis — спільна пам'ять для всіх екземплярів. Та сама причина, чому сесії користувачів тримають у Redis, а не в процесі.

Pub/Sub: повідомити всіх одразу

// Publish/Subscribe: один надсилає — усі підписники отримують. Повідомлення НЕ зберігаються:
// хто не слухав у момент публікації — не отримає (для надійних черг — Streams або RabbitMQ, розділ 13)
const sub = new Redis();
const pub = new Redis();   // окреме з'єднання: підписане з'єднання не може робити інші команди

await sub.subscribe("post:published");
sub.on("message", (channel, message) => {
  const post = JSON.parse(message);
  console.log(`Новий пост "${post.title}" — розсилаємо WebSocket-клієнтам`);
});

await pub.publish("post:published", JSON.stringify({ id: 42, title: "Про Redis" }));

Типовий сценарій: три екземпляри API, до кожного підключені WebSocket-клієнти. Коли на екземплярі №1 з'являється новий коментар, він публікує подію в Redis, а екземпляри №2 і №3 отримують її і пересилають своїм клієнтам.

Підводні камені
  • Redis без maxmemory і політики виселення. Пам'ять закінчується — Redis або падає, або відмовляє у записі. Завжди: maxmemory 512mb і maxmemory-policy allkeys-lru (видаляти найдавніше використані) для кешу.
  • Ключі без TTL. «Тимчасовий» кеш без EX живе вічно й з'їдає пам'ять. Для кешу TTL обов'язковий.
  • KEYS * у продакшені. Блокує весь Redis на час перебору мільйонів ключів (Redis теж однопотоковий!). Тільки SCAN.
  • Redis як основна база. При перезапуску без персистентності дані зникають; з персистентністю можна втратити останні секунди. Джерело правди — Postgres, Redis — прискорювач.
  • Забута інвалідація. Оновили пост у базі, кеш лишився старим — користувач бачить «не те» і пише в підтримку. Кожен UPDATE має свій DEL.
Чому це важливо

Redis — найчастіший другий компонент у будь-якому продакшен-стеку після основної бази. Кеш у Redis знижує навантаження на Postgres у десятки разів і робить відповіді миттєвими; rate limiter — перша лінія захисту від атак; сесії в Redis — умова горизонтального масштабування. Уміння сказати «це в Postgres, а це — в Redis із TTL 5 хвилин» — ознака інженера, а не кодера.

CAP-теорема (вступ)

Коли база розподілена по кількох серверах (а всі NoSQL створювались саме для цього), спрацьовує CAP-теорема: із трьох властивостей — Consistency (узгодженість: усі вузли бачать одні дані), Availability (доступність: кожен запит отримує відповідь), Partition tolerance (стійкість до розділення мережі) — під час розриву мережі можна забезпечити лише дві. Оскільки розриви мережі неминучі (P — не вибір, а факт), реальний вибір — C або A під час збою.

Це спрощення: сучасні системи дають налаштовувати вибір на кожен запит (write concern у MongoDB, consistency level у Cassandra), а формулювання «або C, або A» справедливе лише під час збою. Детально — у розділі 14 про розподілені системи. Поки що запам'ятайте практичний висновок: eventual consistency (дані стануть узгодженими «з часом») — нормально для лайків і переглядів, і неприйнятно для балансу рахунку.

6. Polyglot persistence: кілька баз в одній системі

Термін polyglot persistence («багатомовне зберігання») ввів Мартін Фаулер: сучасний застосунок використовує кілька баз даних, кожну для того, у чому вона найкраща. Не «Postgres або Mongo», а «Postgres для замовлень, Redis для кешу і сесій, Elasticsearch для пошуку». Ось реальна архітектура інтернет-магазину:

Розберімо, чому саме так:

  • Замовлення і платежі — Postgres. Тут потрібні транзакції («зарезервувати товар і списати гроші — разом або ніяк»), зовнішні ключі й сувора схема. Втрата або розбіжність даних недопустима.
  • Картка товару — Postgres як джерело, Redis як кеш. Одна й та сама сторінка товару відкривається тисячі разів на хвилину; змінюється — раз на день. Кеш із TTL 5 хвилин знімає 99 % навантаження з бази.
  • Сесія і кошик — Redis. Читаються на кожному запиті (мікросекунди важливі), мають природний TTL (кошик живе 30 днів), і їх можна безболісно втратити (користувач залогіниться знову). Спільні для всіх трьох екземплярів API.
  • Пошук — Elasticsearch. «Кросівки найк 42 червоні» з урахуванням морфології, синонімів, одруків, з фасетами «бренд/розмір/колір» і сортуванням за релевантністю. Postgres із ILIKE цього не вміє; його повнотекстовий пошук (tsvector) — компроміс для малих каталогів.
  • Синхронізація через чергу. Коли товар змінюється в Postgres, API кладе подію в чергу; окремий worker читає її та оновлює документ в Elasticsearch. Так API не чекає на ES, а якщо ES недоступний — подія дочекається в черзі. Це патерн, який детально розберемо в розділі 13.

Мінус polyglot persistence — складність: три системи треба запускати, моніторити, бекапити і синхронізувати. Тому правило для старту: починайте з Postgres + Redis. Це покриває 95 % потреб. MongoDB, Elasticsearch, Cassandra додавайте тоді, коли зможете сформулювати конкретну задачу, яку Postgres не вирішує.

Для просунутих

Синхронізацію між сховищами можна робити без коду в API — через CDC (Change Data Capture): інструмент на кшталт Debezium читає WAL-журнал Postgres і публікує кожну зміну в Kafka, звідки її споживають індексатор Elasticsearch, інвалідатор кешу, аналітика. API взагалі не знає про похідні сховища. Ще один важливий патерн — outbox: замість «записати в Postgres, потім опублікувати в чергу» (де між двома кроками може статись збій), зміну і подію записують в одну транзакцію в таблицю outbox, а окремий процес надійно переносить події з неї в чергу. Обидва патерни вирішують головну проблему polyglot persistence — розсинхронізацію.

Спробуй сам
  1. Підключіть Redis до API нотаток із розділів 04–05: кешуйте GET /notes/:id на 60 секунд, інвалідуйте при PATCH/DELETE. Зробіть 100 запитів через curl у циклі до і після кешу, порівняйте час через time.
  2. Додайте rate limiter: 10 запитів на хвилину на POST /notes. Перевищіть ліміт і подивіться на 429 і заголовки X-RateLimit-*.
  3. Запустіть два екземпляри API на портах 3000 і 3001 (один код, різний PORT). Переконайтесь, що ліміт спільний — бо лічильник у Redis, а не в процесі.
  4. Реалізуйте «останні 10 переглянутих нотаток» користувача через Redis List (LPUSH + LTRIM 0 9) і таблицю лідерів «найпопулярніші нотатки» через Sorted Set (ZINCRBY при кожному перегляді, ZREVRANGE 0 4 WITHSCORES).
  5. Відкрийте redis-cli (docker exec -it redis redis-cli), виконайте INFO memory і CONFIG GET maxmemory-policy. Встановіть CONFIG SET maxmemory 100mb та allkeys-lru.

7. Типові помилки

  1. «Mongo без схеми» = хаос. Гнучкість схеми — не привід її не мати. Через рік у колекції users буде phone, phoneNumber, phone_number і contacts.phone, а код обробляє всі чотири. Ліки: схема в коді (Mongoose або zod) плюс schema validation на рівні бази; свідомі міграції даних при зміні форми.
  2. Mongo як реляційна база. Десять колекцій, усе через referencing, на кожній сторінці по п'ять $lookup. Це найгірше з обох світів: немає ні швидкості документів, ні потужності SQL JOIN. Якщо дані реляційні за природою — беріть Postgres.
  3. Необмежене embedding. Масив коментарів усередині поста росте до 16 МБ (ліміт документа) і все ламається. Правило: вбудовуйте лише те, що обмежене (адреси, останні 5 коментарів), необмежене — в окрему колекцію.
  4. Redis без maxmemory і без TTL. Розібрано вище: пам'ять закінчується, сервер падає посеред ночі.
  5. Redis як джерело правди. Замовлення тільки в Redis → перезапуск → замовлень немає. Redis — прискорювач для даних, які можна відновити.
  6. Дублювання без плану оновлення. Скопіювали ім'я автора в кожен пост (це нормальна денормалізація), але не написали код, який оновлює копії при зміні імені. Через місяць у половини постів старе ім'я. Кожен дублікат = задокументований механізм синхронізації (транзакція, подія в черзі, фонова задача).
  7. Кеш без інвалідації або з інвалідацією «колись». Користувач змінив аватар, а бачить старий 10 хвилин і пише в підтримку. Кожна мутація має знати, які ключі кешу вона псує.
  8. Вибір бази за модою. «Візьмемо Cassandra, бо в Netflix» — для стартапу з 1000 користувачів. Кожна додаткова база — це +1 система для моніторингу, бекапів і онбордингу. Postgres + Redis, поки не доведено зворотне.
Чому це важливо

Усі помилки вище об'єднує одне: NoSQL перекладає на розробника відповідальність, яку реляційна база брала на себе — за цілісність, за схему, за узгодженість дублікатів. Це не погано: ви отримуєте свободу і швидкість. Але свобода без дисципліни дає базу, яку через рік ніхто не розуміє. Коли обираєте NoSQL, одразу пишіть: де схема, хто оновлює копії, коли інвалідується кеш.

Перевір себе

Питання
1. Що означає NoSQL і які дві головні причини його появи?

«Not Only SQL» — бази, що не є класичними реляційними. Причини: горизонтальне масштабування на багато серверів (де JOIN і глобальні транзакції не працюють) і гнучкість схеми для даних із різною структурою. Додатково — спеціалізація під швидкість (кеш) і пошук.

2. Назвіть п'ять типів NoSQL-баз і по одній задачі для кожного.

Документні (MongoDB — каталог товарів із різними атрибутами), ключ-значення (Redis — кеш і сесії), колонкові (Cassandra — логи й метрики з величезним потоком записів), графові (Neo4j — рекомендації «друзі друзів»), пошукові (Elasticsearch — повнотекстовий пошук з одруками).

3. Коли в MongoDB вбудовувати (embed), а коли посилатись (reference)?

Вбудовувати — коли дані обмежені за кількістю, читаються завжди разом із батьківським документом і оновлюються разом із ним (адреса, налаштування). Посилатись — коли даних необмежено багато, вони оновлюються незалежно або потрібні окремо (коментарі, автори). Ліміт документа — 16 МБ.

4. Як реалізувати кеш-aside і чому обов'язкові TTL та інвалідація?

Спершу читаємо з Redis; при промаху — з бази, і записуємо в Redis із TTL. TTL гарантує, що застарілі дані зникнуть самі й пам'ять не переповниться. Інвалідація (DEL при оновленні) потрібна, щоб користувачі не бачили старі дані впродовж усього TTL.

5. Чому rate limiter тримають у Redis, а не в змінній у Node.js?

Бо з кількома екземплярами сервера кожен мав би окремий лічильник, і ліміт множився б на кількість екземплярів. Redis — спільна пам'ять для всіх; INCR атомарний, тому гонок немає; TTL сам чистить старі вікна.

6. Що каже CAP-теорема і який практичний висновок?

Під час розриву мережі розподілена система може гарантувати або узгодженість (відмовити в операції), або доступність (відповісти, ризикуючи розбіжністю). Практично: для грошей і унікальних обмежень — C (Postgres), для лайків, переглядів, кошика — прийнятна eventual consistency (A).

7. Що таке polyglot persistence і яке головне правило при його застосуванні?

Використання кількох баз, кожної для своєї задачі (Postgres — правда і транзакції, Redis — швидкість, Elasticsearch — пошук). Головне правило: одне джерело правди; решта сховищ — похідні, які можна перебудувати з нього; синхронізація через чергу подій.

8. Чому «Mongo без схеми» — це помилка, якщо Mongo і є безсхемною?

База не вимагає схеми, але застосунок її завжди має — просто неявно. Без явної схеми (Mongoose, zod, schema validation) поля розповзаються у варіанти назв і типів, а код обростає перевірками «якщо поле є і воно рядок...». Гнучкість схеми — про еволюцію, а не про відсутність.

Що запам'ятати

  • NoSQL = «Not Only SQL»: не заміна реляційних баз, а інші інструменти для інших форм даних і масштабу.
  • П'ять сімейств: документні (MongoDB), ключ-значення (Redis, DynamoDB), колонкові (Cassandra), графові (Neo4j), пошукові (Elasticsearch). Обирають за патерном доступу.
  • MongoDB: документ ≈ JSON (BSON), колекція ≈ таблиця; проєктуйте під те, як читаєте: embedding для «мало і разом», referencing для «багато і окремо».
  • Індекси в Mongo так само обов'язкові, як у Postgres; explain() показує COLLSCAN проти IXSCAN.
  • Redis — структури даних у RAM: string, hash, list, set, sorted set, stream; TTL робить його ідеальним кешем.
  • Cache-aside: читати з Redis → при промаху з бази → записати з TTL; кожна мутація інвалідує свої ключі.
  • Rate limiter, сесії, лічильники — у Redis, бо це спільна атомарна пам'ять для всіх екземплярів сервера.
  • Обов'язково: maxmemory + allkeys-lru для кешу, ніякого KEYS *, Redis — не джерело правди.
  • CAP: під час збою — узгодженість або доступність; гроші — C, лайки — A (eventual consistency).
  • Polyglot persistence: одне джерело правди (Postgres), похідні сховища синхронізуються через чергу. Починайте з Postgres + Redis.
  • Гнучка схема ≠ відсутність схеми; кожен дублікат даних — задокументований механізм оновлення.
