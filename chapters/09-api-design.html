Пояснення для п'ятирічного

Уяви ресторан. Ти не заходиш на кухню і не береш каструлі сам — ти дивишся в меню і кажеш офіціанту: «Борщ, номер 12». Меню — це домовленість: що можна замовити, як це називається, що ти отримаєш. API — це меню для програм. REST — класичне меню зі сторінками «Супи», «Салати», де кожна страва має номер. GraphQL — конструктор: «мені борщ, але без сметани, і з нього тільки буряк і м'ясо». gRPC — переговорний пристрій між кухнею і складом, яким люди не користуються, зате він дуже швидкий. WebSocket — коли офіціант не йде, а стоїть біля столика і одразу приносить усе, щойно щось готове. А webhook — це коли ресторан сам дзвонить тобі: «ваше замовлення доставлено».

1. API як контракт

API (Application Programming Interface) — це домовленість між тим, хто надає функціональність (сервер), і тим, хто нею користується (клієнт: браузер, мобільний застосунок, інший сервіс). Хороший API — як хороше меню: зрозумілий без пояснень, передбачуваний (якщо суп №12 — борщ, то й завтра він борщ), повний (є все, що треба) і не надлишковий.

Ключове слово — контракт. Після того, як API опублікований і ним хтось користується, змінювати його стає важко: кожна зміна — ризик зламати чужий код. Тому проєктування API — це радше про сумісність у часі, ніж про красу URL. Усе, що далі, — способи зробити контракт чітким, а його зміни — безпечними.

2. REST глибше: ресурси, методи, ідемпотентність, статуси

У розділі 04 ви побачили REST на прикладі. Тепер — правила, за якими його проєктують.

Ресурси та іменування URL

REST мислить ресурсами (resources) — іменниками, а не діями. Дія виражається HTTP-методом.

Ідемпотентність методів

Ідемпотентність (idempotency) — властивість операції, коли повторне виконання дає той самий результат, що й одноразове. Це критично для мереж, де запит може «загубитися» і клієнт не знає, чи він дійшов: ідемпотентний запит можна безпечно повторити.

Статуси відповіді, які треба знати напам'ять

  • 200 OK — успіх з тілом; 201 Created — створено (додайте заголовок Location: /notes/8); 202 Accepted — прийнято в обробку (асинхронно); 204 No Content — успіх без тіла (DELETE).
  • 304 Not Modified — кеш клієнта актуальний (з ETag/If-None-Match).
  • 400 Bad Request — невалідний вхід; 401 — не автентифікований; 403 — заборонено; 404 — нема; 405 — метод не дозволений; 409 Conflict — конфлікт стану (email зайнятий, версія застаріла); 422 Unprocessable Content — синтаксис ок, семантика ні (часто для валідації); 429 Too Many Requests — rate limit (з Retry-After).
  • 500 — наша помилка; 502/503/504 — проблеми з апстрімом / перевантаження / таймаут.

Правило: не повертайте 200 з {"success": false}. Статус — це перше, що бачать клієнти, проксі, моніторинг і кеші.

3. Пагінація, фільтрація, помилки, версіонування

Пагінація: offset проти cursor

Колекція на мільйон записів не віддається одним запитом. Два підходи:

// Відповідь із cursor-пагінацією — стандартний конверт
{
  "data": [ { "id": 4, "title": "…" }, { "id": 5, "title": "…" }, { "id": 6, "title": "…" } ],
  "pageInfo": { "hasNextPage": true, "endCursor": "eyJpZCI6Nn0" }
}

Фільтрація, сортування, вибір полів

GET /notes?status=done&tag=work            # фільтр за полями
GET /notes?createdAt[gte]=2025-01-01         # діапазони — у дужках або окремими параметрами
GET /notes?sort=-createdAt,title             # «-» — за спаданням; кілька ключів через кому
GET /notes?fields=id,title                   # sparse fieldsets — лише потрібні поля
GET /notes?q=borsch                          # повнотекстовий пошук

Документуйте, які поля можна фільтрувати і сортувати, і відхиляйте невідомі — інакше хтось відсортує за неіндексованим полем і покладе базу.

Помилки в єдиному форматі: RFC 9457

Кожен endpoint повертає помилки по-різному — біль для клієнта. Стандарт RFC 9457 «Problem Details for HTTP APIs» (оновлений RFC 7807) задає формат із Content-Type: application/problem+json:

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation-error",   // URI, що ідентифікує тип помилки
  "title": "Validation failed",                                    // коротко, однаково для типу
  "status": 422,
  "detail": "Поле 'title' має бути від 1 до 200 символів",        // людське пояснення конкретного випадку
  "instance": "/notes",                                            // де сталося
  "errors": [ { "field": "title", "code": "too_long", "max": 200 } ] // розширення — свої поля дозволені
}
// Express: один обробник помилок замість сотні res.status(...).json(...)
class HttpProblem extends Error {
  constructor(status, title, detail, extra = {}) { super(detail); Object.assign(this, { status, title, extra }); }
}
app.use((err, req, res, _next) => {
  const status = err.status ?? 500;
  if (status >= 500) console.error(err);                  // 5xx логуємо, 4xx — ні
  res.status(status).type("application/problem+json").json({
    type: `https://api.example.com/problems/${err.type ?? "internal"}`,
    title: err.title ?? "Internal Server Error",
    status,
    detail: status >= 500 ? "Щось пішло не так" : err.message, // не витікаємо stack trace
    instance: req.originalUrl,
    ...err.extra,
  });
});

Версіонування

  • В URL: /v1/notes. Видно, просто, кешується, найпоширеніше (Stripe, GitHub у минулому, Twitter).
  • У заголовку: Accept: application/vnd.example.v2+json або власний X-API-Version: 2024-06-01. «Чистіші» URL, але невидимо в браузері і складніше тестувати. Stripe використовує дати як версії у заголовку, а мажорна — в URL.
  • Найкраща версія — та, якої не було: додавайте поля, не видаляйте; нові обов'язкові параметри — з дефолтами. Нова мажорна версія — лише коли зламати сумісність неминуче.

HATEOAS коротко

Ідея з «канонічного» REST: відповідь містить посилання на можливі дії ("links": {"publish": "/notes/7/publish"}), як сторінка містить гіперпосилання. На практиці мало хто реалізує повністю, але Location після 201 і next у пагінації — це саме воно.

4. OpenAPI / Swagger: контракт як код

OpenAPI — стандарт опису REST API у YAML/JSON (раніше називався Swagger; Swagger тепер — набір інструментів навколо OpenAPI). З одного файлу отримуємо: інтерактивну документацію (Swagger UI, Redoc), клієнти для будь-якої мови, валідацію запитів, моки, тести на відповідність.

# openapi.yaml — фрагмент для API нотаток
openapi: 3.1.0
info:
  title: Notes API
  version: 1.0.0
  description: Прості нотатки з розділу 04
servers:
  - url: http://localhost:3000/api
paths:
  /notes:
    get:
      operationId: listNotes            # з цього імені генератор зробить client.listNotes()
      summary: Список нотаток
      parameters:
        - name: status
          in: query
          schema: { type: string, enum: [active, done] }
        - name: after
          in: query
          description: Курсор з попередньої відповіді
          schema: { type: string }
        - name: limit
          in: query
          schema: { type: integer, minimum: 1, maximum: 100, default: 20 }
      responses:
        "200":
          description: Сторінка нотаток
          content:
            application/json:
              schema:
                type: object
                required: [data, pageInfo]
                properties:
                  data: { type: array, items: { $ref: "#/components/schemas/Note" } }
                  pageInfo: { $ref: "#/components/schemas/PageInfo" }
    post:
      operationId: createNote
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: "#/components/schemas/NewNote" }
      responses:
        "201":
          description: Створено
          headers:
            Location: { schema: { type: string }, description: URL нової нотатки }
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Note" }
        "422":
          $ref: "#/components/responses/Problem"
  /notes/{id}:
    parameters:
      - name: id
        in: path
        required: true
        schema: { type: integer }
    get:
      operationId: getNote
      responses:
        "200": { description: Нотатка, content: { application/json: { schema: { $ref: "#/components/schemas/Note" } } } }
        "404": { $ref: "#/components/responses/Problem" }
    patch:
      operationId: updateNote
      requestBody:
        content:
          application/json:
            schema:
              type: object
              properties: { title: { type: string }, done: { type: boolean } }
      responses:
        "200": { description: Оновлено, content: { application/json: { schema: { $ref: "#/components/schemas/Note" } } } }
    delete:
      operationId: deleteNote
      responses:
        "204": { description: Видалено }
components:
  schemas:
    Note:
      type: object
      required: [id, title, done, createdAt]
      properties:
        id: { type: integer, examples: [7] }
        title: { type: string, maxLength: 200 }
        done: { type: boolean }
        createdAt: { type: string, format: date-time }
    NewNote:
      type: object
      required: [title]
      properties:
        title: { type: string, minLength: 1, maxLength: 200 }
    PageInfo:
      type: object
      properties:
        hasNextPage: { type: boolean }
        endCursor: { type: [string, "null"] }
    Problem:
      type: object
      properties:
        type: { type: string }
        title: { type: string }
        status: { type: integer }
        detail: { type: string }
  responses:
    Problem:
      description: Помилка у форматі RFC 9457
      content:
        application/problem+json:
          schema: { $ref: "#/components/schemas/Problem" }

Два підходи: design-first (спочатку YAML, потім код — спека як предмет обговорення з фронтендом) і code-first (декоратори/схеми Zod у коді генерують спеку — NestJS, Fastify, Hono роблять це з коробки). Обидва працюють; головне, щоб спека і код ніколи не розходилися — для цього є тести на відповідність (contract tests).

Чому OpenAPI варте зусиль

Без спеки фронтенд і бекенд домовляються «на словах» і кожен неправильно запам'ятовує. Зі спекою: фронтенд починає роботу з моків до готовності бекенду; типи генеруються, а не дублюються вручну; зміна поля у спеці підсвічує всі місця, що зламаються; новий розробник читає Swagger UI замість того, щоб смикати колег. Це та сама ідея, що й TypeScript, але на рівні мережі.

5. GraphQL: схема, resolvers, N+1 і DataLoader

GraphQL — мова запитів і рантайм від Facebook (2015). Замість багатьох endpoint'ів — один (POST /graphql), а клієнт описує, яку саме форму даних хоче. Сервер публікує схему (schema) — строго типізований опис усього, що можна запитати.

# schema.graphql
type Note {
  id: ID!
  title: String!
  done: Boolean!
  author: User!          # зв'язок — і клієнт сам вирішує, чи тягнути його
  tags: [Tag!]!
}
type User { id: ID!, name: String!, notes: [Note!]! }
type Tag { id: ID!, name: String! }

type Query {
  notes(status: NoteStatus, first: Int = 20, after: String): NoteConnection!
  note(id: ID!): Note
}
type Mutation {
  createNote(input: NewNoteInput!): Note!
  toggleNote(id: ID!): Note!
}
type Subscription {
  noteAdded: Note!        # push через WebSocket
}
enum NoteStatus { ACTIVE, DONE }
input NewNoteInput { title: String! }
type NoteConnection { edges: [NoteEdge!]!, pageInfo: PageInfo! }
type NoteEdge { node: Note!, cursor: String! }
type PageInfo { hasNextPage: Boolean!, endCursor: String }
# Запит клієнта: рівно ті поля, які треба для екрана — не більше, не менше
query NotesScreen {
  notes(status: ACTIVE, first: 10) {
    edges {
      node {
        id
        title
        author { name }        # вкладені дані одним запитом — без другого round-trip
      }
    }
    pageInfo { hasNextPage endCursor }
  }
}

# Мутація
mutation { createNote(input: { title: "Купити хліб" }) { id title } }

Resolver — функція, яка знає, як дістати одне поле. GraphQL-сервер обходить запит як дерево і викликає resolver для кожного поля. І тут ховається головна проблема:

// resolvers.js — з graphql-yoga або Apollo Server
import DataLoader from "dataloader";

// Створюємо loader НА КОЖЕН ЗАПИТ (у context), щоб кеш не тік між користувачами
export function createLoaders(db) {
  return {
    userById: new DataLoader(async (ids) => {
      const rows = await db.select().from(users).where(inArray(users.id, ids));
      const byId = new Map(rows.map(u => [u.id, u]));
      return ids.map(id => byId.get(id) ?? null);   // порядок і довжина мають збігатися з ids!
    }),
  };
}

export const resolvers = {
  Query: {
    notes: (_, { status, first, after }, { db }) => paginateNotes(db, { status, first, after }),
  },
  Note: {
    author: (note, _, { loaders }) => loaders.userById.load(note.authorId), // батчиться
  },
  Mutation: {
    createNote: async (_, { input }, { db, user, pubsub }) => {
      if (!user) throw new GraphQLError("Unauthenticated", { extensions: { code: "UNAUTHENTICATED" } });
      const [note] = await db.insert(notes).values({ title: input.title, authorId: user.id }).returning();
      pubsub.publish("NOTE_ADDED", { noteAdded: note });
      return note;
    },
  },
  Subscription: {
    noteAdded: { subscribe: (_, __, { pubsub }) => pubsub.subscribe("NOTE_ADDED") },
  },
};

Коли GraphQL доречний: багато різних клієнтів із різними потребами в даних (веб, мобільний, партнери); глибоко зв'язані дані (соцграф); фронтенд-команди хочуть самостійності від бекенду. Коли ні: простий CRUD з одним клієнтом (REST простіший); потрібне HTTP-кешування (GraphQL — усе через POST); файли (незручно); команда без досвіду — складність схем, авторизації на рівні полів, обмеження глибини запитів і вартості (query complexity), N+1 — усе це треба вирішувати, тоді як у REST воно вирішується «саме собою».

6. gRPC і protobuf; tRPC для TypeScript

gRPC — фреймворк віддалених викликів від Google. Ви описуєте сервіс у файлі .proto (Protocol Buffers), генератор створює клієнт і сервер для десятка мов, а дані передаються у компактному бінарному форматі поверх HTTP/2 (мультиплексування, стріми в обидва боки).

// notes.proto
syntax = "proto3";
package notes.v1;

service NotesService {
  rpc GetNote (GetNoteRequest) returns (Note);                   // унарний виклик
  rpc ListNotes (ListNotesRequest) returns (stream Note);        // серверний стрім: нотатки по одній
  rpc WatchNotes (stream WatchRequest) returns (stream NoteEvent); // двонаправлений стрім
}

message Note {
  int64  id         = 1;   // номери полів — це і є контракт; імена можна міняти, номери — ні
  string title      = 2;
  bool   done       = 3;
  int64  author_id  = 4;
  reserved 5;              // видалене поле: номер не перевикористовувати
}
message GetNoteRequest  { int64 id = 1; }
message ListNotesRequest { optional bool done = 1; int32 page_size = 2; }
message WatchRequest { repeated int64 ids = 1; }
message NoteEvent { Note note = 1; string type = 2; }
// server.js — @grpc/grpc-js + @grpc/proto-loader (Node)
import grpc from "@grpc/grpc-js";
import protoLoader from "@grpc/proto-loader";

const pkg = grpc.loadPackageDefinition(protoLoader.loadSync("notes.proto")).notes.v1;
const server = new grpc.Server();
server.addService(pkg.NotesService.service, {
  GetNote: (call, cb) => cb(null, { id: call.request.id, title: "Привіт", done: false, author_id: 1 }),
  ListNotes: (call) => { for (const n of allNotes) call.write(n); call.end(); }, // стрім
});
server.bindAsync("0.0.0.0:50051", grpc.ServerCredentials.createInsecure(), () => console.log("gRPC :50051"));

Де використовують: між мікросервісами всередині інфраструктури (Kubernetes, Envoy, etcd — усі говорять gRPC), де важливі швидкість, строгі типи між мовами (Go ↔ Java ↔ Node) і стрімінг. Де ні: з браузера напряму (потрібен gRPC-Web проксі), для публічних API (людям звичніший JSON), для простих проєктів.

tRPC: типи без схеми для TS-монорепо

Якщо і клієнт, і сервер — TypeScript в одному репозиторії, tRPC дає end-to-end типізацію без генерації коду: клієнт імпортує тип роутера, і автодоповнення знає всі процедури та їхні аргументи. Змінили тип на сервері — фронтенд не компілюється. Немає ні YAML, ні .proto, ні кодогенерації.

// server/router.ts
import { initTRPC } from "@trpc/server";
import { z } from "zod";
const t = initTRPC.create();
export const appRouter = t.router({
  notes: t.router({
    list: t.procedure.input(z.object({ done: z.boolean().optional() })).query(({ input }) => db.listNotes(input)),
    create: t.procedure.input(z.object({ title: z.string().min(1).max(200) })).mutation(({ input }) => db.createNote(input)),
  }),
});
export type AppRouter = typeof appRouter;   // лише ТИП експортується на клієнт

// client.ts
import { createTRPCClient, httpBatchLink } from "@trpc/client";
import type { AppRouter } from "../server/router";
const trpc = createTRPCClient<AppRouter>({ links: [httpBatchLink({ url: "/trpc" })] });
const notes = await trpc.notes.list.query({ done: false });  // повністю типізовано, без генерації

Ціна: працює тільки для TypeScript-клієнтів, яких ви контролюєте. Для публічного API або мобільного застосунку на Swift усе одно потрібен REST/OpenAPI.

7. Реальний час: polling, long polling, SSE, WebSocket

HTTP — «клієнт питає, сервер відповідає». А якщо сервер хоче повідомити щось сам — нове повідомлення в чаті, зміна ціни, прогрес задачі? Чотири підходи, від найпростішого до найпотужнішого:

SSE (Server-Sent Events) — недооцінений

Якщо дані течуть лише від сервера до клієнта (сповіщення, стрічка, прогрес, стрімінг відповіді LLM), SSE — найкращий вибір: це звичайний HTTP, працює через будь-які проксі, браузер сам перепідключається і надсилає Last-Event-ID.

// server: Express
app.get("/events", (req, res) => {
  res.set({ "Content-Type": "text/event-stream", "Cache-Control": "no-cache", Connection: "keep-alive" });
  res.flushHeaders();
  const send = (event, data, id) => res.write(`id: ${id}\nevent: ${event}\ndata: ${JSON.stringify(data)}\n\n`);
  const unsubscribe = bus.subscribe("note", (note) => send("note", note, note.id));
  const ping = setInterval(() => res.write(": ping\n\n"), 25_000); // щоб проксі не закрив з'єднання
  req.on("close", () => { clearInterval(ping); unsubscribe(); });
});

// browser
const es = new EventSource("/events");
es.addEventListener("note", (e) => console.log("нова нотатка", JSON.parse(e.data)));

WebSocket: чат на бібліотеці ws

// chat-server.js — npm i ws
import { WebSocketServer } from "ws";
import http from "node:http";

const server = http.createServer();                       // можна ділити порт з Express
const wss = new WebSocketServer({ server, path: "/chat" });
const rooms = new Map();                                  // room → Set<ws>

wss.on("connection", (ws, req) => {
  // автентифікація: cookie сесії з req.headers.cookie або token у query — перевіряємо ТУТ, при handshake
  const user = authenticate(req);
  if (!user) return ws.close(4401, "unauthorized");
  ws.isAlive = true;
  ws.on("pong", () => { ws.isAlive = true; });

  ws.on("message", (raw) => {
    let msg;
    try { msg = JSON.parse(raw); } catch { return ws.send(JSON.stringify({ type: "error", detail: "bad json" })); }
    if (msg.type === "join") {
      ws.room = msg.room;
      (rooms.get(msg.room) ?? rooms.set(msg.room, new Set()).get(msg.room)).add(ws);
    } else if (msg.type === "chat" && ws.room && typeof msg.text === "string" && msg.text.length <= 1000) {
      const out = JSON.stringify({ type: "chat", from: user.name, text: msg.text, at: Date.now() });
      for (const peer of rooms.get(ws.room)) if (peer.readyState === peer.OPEN) peer.send(out);
    }
  });
  ws.on("close", () => rooms.get(ws.room)?.delete(ws));
});

// heartbeat: мертві з'єднання (мобільний пішов у тунель) не закриваються самі
setInterval(() => {
  for (const ws of wss.clients) { if (!ws.isAlive) return ws.terminate(); ws.isAlive = false; ws.ping(); }
}, 30_000);

server.listen(3000);

// browser
const ws = new WebSocket("wss://example.com/chat");
ws.onopen = () => ws.send(JSON.stringify({ type: "join", room: "general" }));
ws.onmessage = (e) => render(JSON.parse(e.data));
ws.onclose = () => setTimeout(reconnect, 1000);           // reconnect — ваша відповідальність (на відміну від SSE)

Для продакшену з кількома серверами: з'єднання з одного сервера не бачать клієнтів іншого — потрібен брокер (Redis Pub/Sub) між інстансами. Бібліотека Socket.IO додає кімнати, reconnect, fallback і адаптери для цього з коробки.

Підводні камені реального часу
  • Автентифікуйте при handshake і перевіряйте права на кожне повідомлення — WebSocket не має «middleware на маршрут».
  • Валідуйте розмір і формат кожного повідомлення; обмежуйте частоту (rate limit на з'єднання).
  • Cross-Site WebSocket Hijacking: перевіряйте заголовок Origin при handshake — cookie до WS надсилаються, а CORS не діє.
  • Балансувальники і проксі мають таймаути на «тихі» з'єднання — робіть ping/heartbeat.
  • Serverless-платформи (Lambda, Vercel Functions) погано тримають довгі з'єднання — беріть керований сервіс (Pusher, Ably) або окремий сервер.

8. Webhooks і їх безпека

Webhook — «зворотний API»: не ви питаєте Stripe «чи пройшов платіж?», а Stripe робить POST на ваш URL, коли подія сталася. Так працюють платежі, GitHub-події, повідомлення в месенджерах.

// Прийом webhook від Stripe: ВАЖЛИВО — сирий body, а не розпарсений JSON
import express from "express";
import Stripe from "stripe";
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);

app.post("/webhooks/stripe", express.raw({ type: "application/json" }), async (req, res) => {
  let event;
  try {
    // перевіряє HMAC-SHA256 підпис із секретом endpoint'а і timestamp (захист від replay)
    event = stripe.webhooks.constructEvent(req.body, req.headers["stripe-signature"], process.env.STRIPE_WEBHOOK_SECRET);
  } catch (err) {
    return res.status(400).send(`Webhook signature failed: ${err.message}`);
  }

  // Ідемпотентність: той самий event.id може прийти двічі
  const seen = await db.insert(webhookEvents).values({ id: event.id }).onConflictDoNothing().returning();
  if (seen.length === 0) return res.status(200).end();          // уже обробляли

  await queue.add("stripe-event", event);                        // важку роботу — у чергу, не тут
  res.status(200).end();                                         // відповісти швидко
});

// Власний webhook (ви — провайдер): підписуйте так само
import crypto from "node:crypto";
function sign(body, secret) {
  const t = Math.floor(Date.now() / 1000);
  const sig = crypto.createHmac("sha256", secret).update(`${t}.${body}`).digest("hex");
  return `t=${t},v1=${sig}`;
}
Чому підпис, а не «секретний URL»

URL потрапляє в логи проксі, історію браузера, репозиторії. HMAC-підпис із секретом, який ніколи не передається мережею, доводить, що тіло надіслав саме провайдер і що воно не змінене. Timestamp у підписі не дає зловмиснику «переграти» перехоплений запит через годину. Без цього будь-хто, хто дізнався URL, може надіслати вам payment.succeeded і отримати товар безкоштовно.

Backward compatibility і deprecation

Безпечні зміни (не ламають клієнтів): додати поле у відповідь; додати необов'язковий параметр; додати новий endpoint; додати значення в enum (обережно — старі клієнти можуть падати на невідомому). Небезпечні: перейменувати/видалити поле; змінити тип; зробити параметр обов'язковим; змінити семантику статусу; змінити формат дати. Правило Постела: «будь консервативним у тому, що надсилаєш, і ліберальним у тому, що приймаєш» — клієнти мають ігнорувати невідомі поля.

Коли ламати все ж треба — deprecation як процес: оголосити (заголовки Deprecation: true, Sunset: Sat, 01 Mar 2026 00:00:00 GMT, Link: <…/migration>; rel="deprecation"), логувати, хто ще користується старим, попередити їх, дати 6–12 місяців, потім вимкнути. Stripe тримає старі версії роками — саме тому їм довіряють.

Rate limits

Повідомляйте ліміти в заголовках, щоб клієнти могли адаптуватися: RateLimit-Limit: 100, RateLimit-Remaining: 37, RateLimit-Reset: 42 (стандарт IETF draft), при перевищенні — 429 + Retry-After. Клієнти мають робити backoff з jitter, а не бити в стіну.

Ідемпотентні ключі для платежів

POST /payments не ідемпотентний: мережа обірвалась після того, як сервер списав гроші, але до того, як клієнт отримав відповідь. Клієнт повторює — і списує вдруге. Рішення, стандартизоване Stripe: клієнт генерує унікальний Idempotency-Key для операції і надсилає його з кожним повтором.

// middleware ідемпотентності (Redis)
export const idempotent = (redis) => async (req, res, next) => {
  const key = req.get("Idempotency-Key");
  if (!key) return next();                                   // або 400, якщо ключ обов'язковий
  const storeKey = `idem:${req.user.id}:${key}`;             // ключ належить користувачу — чужий не підмінить
  const cached = await redis.get(storeKey);
  if (cached) { const { status, body } = JSON.parse(cached); return res.status(status).json(body); }

  const locked = await redis.set(`${storeKey}:lock`, "1", "NX", "EX", 30); // паралельний повтор → 409
  if (!locked) return res.status(409).json({ title: "Request in progress" });

  const json = res.json.bind(res);
  res.json = async (body) => {                               // перехоплюємо відповідь, щоб зберегти
    await redis.set(storeKey, JSON.stringify({ status: res.statusCode, body }), "EX", 86_400);
    await redis.del(`${storeKey}:lock`);
    return json(body);
  };
  next();
};
app.post("/payments", requireAuth, idempotent(redis), createPayment);
Для просунутих

Вивчіть, як Stripe документує API: кожен endpoint має приклади для всіх мов, кожна помилка — код і пояснення, версії — дати, зміни — changelog із міграцією, а ідемпотентність і webhooks — окремі розділи. Це еталон не тому, що красиво, а тому, що кожне рішення там продиктоване болем реальних інтеграцій. Друге джерело — Google API Design Guide: стандарт для всіх Google Cloud API, який пояснює resource-oriented design, стандартні методи (List/Get/Create/Update/Delete), довгі операції (Operation для async) і поля-маски для часткових оновлень. Читаючи обидва, ви побачите, що REST у великих компаніях — це набір дуже конкретних конвенцій, а не «щось із HTTP-методами».

10. Практика: API нотаток в OpenAPI і генерація клієнта

Спробуй сам
  1. Візьми openapi.yaml з §4, збережи поруч із API нотаток із розділу 04. Запусти npx @redocly/cli lint openapi.yaml і виправ зауваження.
  2. Підніми Swagger UI (docker run з §4) і виконай запити прямо з браузера кнопкою «Try it out».
  3. Згенеруй типи: npx openapi-typescript openapi.yaml -o api-types.d.ts. Відкрий файл — там інтерфейси для кожного шляху й відповіді.
  4. Встанови openapi-fetch і напиши клієнт: 
    import createClient from "openapi-fetch";
import type { paths } from "./api-types";

const client = createClient<paths>({ baseUrl: "http://localhost:3000/api" });
const { data, error } = await client.GET("/notes", { params: { query: { status: "active", limit: 10 } } });
//     ^ data типізований як { data: Note[], pageInfo }, а status: "foo" — помилка компіляції
const created = await client.POST("/notes", { body: { title: "Зі спеки" } });
  5. Додай до бекенду валідацію запитів за спекою (express-openapi-validator) — надішли { "title": "" } і отримай 400 автоматично.
  6. Зміни у спеці title на text, перегенеруй типи — і подивись, скільки місць у клієнті перестало компілюватися. Це і є контракт у дії.
Спробуй сам: реальний час і webhooks
  1. Додай до API нотаток endpoint GET /api/notes/events на SSE, який надсилає подію при кожному створенні нотатки. Відкрий дві вкладки: створи нотатку в одній — побачиш її в іншій.
  2. Перепиши те саме на WebSocket з ws. Порівняй кількість коду й поведінку при перезапуску сервера (SSE перепідключиться сам).
  3. Зроби «провайдера webhook»: при створенні нотатки твій сервер робить POST на URL із webhook.site з підписом X-Signature. Потім напиши «приймача» на іншому порту, який перевіряє підпис і відхиляє підроблений запит через curl.
  4. Додай Idempotency-Key до POST /api/notes. Надішли той самий запит двічі — переконайся, що нотатка одна.
Типові помилки в дизайні API
  • 200 на все, а помилка — у тілі. Моніторинг сліпий, кеші кешують помилки.
  • Різні форми помилок у різних endpoint'ах. Один формат (RFC 9457) — і клієнт пише один обробник.
  • Offset-пагінація на стрічках, що постійно змінюються — дублікати і пропуски.
  • Без лімітів: GET /notes повертає всі 2 мільйони. Завжди limit з максимумом.
  • Витік внутрішніх деталей: stack trace, SQL, назви таблиць у відповідях.
  • Ламання контракту без версії/deprecation — мобільні клієнти оновлюються тижнями.
  • Webhook без перевірки підпису і без ідемпотентності — подвійні замовлення й підроблені платежі.

Перевір себе

Питання
1. Чому PUT ідемпотентний, а POST — ні?

PUT повністю замінює ресурс: два однакові PUT дають той самий стан. POST створює новий ресурс щоразу — два POST = два ресурси. Тому для безпечного повтору POST потрібен Idempotency-Key.

2. Коли cursor-пагінація краща за offset?

На великих або часто змінюваних колекціях: offset змушує БД читати всі пропущені рядки і дає дублікати при вставках; cursor використовує індекс (WHERE id > X) і стабільний. Offset кращий, коли треба «перейти на сторінку N».

3. Що дає RFC 9457?

Єдиний формат помилок (type, title, status, detail, instance) з Content-Type application/problem+json, розширюваний власними полями. Клієнт пише один обробник для всіх помилок.

4. Що таке N+1 у GraphQL і як його лікує DataLoader?

Resolver вкладеного поля викликається для кожного елемента списку, роблячи N окремих запитів до БД плюс один на список. DataLoader збирає всі load(id) за один tick event loop і робить один запит WHERE id IN (...), повертаючи кожному його результат; плюс кешує в межах запиту.

5. Коли обрати SSE замість WebSocket?

Коли дані течуть лише від сервера до клієнта: SSE — звичайний HTTP, працює через проксі і CDN, має вбудований reconnect і Last-Event-ID, не потребує окремої інфраструктури. WebSocket — коли потрібен двонаправлений або бінарний обмін з низькою затримкою.

6. Навіщо перевіряти підпис webhook, якщо URL секретний?

URL витікає через логи і репозиторії; без підпису будь-хто може надіслати підроблену подію. HMAC-підпис із секретом, що не передається мережею, і timestamp у ньому доводять автентичність і захищають від replay.

7. Чим tRPC відрізняється від gRPC?

gRPC — мовно-незалежний RPC на protobuf і HTTP/2 із кодогенерацією, для мікросервісів. tRPC — типізація end-to-end лише для TypeScript через спільні типи в монорепо, без схеми і генерації, для власного фронтенду.

8. Які зміни в API безпечні для старих клієнтів?

Додавання: нове поле у відповіді, необов'язковий параметр, новий endpoint. Небезпечні: видалення/перейменування полів, зміна типів, нові обов'язкові параметри, зміна семантики.

Що запам'ятати

  • API — контракт; його цінність у стабільності. Проєктуйте так, щоб зміни були додаваннями.
  • REST: іменники в URL, дії в методах; GET/PUT/DELETE ідемпотентні, POST — ні; статуси означають те, що означають.
  • Пагінація: offset для «сторінок», cursor для стрічок і великих даних; завжди ліміт із максимумом.
  • Помилки — в одному форматі (RFC 9457, application/problem+json), без витоку внутрішніх деталей.
  • OpenAPI: одна спека → документація, типи, клієнти, валідація, контрактні тести.
  • GraphQL — коли клієнтів багато і дані зв'язані; обов'язково DataLoader, ліміти глибини й складності.
  • gRPC — між сервісами (protobuf, HTTP/2, стріми); tRPC — для TS-монорепо без схеми.
  • Реальний час: polling → long polling → SSE (сервер → клієнт, просто) → WebSocket (обидва боки, складніше масштабувати).
  • Webhooks: HMAC-підпис + timestamp, ідемпотентність за event.id, швидка відповідь, обробка в черзі.
  • Платежі та інші небезпечні POST — з Idempotency-Key і збереженою відповіддю.
Ресурси для поглиблення
  • restfulapi.net — основи REST: ресурси, методи, статуси, HATEOAS простими словами.
  • Microsoft REST API Guidelines — детальні правила іменування, пагінації, помилок, версій від великої компанії.
  • Google API Design Guide — resource-oriented design, стандартні методи, довгі операції; застосовно і до REST, і до gRPC.
  • OpenAPI Specification — першоджерело формату; читайте розділи Paths, Components, Schema.
  • swagger.io docs — інструменти навколо OpenAPI: Editor, UI, Codegen.
  • RFC 9457 Problem Details — стандарт формату помилок; короткий і читабельний RFC.
  • graphql.org/learn — офіційний вступ: схеми, запити, best practices (пагінація, кешування).
  • Apollo docs — сервер і клієнт GraphQL, DataLoader, федерація для мікросервісів.
  • grpc.io docs — концепції gRPC, Node-туторіал, види стрімінгу.
  • protobuf.dev — мова .proto, правила сумісності (номери полів, reserved).
  • MDN: WebSockets API та MDN: Server-sent events — браузерні API з прикладами.
  • trpc.io — end-to-end типізація для TypeScript.
  • Stripe API Reference — еталон документації; окремо: Idempotent requests і Webhooks.
  • roadmap.sh/api-design — карта тем дизайну API для самоперевірки.
