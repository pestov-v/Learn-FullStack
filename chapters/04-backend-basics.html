Уяви ресторан. Ти сидиш у залі — це фронтенд: красиві столики, меню з картинками, офіціант, що усміхається. Але їжу готують на кухні, куди гостям заходити не можна. Кухня — це бекенд (backend). Ти кажеш офіціанту «борщ і компот» — це запит (request). Офіціант несе замовлення на кухню, кухар дістає продукти з холодильника (бази даних), готує і віддає тарілку — це відповідь (response). Ти ніколи не бачиш кухню, але без неї ресторан — просто гарна кімната зі стільцями. У цьому розділі ми підемо на кухню і навчимося готувати самі.

1. Що таке сервер: фізично і логічно

Слово «сервер» (server, від англ. to serve — обслуговувати) має два значення, і новачки постійно їх плутають.

Фізично сервер — це просто комп'ютер. Часто без монітора й клавіатури, у металевій коробці, що стоїть у стійці дата-центру разом із сотнями таких самих. У нього більше оперативної пам'яті й процесорних ядер, ніж у вашого ноутбука, але принцип той самий: процесор, пам'ять, диск, мережева карта. Ваш ноутбук теж може бути сервером — просто зазвичай він вимикається на ніч, а справжній сервер працює 24/7.

Логічно сервер — це програма, яка слухає мережевий порт і відповідає на запити. Коли кажуть «підняти сервер на Node.js», мають на увазі саме програму. На одному фізичному комп'ютері можуть працювати десятки логічних серверів: веб-сервер на порту 3000, база даних на 5432, Redis на 6379.

Тобто бекенд — це все, що відбувається «на кухні»: прийняти запит, перевірити, чи гість має право на цю страву (авторизація), сходити в холодильник (база даних), приготувати (бізнес-логіка), гарно викласти на тарілку (сформувати JSON) і віддати.

Чому це важливо

Розуміння межі між «залом» і «кухнею» — це основа безпеки. Все, що відправлено в браузер, гість може прочитати і змінити: HTML, JavaScript, навіть запити, які браузер надсилає. Тому перевірка прав, розрахунок ціни, робота з паролями і секретами відбуваються тільки на бекенді. Якщо ціна товару рахується у фронтенді й просто відправляється на сервер — будь-який школяр купить айфон за одну гривню.

2. Мови та рантайми для бекенду. Чому Node.js

На кухні можна готувати на газі, на індукції або на дровах — результат схожий, різні лише інструменти. Так само бекенд можна писати майже будь-якою мовою. Ось найпопулярніші варіанти:

Важливо відрізняти мову від рантайму (runtime — середовище виконання). JavaScript — мова. Node.js — рантайм, тобто програма, яка вміє виконувати JavaScript поза браузером. Node.js складається з рушія V8 (того самого, що в Chrome) плюс бібліотеки libuv для роботи з файлами, мережею та таймерами. Є й інші рантайми для JavaScript: Deno і Bun — вони молодші, швидші в деяких сценаріях, але Node.js досі стандарт індустрії.

Чому в цьому посібнику саме Node.js? Три причини:

  1. Одна мова. Ви вже вивчили JavaScript у розділі 02. Не потрібно вивчати другу мову, щоб написати бекенд — ви одразу fullstack.
  2. Екосистема. npm — найбільший реєстр пакетів у світі. Для будь-якої задачі вже є бібліотека.
  3. Модель виконання. Node.js створений для задач, де сервер здебільшого чекає: на базу даних, на інший сервіс, на мережу. Це 90 % типових веб-застосунків. І саме тому треба зрозуміти event loop.

3. Event loop: один офіціант і багато столів

Уявіть кафе, у якому працює один-єдиний офіціант. Здавалося б, катастрофа: якщо він прийме замовлення у столика №1 і стоятиме біля кухні, чекаючи, поки борщ звариться, столики №2–20 залишаться без уваги. Але хороший офіціант робить інакше: він передає замовлення на кухню і одразу йде до наступного столика. Коли кухня дзвонить у дзвіночок «борщ готовий», він забирає тарілку і несе гостю. Один офіціант обслуговує двадцять столиків, тому що він ніколи не стоїть і не чекає.

Це і є event loop (цикл подій) Node.js. JavaScript у Node виконується в одному потоці (single thread) — це «офіціант». Довгі операції — читання файлу, запит до бази даних, HTTP-запит до іншого сервера, таймер — віддаються «на кухню», тобто у libuv та операційну систему. Поки вони виконуються, офіціант вільний. Коли операція завершилась, у чергу подій кладеться повідомлення «готово, ось результат», і офіціант, звільнившись, виконує відповідний callback (зворотний виклик) або продовжує async-функцію після await.

Подивімося, як це виглядає у коді. Три «замовлення» стартують майже одночасно, а завершуються в порядку готовності, а не в порядку старту:

// event-loop-demo.mjs — запускати: node event-loop-demo.mjs
import { setTimeout as sleep } from "node:timers/promises";

console.log("1. Офіціант прийшов на роботу");

// Замовлення для столика 1: "готується" 300 мс
sleep(300).then(() => console.log("4. Столик 1: борщ готовий"));

// Замовлення для столика 2: "готується" 100 мс
sleep(100).then(() => console.log("3. Столик 2: кава готова"));

// Це синхронний код — виконується одразу, поки "кухня" працює
console.log("2. Офіціант пішов до інших столиків");

// Вивід у консолі:
// 1. Офіціант прийшов на роботу
// 2. Офіціант пішов до інших столиків
// 3. Столик 2: кава готова        (через ~100 мс)
// 4. Столик 1: борщ готовий       (через ~300 мс)

Зверніть увагу: рядок «2» виводиться раніше, ніж «3» і «4», хоча в коді записаний після них. Це не помилка — це офіціант, що не чекає.

Підводні камені
  • Блокування event loop. Якщо ви напишете while (Date.now() < start + 5000) {} або синхронно розпарсите файл на гігабайт, усі клієнти вашого сервера будуть чекати. Важкі обчислення (криптографія, обробка зображень, великі цикли) виносьте у worker_threads або окремий сервіс.
  • Синхронні API. У Node є пари функцій: fs.readFile (асинхронна) і fs.readFileSync (синхронна, блокує). Синхронні версії допустимі тільки при старті програми (прочитати конфіг), але ніколи — усередині обробника запиту.
Чому це важливо

Розуміння event loop пояснює, чому Node.js із одним потоком обслуговує десятки тисяч одночасних з'єднань, тоді як класичні сервери на «потік на запит» упираються в пам'ять. І водночас пояснює, чому один невдалий цикл може «покласти» весь сервер. Це найважливіша ментальна модель для Node-розробника — офіційний гайд The Node.js Event Loop варто прочитати повністю.

4. Перший HTTP-сервер на чистому node:http

У Node.js є вбудований модуль node:http. Він низькорівневий, зате показує, що насправді відбувається під капотом будь-якого фреймворку. Створімо сервер, який слухає порт 3000:

// server.mjs — запускати: node server.mjs
import { createServer } from "node:http";

const server = createServer((req, res) => {
  // req — об'єкт запиту (IncomingMessage): метод, URL, заголовки, тіло
  // res — об'єкт відповіді (ServerResponse): ми його заповнюємо і відправляємо
  console.log(`${req.method} ${req.url}`); // напр. "GET /notes?limit=5"

  res.statusCode = 200;                            // статус: усе добре
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("Привіт від кухні!");                    // тіло відповіді + завершити
});

server.listen(3000, () => {
  console.log("Сервер слухає http://localhost:3000");
});

Запустіть і відкрийте у браузері http://localhost:3000. Браузер (гість) надіслав запит GET /, ваш код (кухня) відповів текстом. Вітаю, ви написали бекенд.

Маршрути, методи і параметри

Справжній API розрізняє, що саме просить клієнт. Для цього є три речі:

  • Метод (method) — дієслово: GET (дай), POST (створи), PUT/PATCH (онови повністю / частково), DELETE (видали).
  • Шлях (path) — іменник: /notes (усі нотатки), /notes/42 (нотатка №42). Комбінація «метод + шлях» називається маршрутом (route).
  • Параметри — уточнення. Вони бувають трьох видів:
    • параметри шляху (path params): /notes/42 — ідентифікатор конкретного ресурсу;
    • query-параметри: /notes?limit=5&sort=date — фільтри, сортування, пагінація;
    • тіло запиту (body): дані, які треба зберегти — приходять у POST/PUT/PATCH, зазвичай як JSON.

На чистому node:http усе це доводиться розбирати вручну. Ось мінімальний, але робочий приклад із розбором URL і тіла запиту:

// raw-api.mjs
import { createServer } from "node:http";

const notes = [{ id: 1, title: "Перша нотатка" }]; // "холодильник" у пам'яті

// Допоміжна функція: прочитати тіло запиту цілком і розпарсити JSON
async function readJson(req) {
  let raw = "";
  for await (const chunk of req) raw += chunk; // тіло приходить шматками (chunks)
  return raw ? JSON.parse(raw) : {};
}

function send(res, status, data) {
  res.writeHead(status, { "Content-Type": "application/json; charset=utf-8" });
  res.end(JSON.stringify(data));
}

createServer(async (req, res) => {
  const url = new URL(req.url, "http://localhost"); // зручний розбір шляху і query
  const limit = Number(url.searchParams.get("limit") ?? 100);

  if (req.method === "GET" && url.pathname === "/notes") {
    return send(res, 200, notes.slice(0, limit));
  }

  if (req.method === "POST" && url.pathname === "/notes") {
    const body = await readJson(req);
    const note = { id: notes.length + 1, title: body.title };
    notes.push(note);
    return send(res, 201, note); // 201 Created — ресурс створено
  }

  // Параметр шляху: /notes/42 -> ["", "notes", "42"]
  const [, resource, id] = url.pathname.split("/");
  if (req.method === "GET" && resource === "notes" && id) {
    const note = notes.find((n) => n.id === Number(id));
    return note ? send(res, 200, note) : send(res, 404, { error: "Не знайдено" });
  }

  send(res, 404, { error: "Немає такого маршруту" });
}).listen(3000, () => console.log("http://localhost:3000"));

Уже на цьому прикладі видно, що фреймворк потрібен не для «магії», а щоб не писати щоразу розбір шляхів, JSON і статуси вручну.

JSON — мова спілкування кухні й залу

JSON (JavaScript Object Notation) — це текстовий формат для передачі структурованих даних. Він виглядає майже як об'єкт JavaScript, але з кількома суворими правилами: ключі завжди в подвійних лапках, немає коментарів, немає функцій, немає undefined, останній елемент без коми. Бекенд серіалізує (serialize — перетворює на рядок) об'єкт через JSON.stringify(), ставить заголовок Content-Type: application/json, а браузер робить JSON.parse() (у fetch це await res.json()). Саме JSON зробив можливим, щоб бекенд на будь-якій мові спілкувався з фронтендом на будь-якій мові: це «англійська» для програм.

Спробуй сам
  1. Збережіть raw-api.mjs, запустіть node raw-api.mjs.
  2. У другому терміналі виконайте curl http://localhost:3000/notes — побачите масив із однією нотаткою.
  3. Створіть нову: curl -X POST http://localhost:3000/notes -H "Content-Type: application/json" -d '{"title":"Купити хліб"}'.
  4. Запитайте її за id: curl http://localhost:3000/notes/2. Потім спробуйте /notes/99 і подивіться на 404.
  5. Додайте маршрут DELETE /notes/:id самостійно. Підказка: notes.splice(index, 1) і статус 204 No Content без тіла.

5. Express: CRUD API для нотаток

Express — найстаріший і найпоширеніший веб-фреймворк для Node.js. Він тонкий: не нав'язує структуру, лише дає роутер, middleware і зручні обгортки над req/res. Альтернатива з тією самою філософією, але сучасніша і швидша — Hono; його код майже дзеркальний до Express, тож вивчивши один, ви за годину освоїте інший. Тут ми пишемо на Express, бо в 90 % туторіалів і вакансій зустрінете саме його.

CRUD — це чотири базові операції над будь-якими даними: Create (створити), Read (прочитати), Update (оновити), Delete (видалити). Вони відповідають методам HTTP: POST, GET, PUT/PATCH, DELETE. Майже будь-який бекенд — це CRUD із додатковими правилами.

# Створюємо проєкт
mkdir notes-api && cd notes-api
npm init -y
npm pkg set type=module          # вмикаємо ES modules (import/export)
npm install express zod
npm install -D nodemon           # автоперезапуск при змінах (для розробки)
// src/app.mjs — повний CRUD для нотаток з in-memory масивом
import express from "express";
import { randomUUID } from "node:crypto";

const app = express();

// Middleware: розбирати JSON у тілі запиту і класти в req.body
app.use(express.json());

// "База даних" у пам'яті. Зникне після перезапуску — це нормально для навчання.
let notes = [
  { id: randomUUID(), title: "Вивчити event loop", done: false, createdAt: new Date().toISOString() },
];

// READ — усі нотатки (з фільтром ?done=true і лімітом ?limit=10)
app.get("/notes", (req, res) => {
  let result = notes;
  if (req.query.done !== undefined) {
    const done = req.query.done === "true";
    result = result.filter((n) => n.done === done);
  }
  const limit = Number(req.query.limit ?? 100);
  res.json(result.slice(0, limit)); // res.json = stringify + правильний Content-Type
});

// READ — одна нотатка за id (параметр шляху :id доступний у req.params)
app.get("/notes/:id", (req, res) => {
  const note = notes.find((n) => n.id === req.params.id);
  if (!note) return res.status(404).json({ error: "Нотатку не знайдено" });
  res.json(note);
});

// CREATE — нова нотатка
app.post("/notes", (req, res) => {
  const { title } = req.body;
  if (typeof title !== "string" || title.trim() === "") {
    return res.status(400).json({ error: "Поле title обов'язкове і має бути рядком" });
  }
  const note = { id: randomUUID(), title: title.trim(), done: false, createdAt: new Date().toISOString() };
  notes.push(note);
  res.status(201).json(note); // 201 + повертаємо створений ресурс (з id!)
});

// UPDATE — часткове оновлення (PATCH): змінюємо тільки передані поля
app.patch("/notes/:id", (req, res) => {
  const note = notes.find((n) => n.id === req.params.id);
  if (!note) return res.status(404).json({ error: "Нотатку не знайдено" });

  const { title, done } = req.body;
  if (title !== undefined) note.title = String(title).trim();
  if (done !== undefined) note.done = Boolean(done);
  res.json(note);
});

// DELETE — видалити
app.delete("/notes/:id", (req, res) => {
  const before = notes.length;
  notes = notes.filter((n) => n.id !== req.params.id);
  if (notes.length === before) return res.status(404).json({ error: "Нотатку не знайдено" });
  res.status(204).end(); // 204 No Content — успіх, тіла немає
});

// Якщо жоден маршрут не спрацював — 404 у JSON, а не HTML-сторінка Express
app.use((req, res) => {
  res.status(404).json({ error: `Маршрут ${req.method} ${req.path} не існує` });
});

const PORT = process.env.PORT ?? 3000;
app.listen(PORT, () => console.log(`API на http://localhost:${PORT}`));

Порівняйте з версією на чистому node:http: зникли ручний парсинг URL, читання тіла шматками, writeHead. З'явились req.params, req.query, req.body, res.json(), res.status(). Ось за це ми і любимо фреймворки.

Зверніть увагу на кілька конвенцій REST (REpresentational State Transfer — архітектурний стиль, який робить API передбачуваним):

  • Шляхи — іменники у множині: /notes, а не /getNotes чи /note. Дієслово — це метод HTTP.
  • POST /notes повертає 201 і створений об'єкт разом із id, щоб клієнт міг одразу з ним працювати.
  • DELETE повертає 204 без тіла. Повторний DELETE тієї самої нотатки — 404 (або, за іншою школою, знову 204: операція ідемпотентна).
  • Помилки завжди в однаковому JSON-форматі ({ "error": "..." }), щоб фронтенд обробляв їх одним кодом.
Чому це важливо

REST-конвенції — це не бюрократія, а спільна мова. Коли ваш колега-фронтендер бачить GET /notes/:id, він без документації знає: буде 200 із об'єктом або 404. Коли бачить POST — очікує 201 і тіло з id. Дотримання конвенцій економить години узгоджень. Детальніше — у розділі 09 про дизайн API, а поки що тримайтеся цих чотирьох правил.

6. Middleware, статуси, валідація, конфіг

Middleware — конвеєр на кухні

На професійній кухні страва не готується однією людиною. Спершу замовлення реєструють (лог), потім перевіряють, чи є всі інгредієнти (парсинг і валідація), потім кухар готує (обробник маршруту), і наприкінці шеф перевіряє тарілку (обробка помилок). Кожна станція робить одну справу і передає далі. В Express така станція називається middleware (проміжний обробник) — функція з сигнатурою (req, res, next). Вона може: щось зробити і викликати next() (передати далі), або сама відправити відповідь і не викликати next() (зупинити конвеєр).

// src/middleware.mjs
// 1. Логер: записує метод, шлях і час обробки
export function logger(req, res, next) {
  const start = Date.now();
  // подія "finish" спрацьовує, коли відповідь повністю відправлена
  res.on("finish", () => {
    console.log(`${req.method} ${req.originalUrl} → ${res.statusCode} (${Date.now() - start} мс)`);
  });
  next(); // передати далі по конвеєру
}

// 2. Проста перевірка API-ключа (справжню автентифікацію розберемо в розділі 07)
export function requireApiKey(req, res, next) {
  if (req.headers["x-api-key"] !== process.env.API_KEY) {
    return res.status(401).json({ error: "Немає або невірний API-ключ" }); // зупиняємо конвеєр
  }
  next();
}

// 3. Обробник помилок — ЧОТИРИ аргументи, Express впізнає його саме за кількістю
export function errorHandler(err, req, res, next) {
  console.error(err); // у продакшені — у систему логування, не в консоль
  const status = err.status ?? 500;
  res.status(status).json({
    error: status === 500 ? "Внутрішня помилка сервера" : err.message, // не витікаємо деталі
  });
}
// у src/app.mjs — порядок має значення!
import { logger, requireApiKey, errorHandler } from "./middleware.mjs";

app.use(logger);          // 1. логуємо все
app.use(express.json());  // 2. парсимо JSON
app.use("/notes", requireApiKey); // 3. захищаємо тільки /notes
// ... маршрути ...
app.use(errorHandler);    // останній — ловить помилки з усіх обробників вище

Важлива деталь для Express 4: помилки з async-обробників не потрапляють в error handler автоматично — треба писати try/catch і викликати next(err), або поставити пакет express-async-errors. В Express 5 (стабільний з 2024 року) відхилені проміси ловляться автоматично. Hono ловить їх «з коробки».

Статуси відповіді: як казати правду про результат

Статус — це перша річ, яку бачить клієнт. Він має бути чесним. Найпотрібніші:

КодНазваКоли використовувати
200OKУспішний GET, PATCH, PUT — повертаємо дані
201CreatedPOST створив ресурс; у тілі — створений об'єкт
204No ContentУспіх без тіла: DELETE, іноді PUT
400Bad RequestКлієнт надіслав некоректні дані (невалідний JSON, немає поля)
401UnauthorizedМи не знаємо, хто ви (немає/невірний токен). Насправді означає «не автентифіковано»
403ForbiddenМи знаємо, хто ви, але вам не можна (немає прав)

Головне правило: 2xx — успіх, 4xx — винен клієнт, 5xx — винен сервер. Найпоширеніший гріх — повертати 200 із { "success": false } у тілі. Так фронтенд, проксі, кеші й моніторинг думають, що все добре, і помилки губляться.

Валідація вхідних даних із zod

Ніколи не довіряйте тому, що прийшло від клієнта. Гість може замовити «-5 порцій борщу» або «борщ, а ще видали всі рахунки». Ручні перевірки typeof title === "string" швидко перетворюються на кашу, тому використовують бібліотеку схем. zod — стандарт де-факто в TypeScript/JavaScript-світі: описуєте форму даних один раз, отримуєте і перевірку, і типи.

// src/schemas.mjs
import { z } from "zod";

export const createNoteSchema = z.object({
  title: z.string().trim().min(1, "Заголовок не може бути порожнім").max(200),
  done: z.boolean().optional().default(false),
});

// Для PATCH усі поля необов'язкові, але хоча б одне має бути
export const updateNoteSchema = createNoteSchema.partial().refine(
  (data) => Object.keys(data).length > 0,
  { message: "Передайте хоча б одне поле для оновлення" }
);

// Універсальний middleware: перевіряє req.body за схемою
export function validate(schema) {
  return (req, res, next) => {
    const result = schema.safeParse(req.body); // safeParse не кидає виняток
    if (!result.success) {
      return res.status(422).json({
        error: "Некоректні дані",
        details: result.error.issues.map((i) => ({ path: i.path.join("."), message: i.message })),
      });
    }
    req.body = result.data; // очищені й приведені до типу дані (зайві поля відкинуті)
    next();
  };
}
// у маршрутах — валідація як окрема станція конвеєра
import { createNoteSchema, updateNoteSchema, validate } from "./schemas.mjs";

app.post("/notes", validate(createNoteSchema), (req, res) => {
  // тут req.body гарантовано { title: string, done: boolean }
  const note = { id: randomUUID(), ...req.body, createdAt: new Date().toISOString() };
  notes.push(note);
  res.status(201).json(note);
});

app.patch("/notes/:id", validate(updateNoteSchema), (req, res) => { /* ... */ });

Змінні оточення і конфіг

Порт, ключі до бази даних, секрети для токенів — це не код, а налаштування середовища. На вашому ноутбуці база на localhost, на продакшені — на іншому хості з іншим паролем. Такі значення читають зі змінних оточення (environment variables) через process.env. Для локальної розробки їх зручно тримати у файлі .env, який ніколи не комітять у Git — замість нього комітять .env.example з порожніми значеннями.

# .env  (додайте його в .gitignore!)
PORT=3000
API_KEY=dev-secret-123
DATABASE_URL=postgres://user:pass@localhost:5432/notes
// src/config.mjs — єдине місце, де читаємо process.env, і одразу валідуємо
import { z } from "zod";

const envSchema = z.object({
  PORT: z.coerce.number().default(3000),        // coerce: "3000" -> 3000
  API_KEY: z.string().min(8),
  DATABASE_URL: z.string().url(),
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
});

// Node 20.6+ вміє читати .env без бібліотек: node --env-file=.env src/app.mjs
export const config = envSchema.parse(process.env); // впаде при старті, якщо чогось бракує — і це добре

Ідея «впасти при старті» важлива: краще, щоб сервер не запустився взагалі з повідомленням «немає DATABASE_URL», ніж запустився і впав о третій ночі на першому запиті до бази.

7. Структура проєкту та CORS

Шари: routes → controllers → services → repositories

Поки нотаток одна сотня рядків, усе може жити в одному файлі. Але проєкти ростуть, і «все в app.mjs» перетворюється на кухню, де суп варять у мийці. Індустрія виробила стандартне розділення на шари (layers), кожен із яких відповідає за одне:

notes-api/
├── src/
│   ├── app.mjs                 # створення Express, підключення middleware і роутерів
│   ├── server.mjs              # app.listen(config.PORT) — єдиний файл із побічним ефектом
│   ├── config.mjs              # читання і валідація process.env
│   ├── routes/notes.routes.mjs        # router.get("/", controller.list) ...
│   ├── controllers/notes.controller.mjs
│   ├── services/notes.service.mjs
│   ├── repositories/notes.repository.mjs
│   ├── schemas/notes.schema.mjs       # zod-схеми
│   └── middleware/{logger,errorHandler,validate}.mjs
├── tests/
├── .env.example
├── .gitignore                  # node_modules, .env
└── package.json
// src/repositories/notes.repository.mjs — єдине місце, що знає, ДЕ лежать дані
let notes = [];
export const notesRepository = {
  findAll: async () => [...notes],
  findById: async (id) => notes.find((n) => n.id === id) ?? null,
  create: async (note) => { notes.push(note); return note; },
  remove: async (id) => { const len = notes.length; notes = notes.filter((n) => n.id !== id); return notes.length !== len; },
};

// src/services/notes.service.mjs — правила, без HTTP
import { randomUUID } from "node:crypto";
import { notesRepository } from "../repositories/notes.repository.mjs";

export const notesService = {
  async create({ title, done }) {
    return notesRepository.create({ id: randomUUID(), title, done, createdAt: new Date().toISOString() });
  },
  async getOrThrow(id) {
    const note = await notesRepository.findById(id);
    if (!note) { const err = new Error("Нотатку не знайдено"); err.status = 404; throw err; }
    return note;
  },
};

// src/controllers/notes.controller.mjs — HTTP-обгортка
import { notesService } from "../services/notes.service.mjs";
export const notesController = {
  async getOne(req, res, next) {
    try { res.json(await notesService.getOrThrow(req.params.id)); }
    catch (err) { next(err); }   // передаємо в errorHandler
  },
  async create(req, res, next) {
    try { res.status(201).json(await notesService.create(req.body)); }
    catch (err) { next(err); }
  },
};

// src/routes/notes.routes.mjs — меню
import { Router } from "express";
import { notesController } from "../controllers/notes.controller.mjs";
import { validate } from "../middleware/validate.mjs";
import { createNoteSchema } from "../schemas/notes.schema.mjs";
export const notesRouter = Router();
notesRouter.get("/:id", notesController.getOne);
notesRouter.post("/", validate(createNoteSchema), notesController.create);

// src/app.mjs
app.use("/notes", notesRouter);

Зверніть увагу: репозиторій уже async, хоча працює з масивом. Коли в розділі 05 ми замінимо масив на PostgreSQL, сервіси і контролери не зміняться взагалі. Це головна вигода шарів.

Для просунутих

Шарова структура — спрощена версія «чистої архітектури» (Clean Architecture) і гексагональної архітектури (Ports & Adapters). Головна ідея в обох: бізнес-логіка в центрі не залежить від фреймворку, бази чи протоколу — це «порти», до яких підключаються «адаптери». Такий код легко тестувати (підмінили репозиторій на фейковий — сервіс тестується без бази) і легко переносити (замінили Express на Hono або HTTP на gRPC — сервіси не чіпаємо). NestJS, який часто зустрінете у вакансіях, — це Express/Fastify з примусово вбудованими шарами, модулями та впровадженням залежностей (dependency injection). Вивчивши шари «руками», ви зрозумієте, навіщо NestJS усі ці декоратори.

CORS простими словами

Ваш фронтенд працює на http://localhost:5173, а API — на http://localhost:3000. Це різні джерела (origin = схема + хост + порт). Браузер має правило безпеки — Same-Origin Policy: JavaScript зі сторінки одного джерела не може читати відповіді від іншого джерела без дозволу. Інакше будь-який сайт міг би від вашого імені зробити запит до вашого банку і прочитати баланс.

CORS (Cross-Origin Resource Sharing) — механізм, яким сервер каже браузеру: «цьому джерелу я дозволяю читати мої відповіді». Дозвіл передається заголовком Access-Control-Allow-Origin. Для «небезпечних» запитів (методи PUT/DELETE, нестандартні заголовки, Content-Type: application/json) браузер спершу надсилає preflight — розвідувальний запит методом OPTIONS, і лише отримавши дозвіл, надсилає справжній запит.

// npm install cors
import cors from "cors";

// Розробка: дозволити конкретний origin фронтенду
app.use(cors({
  origin: ["http://localhost:5173", "https://myapp.example.com"], // ніколи не "*" з credentials
  methods: ["GET", "POST", "PATCH", "DELETE"],
  credentials: true, // якщо надсилаєте cookie
}));
Підводні камені
  • CORS — не захист сервера. Це захист користувача браузера від чужих сайтів. Зловмисник із curl зробить будь-який запит незалежно від CORS. Авторизація має бути окремо.
  • origin: "*" у продакшені — дозволити всім читати відповіді. Для публічного read-only API нормально, для чогось із cookie або токенами — ні (браузер до того ж заборонить * разом із credentials: true).
  • Preflight на кожен запит уповільнює API. Заголовок Access-Control-Max-Age дозволяє браузеру кешувати дозвіл.

8. Тестування API і типові помилки

Три способи «пощупати» API

curl — консольна утиліта, є всюди, ідеальна для швидких перевірок і скриптів:

# GET із гарним виводом JSON (потрібен jq: brew install jq)
curl -s http://localhost:3000/notes | jq

# POST із заголовками, -i показує статус і заголовки відповіді
curl -i -X POST http://localhost:3000/notes \
  -H "Content-Type: application/json" \
  -H "x-api-key: dev-secret-123" \
  -d '{"title":"Написати тести"}'

# PATCH і DELETE
curl -X PATCH http://localhost:3000/notes/<id> -H "Content-Type: application/json" -d '{"done":true}'
curl -i -X DELETE http://localhost:3000/notes/<id>

Postman (або відкритий аналог Bruno, Insomnia) — графічний клієнт: колекції запитів, змінні середовища ({{baseUrl}}), автотести на відповідь, можливість поділитися колекцією з командою. Для великих API — стандарт.

REST Client — розширення VS Code: пишете запити в файлі api.http прямо в репозиторії, натискаєте «Send Request». Плюс — запити версіонуються в Git разом із кодом:

### api.http — розширення REST Client для VS Code
@baseUrl = http://localhost:3000
@apiKey = dev-secret-123

### Список нотаток
GET {{baseUrl}}/notes?done=false
x-api-key: {{apiKey}}

### Створити
POST {{baseUrl}}/notes
Content-Type: application/json
x-api-key: {{apiKey}}

{ "title": "Купити молоко" }

### Невалідні дані — очікуємо 422
POST {{baseUrl}}/notes
Content-Type: application/json
x-api-key: {{apiKey}}

{ "title": "" }

Автоматичні тести (Vitest + supertest) розберемо в розділі 10. Але вже зараз корисна звичка: до кожного маршруту мати приклад «щасливого» запиту і хоча б одного помилкового.

Спробуй сам
  1. Розкладіть app.mjs із розділу 5 на шари за структурою з розділу 7. Переконайтесь, що curl-команди вище працюють так само.
  2. Додайте валідацію zod до PATCH і перевірте, що { "done": "так" } повертає 422 з описом помилки.
  3. Створіть index.html з fetch("http://localhost:3000/notes"), відкрийте його через npx serve (буде інший порт) і подивіться на CORS-помилку в консолі. Потім підключіть cors і побачте, як вона зникає.
  4. Напишіть middleware, що додає заголовок X-Request-Id із randomUUID() до кожної відповіді, і виводьте цей id у логері. Так роблять у справжніх системах, щоб знайти запит у логах.
  5. Навмисно заблокуйте event loop: додайте маршрут GET /slow із циклом на 5 секунд і паралельно у другому терміналі викликайте GET /notes. Відчуйте на власному досвіді, що таке «офіціант, що стоїть біля плити».

Типові помилки новачків на бекенді

  1. Блокування event loop. Синхронні операції, важкі обчислення, JSON.parse величезних рядків у обробнику запиту. Ліки: асинхронні API, worker_threads, винесення в чергу задач (розділ 13).
  2. Відсутність обробки помилок. Один throw без catch у callback — і процес Node падає повністю, для всіх користувачів. Ліки: центральний error handler, process.on("unhandledRejection") для логування, менеджер процесів (pm2, Docker restart) для перезапуску.
  3. Довіра до вхідних даних. notes[req.params.id], підстановка req.body цілком в об'єкт (клієнт додасть isAdmin: true), SQL із конкатенацією рядків. Ліки: zod-схеми, що відкидають зайві поля, параметризовані запити (розділ 05).
  4. Секрети в коді. Пароль від бази у app.mjs, закомічений у GitHub. Ліки: .env + .gitignore, у продакшені — секрети платформи.
  5. Неправильні статуси. 200 на помилку, 500 на невалідні дані, 404 замість 401. Ліки: таблиця з розділу 6 і чесність.
  6. Логіка в контролерах. Через півроку в одному обробнику 300 рядків із SQL, відправкою email і розрахунком знижок. Ліки: шари.
  7. Зберігання стану в пам'яті процесу для чогось важливого. Наш масив notes зникає при перезапуску і не працює, якщо запущено два екземпляри сервера. Це нормально для навчання і абсолютно ненормально для продакшену — тому наступний розділ про бази даних.

Перевір себе

Питання
1. Чим відрізняється сервер «фізичний» від «логічного»?

Фізичний — комп'ютер (залізо в дата-центрі або ваш ноутбук). Логічний — програма, яка слухає порт і відповідає на запити. На одному фізичному сервері може працювати багато логічних (веб-сервер, база, кеш) на різних портах.

2. Чому Node.js в одному потоці встигає обслужити тисячі клієнтів?

Завдяки event loop: довгі операції введення-виведення (мережа, диск, база) віддаються libuv і операційній системі, а потік JavaScript тим часом обробляє інші запити. Він повертається до операції, коли та завершилась, через чергу подій. Це працює, поки сам JavaScript-код не виконує довгих синхронних обчислень.

3. Що виведе код: setTimeout(() => console.log("A"), 0); console.log("B");

Спочатку «B», потім «A». Навіть із затримкою 0 мс callback потрапляє у чергу подій і виконається лише після завершення поточного синхронного коду.

4. Які статуси мають повертати успішні POST, DELETE і запит неіснуючого ресурсу?

POST, що створив ресурс — 201 Created з об'єктом у тілі. DELETE — 204 No Content без тіла. Неіснуючий ресурс — 404 Not Found. А 200 з { success: false } — антипатерн.

5. Чим 401 відрізняється від 403?

401 Unauthorized — «ми не знаємо, хто ви»: немає або невірний токен, потрібна автентифікація. 403 Forbidden — «ми знаємо, хто ви, але вам не дозволено»: не вистачає прав.

6. Що таке middleware і чому важливий порядок їх реєстрації?

Middleware — функція (req, res, next), станція на конвеєрі обробки запиту. Виконуються в порядку app.use(). Якщо зареєструвати роутер до express.json(), у обробниках req.body буде undefined; обробник помилок (4 аргументи) має бути останнім, інакше не зловить помилки з маршрутів нижче.

7. Чому «у Postman працює, а в браузері помилка CORS»?

CORS перевіряє тільки браузер, захищаючи користувача від чужих сайтів. Postman і curl не є браузерами і на заголовок Access-Control-Allow-Origin не дивляться. Щоб працювало в браузері, сервер має явно дозволити origin фронтенду.

8. Навіщо шар repositories, якщо сервіс може сам зробити запит до бази?

Щоб бізнес-логіка не залежала від способу зберігання. Заміна масиву на PostgreSQL або підміна на фейковий репозиторій у тестах не торкається сервісів і контролерів. Кожен шар знає лише про шар під собою.

Що запам'ятати

  • Бекенд — «кухня»: усе, що клієнт не бачить, але від чого залежить результат. Перевірка прав, розрахунки і секрети живуть тільки тут.
  • Node.js — рантайм для JavaScript (V8 + libuv). Один потік JS + event loop: довгі I/O-операції не блокують, довгі обчислення — блокують усіх.
  • Маршрут = метод + шлях. Дані приходять через параметри шляху (/notes/:id), query (?limit=5) і тіло (JSON).
  • REST-конвенції: іменники в множині, POST → 201 з об'єктом, DELETE → 204, помилки в єдиному JSON-форматі, 4xx — винен клієнт, 5xx — сервер.
  • Middleware — конвеєр (req, res, next); порядок реєстрації = порядок виконання; error handler має 4 аргументи і стоїть останнім.
  • Ніколи не довіряйте вхідним даним: валідуйте схемою (zod), відкидайте зайві поля, повертайте 400/422 з поясненням.
  • Конфіг і секрети — у змінних оточення (.env у .gitignore), валідуйте їх при старті.
  • Шари routes → controllers → services → repositories: кожен знає лише про сусіда знизу; це робить код тестованим і замінюваним.
  • CORS — дозвіл від сервера, який перевіряє браузер. Це захист користувача, а не сервера.
  • Перевіряйте API через curl, Postman/Bruno або REST Client; тримайте приклади запитів у репозиторії.
Ресурси для поглиблення
  • Node.js API Documentation — офіційна документація: http, fs, crypto, worker_threads. Звіряйтеся тут, а не з випадковими блогами.
  • The Node.js Event Loop, Timers, and process.nextTick() — офіційний гайд про event loop із фазами циклу. Обов'язково після цього розділу.
  • Express: Routing та Using middleware — два ключові розділи документації Express; там же Error handling.
  • Hono Documentation — сучасна альтернатива Express, яка працює в Node, Bun, Deno і Cloudflare Workers. Порівняйте їхній «Getting started» з нашим кодом.
  • MDN: HTTP — методи, статуси, заголовки, CORS з діаграмами. Довідник, до якого повертатиметесь роками.
  • restfulapi.net — доступне пояснення принципів REST, іменування ресурсів і використання методів/статусів.
  • roadmap.sh — Backend Developer Roadmap — карта всього, що має знати бекенд-розробник; корисно, щоб бачити, куди рухатися після цього посібника.
  • roadmap.sh — Node.js Roadmap — деталізована карта саме Node-екосистеми.
  • zod.dev — документація zod: типи, refine, transform, інтеграція з TypeScript.
  • Postman Learning Center — як організовувати колекції, змінні середовища і писати тести на відповіді.
  • REST Client для VS Code — розширення для .http-файлів у репозиторії.
  • Node.js Best Practices (goldbergyoni) — найповніша збірка практик для продакшен-Node: структура, обробка помилок, безпека, тестування.
