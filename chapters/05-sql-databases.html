Пояснення для п'ятирічного

Уяви, що всі свої малюнки, листівки й фотографії ти складаєш в одну велику коробку. Спершу зручно: кинув — і забув. Але коли треба знайти малюнок кота, який ти намалював минулого літа, доведеться перерити все. А тепер уяви шафу з підписаними шухлядами: «Малюнки», «Листівки», «Фото», і всередині кожної — картки в алфавітному порядку з датою. Знайти кота — секунда. І ще: на кожній картці записано, до якого альбому вона належить, тож ти ніколи не переплутаєш. Ця шафа — база даних. Шухляди — таблиці. Картки — рядки. Підписи «до якого альбому» — зв'язки. А мова, якою ти просиш шафу «дай усі малюнки з котами за минуле літо» — SQL.

1. Навіщо база даних, а не файл

У розділі 04 наші нотатки жили в масиві в пам'яті. Перший крок до «справжнього» зберігання, який спадає на думку новачку: записувати їх у файл notes.json. Це навіть працює — до першої тисячі користувачів. А потім починаються проблеми:

  • Пошук. Щоб знайти одну нотатку серед мільйона, треба прочитати весь файл і перебрати все. База даних знаходить її за кілька мілісекунд завдяки індексам.
  • Одночасний доступ. Два запити одночасно змінюють файл: один читає старий вміст, другий пише новий — зміни першого зникають. База даних керує паралельним доступом і гарантує, що жоден запис не загубиться.
  • Часткова зміна. Оновити одне поле однієї нотатки = переписати весь файл. База змінює тільки потрібний рядок.
  • Надійність. Світло вимкнули посеред запису — файл пошкоджено, дані втрачено. База даних веде журнал (WAL — write-ahead log) і після перезапуску відновлюється у консистентний стан.
  • Зв'язки. Нотатка належить користувачу, має теги, коментарі. У JSON ви або дублюєте дані, або пишете власну систему посилань. У реляційній базі зв'язки — вбудована функція.
  • Мова запитів. «Топ-10 користувачів за кількістю нотаток за останній місяць» — один рядок SQL проти сторінки JavaScript.

Система керування базами даних (СКБД, DBMS — Database Management System) — це програма, яка бере на себе все перелічене. Ми працюватимемо з PostgreSQL — відкритою, безкоштовною, найпотужнішою реляційною СКБД, яка сьогодні є типовим вибором для нових проєктів. Інші популярні: MySQL/MariaDB (класика веб-хостингів), SQLite (вбудована база в одному файлі — ідеальна для мобільних застосунків і прототипів), Microsoft SQL Server і Oracle (корпоративний світ).

Чому це важливо

База даних — єдина частина системи, яку не можна «просто перезапустити». Код можна переписати, сервер — замінити, а втрачені дані користувачів не повернути. Тому розуміння того, як база зберігає, шукає і захищає дані, — не «бекендна деталь», а фундамент. Більшість катастроф у продакшені (втрачені замовлення, повільні сторінки, зламані акаунти) пов'язані з базою даних.

2. Реляційна модель: таблиці, ключі, зв'язки

Слово «реляційна» походить від математичного терміна relation (відношення), а не від «зв'язок», хоч зв'язки там теж є. Практично реляційна база — це набір таблиць (tables). Кожна таблиця має:

  • колонки (columns) — назви полів із фіксованим типом даних (data type): текст, число, дата, логічне значення;
  • рядки (rows, записи) — конкретні дані, по одному значенню для кожної колонки;
  • первинний ключ (primary key, PK) — колонка (або кілька), значення якої унікально ідентифікує рядок. Зазвичай це id;
  • зовнішній ключ (foreign key, FK) — колонка, яка містить первинний ключ рядка з іншої таблиці. Так і виникають зв'язки.

3. Нормалізація простими словами

Нормалізація (normalization) — набір правил, як розкладати дані по таблицях, щоб кожен факт зберігався рівно один раз. Уявіть, що в таблиці posts у кожному рядку записано ім'я та email автора. Автор змінив email — треба оновити тисячу рядків, а якщо один пропустити, база «бреше». Це називається аномалією оновлення. Нормалізація її прибирає.

Класичних «нормальних форм» багато, але на практиці досить трьох:

  1. 1НФ (перша нормальна форма): у кожній комірці — одне атомарне значення, без списків. Погано: колонка tags = "sql, postgres, backend". Добре: окрема таблиця tags і зв'язок N:M. (Postgres дозволяє масиви й JSON, і це свідоме відхилення від 1НФ, яке інколи виправдане, — але не за замовчуванням.)
  2. 2НФ: кожна не-ключова колонка залежить від усього первинного ключа, а не від його частини. Актуально для складених ключів: у таблиці order_items (order_id, product_id, quantity, product_name) поле product_name залежить лише від product_id — його треба винести в products.
  3. 3НФ: не-ключові колонки не залежать одна від одної. У users (id, city, country) країна залежить від міста, а не від користувача — винести в cities. Гасло 3НФ: «кожне поле залежить від ключа, від усього ключа й ні від чого, крім ключа».

Коли денормалізувати? Коли ви точно виміряли, що зв'язування таблиць (JOIN) у гарячому запиті — вузьке місце, і готові підтримувати дублікат. Типові приклади: лічильник comments_count у таблиці posts (щоб не рахувати щоразу), total_amount у замовленні (щоб не перераховувати з позицій і щоб історична сума не змінилась при зміні цін). Правило: спочатку нормалізуйте, потім денормалізуйте свідомо і з планом оновлення дубліката (тригер, транзакція або фонова задача).

Підводні камені
  • Одна гігантська таблиця. Новачки кладуть все в posts: ім'я автора, його email, назви тегів через кому. Перша ж зміна email перетворюється на бомбу.
  • Перенормалізація. Протилежна крайність: таблиця user_first_names, user_last_names. Якщо дані завжди змінюються разом і не дублюються — вони живуть в одній таблиці.
  • float для грошей. 0.1 + 0.2 = 0.30000000000000004. Тільки numeric або цілі копійки в bigint.
  • timestamp без tz. Сервер у Києві, користувач у Варшаві, база в Франкфурті — час «пливе». Завжди timestamptz і зберігання в UTC.

4. SQL: створити, вставити, вибрати, оновити, видалити, з'єднати

SQL (Structured Query Language) — декларативна мова: ви описуєте, що хочете отримати, а база сама вирішує, як це зробити. SQL нечутливий до регістру ключових слів, але за традицією їх пишуть великими, а назви таблиць і колонок — малими через snake_case.

Створення таблиць (DDL)

-- Мова визначення даних (DDL — Data Definition Language)
CREATE TABLE users (
  id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text NOT NULL UNIQUE,            -- обмеження: обов'язкове і унікальне
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE posts (
  id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     integer NOT NULL REFERENCES users(id) ON DELETE CASCADE, -- зовнішній ключ
  title       text NOT NULL CHECK (length(title) > 0),               -- бізнес-правило на рівні бази
  body        text NOT NULL DEFAULT '',
  published   boolean NOT NULL DEFAULT false,
  created_at  timestamptz NOT NULL DEFAULT now()
);

Вставка, вибірка, оновлення, видалення (DML)

-- Мова маніпуляції даними (DML — Data Manipulation Language)
INSERT INTO users (email, name) VALUES
  ('ann@mail.ua', 'Анна'),
  ('bo@mail.ua',  'Богдан')
RETURNING id;   -- Postgres-фішка: одразу повернути згенеровані id

INSERT INTO posts (user_id, title, body, published) VALUES
  (1, 'Про котів', 'Коти — це...', true),
  (1, 'Про собак', 'Собаки — це...', false),
  (2, 'Про SQL',   'SQL — це...', true);

-- SELECT: які колонки, з якої таблиці, за якою умовою, в якому порядку, скільки
SELECT id, title, created_at
FROM posts
WHERE published = true AND user_id = 1     -- фільтр
ORDER BY created_at DESC                    -- сортування: найновіші зверху
LIMIT 10 OFFSET 0;                          -- пагінація: перша сторінка по 10

-- Оператори у WHERE
SELECT * FROM posts WHERE title ILIKE '%кот%';          -- пошук без урахування регістру
SELECT * FROM posts WHERE id IN (1, 2, 3);
SELECT * FROM posts WHERE created_at >= now() - interval '7 days';
SELECT * FROM users WHERE name IS NULL;                   -- NULL порівнюють тільки через IS

-- UPDATE: ЗАВЖДИ з WHERE, інакше оновите всі рядки
UPDATE posts SET published = true, title = 'Про собак (оновлено)'
WHERE id = 2
RETURNING *;

-- DELETE: та сама історія з WHERE
DELETE FROM posts WHERE id = 2;

Агрегації: GROUP BY і HAVING

-- Скільки постів у кожного користувача
SELECT user_id, count(*) AS posts_count, max(created_at) AS last_post_at
FROM posts
GROUP BY user_id            -- згорнути рядки в групи за user_id
HAVING count(*) >= 2        -- фільтр ПІСЛЯ групування (WHERE працює ДО)
ORDER BY posts_count DESC;

-- Інші агрегатні функції: sum(), avg(), min(), max(), count(DISTINCT col), string_agg()

JOIN — з'єднання таблиць

Найважливіша операція реляційної бази. JOIN «склеює» рядки двох таблиць за умовою — зазвичай рівністю FK і PK.

-- Пости з іменами авторів (псевдоніми u і p скорочують запис)
SELECT p.id, p.title, u.name AS author, u.email
FROM posts AS p
INNER JOIN users AS u ON u.id = p.user_id
WHERE p.published = true
ORDER BY p.created_at DESC;

-- Усі користувачі та кількість їхніх постів (включно з тими, у кого 0)
SELECT u.name, count(p.id) AS posts_count
FROM users AS u
LEFT JOIN posts AS p ON p.user_id = u.id
GROUP BY u.id, u.name
ORDER BY posts_count DESC;

-- Підзапит (subquery): користувачі, які мають хоча б один опублікований пост
SELECT name FROM users
WHERE id IN (SELECT user_id FROM posts WHERE published = true);

-- Те саме через EXISTS — часто швидше на великих таблицях
SELECT name FROM users u
WHERE EXISTS (SELECT 1 FROM posts p WHERE p.user_id = u.id AND p.published);

-- CTE (Common Table Expression) — "тимчасова таблиця" для читабельності
WITH active_authors AS (
  SELECT user_id, count(*) AS cnt FROM posts GROUP BY user_id HAVING count(*) > 1
)
SELECT u.name, a.cnt
FROM active_authors a
JOIN users u ON u.id = a.user_id;

5. Індекси: як база шукає швидко

Без індексу запит SELECT * FROM users WHERE email = 'ann@mail.ua' змушує базу прочитати всі рядки таблиці й перевірити кожен. Це називається послідовне сканування (sequential scan) — у мільйонній таблиці це секунди. Індекс (index) — окрема структура даних, яка зберігає значення колонки у відсортованому вигляді разом із «адресами» рядків. Як алфавітний покажчик у кінці книги: замість гортати 500 сторінок, ви дивитесь у покажчик і йдете одразу на сторінку 312.

Стандартний індекс у PostgreSQL — B-tree (збалансоване дерево). Уявіть шафу з шухлядами, на кожній написано діапазон: «А–Ж», «З–О», «П–Я». Усередині — знову шухляди з вужчими діапазонами. Щоб знайти «Кузьменко», ви відкриваєте 3–4 шухляди замість перегляду всіх карток. Кожен «рівень» дерева зменшує область пошуку в сотні разів, тому в дереві з мільйона записів достатньо 3–4 кроків.

-- Створити індекс (PK і UNIQUE створюють індекси автоматично)
CREATE INDEX posts_user_id_idx ON posts (user_id);          -- для JOIN і WHERE user_id = ?
CREATE INDEX posts_published_created_idx ON posts (published, created_at DESC); -- складений: під конкретний запит
CREATE INDEX posts_title_trgm_idx ON posts USING gin (title gin_trgm_ops);     -- для ILIKE '%кот%' (розширення pg_trgm)

-- Подивитись план виконання: чи використовується індекс?
EXPLAIN ANALYZE
SELECT * FROM posts WHERE user_id = 1 AND published ORDER BY created_at DESC LIMIT 10;
-- Погано:  Seq Scan on posts  (cost=0.00..25000 rows=...)   ← читає всю таблицю
-- Добре:   Index Scan using posts_user_id_idx on posts       ← пішов по індексу

Коли створювати індекс: на зовнішні ключі (Postgres не робить це автоматично!), на колонки з WHERE у частих запитах, на колонки сортування в пагінації, на поля пошуку. Чому не на все: кожен індекс — це додаткова структура, яку треба оновлювати при кожному INSERT/UPDATE/DELETE. Десять індексів на таблиці робить запис у неї в кілька разів повільнішим і займає диск. Індекс на колонці з двома значеннями (published окремо) майже марний — база все одно прочитає половину таблиці. Правило: індекс під конкретний повільний запит, підтверджений через EXPLAIN ANALYZE.

Чому це важливо

Дев'ять із десяти «сайт гальмує» у стартапах — це один запит без індексу, який на тестових 100 рядках літав, а на 5 мільйонах у продакшені читає всю таблицю. Уміння відкрити EXPLAIN ANALYZE, побачити Seq Scan і додати правильний індекс — навичка, за яку платять. Сайт Use The Index, Luke — найкраща безкоштовна книга про це.

6. Транзакції та ACID

Класичний приклад: переказ 100 грн з рахунку Анни на рахунок Богдана. Це дві операції: відняти 100 у Анни, додати 100 Богдану. Що, якщо після першої сервер впаде? Гроші зникнуть. Що, якщо в цей же момент інший запит читає баланси? Побачить стан, якого «не було». Транзакція (transaction) — це група операцій, яка виконується як одна: або всі, або жодна.

BEGIN;                                                   -- почати транзакцію
UPDATE accounts SET balance = balance - 100 WHERE id = 1; -- Анна
UPDATE accounts SET balance = balance + 100 WHERE id = 2; -- Богдан
-- Перевірка бізнес-правила прямо в базі:
-- якщо баланс Анни став від'ємним, CHECK (balance >= 0) на таблиці кине помилку
COMMIT;                                                  -- зафіксувати все разом
-- або ROLLBACK; — відкотити все, ніби нічого не було

Гарантії транзакцій описує абревіатура ACID:

  • A — Atomicity (атомарність): усе або нічого. Впав сервер між двома UPDATE — після перезапуску база відкотить перший.
  • C — Consistency (узгодженість): транзакція переводить базу з одного правильного стану в інший. Обмеження (NOT NULL, CHECK, FK) не можуть бути порушені «в кінці».
  • I — Isolation (ізольованість): паралельні транзакції не бачать проміжних станів одна одної (з нюансами — нижче).
  • D — Durability (довговічність): після COMMIT дані не зникнуть навіть при вимкненні живлення — вони вже у журналі WAL на диску.

Рівні ізоляції — це компроміс між «ідеальною ізоляцією» і швидкістю. У Postgres за замовчуванням Read Committed: транзакція бачить лише закомічені зміни інших, але два однакові SELECT усередині однієї транзакції можуть повернути різне, якщо між ними хтось закомітив. Repeatable Read робить «знімок» на початку транзакції — усі читання бачать ту саму картину. Serializable — найсуворіший: база гарантує, що результат такий, ніби транзакції виконувались по черзі, і при конфлікті одну з них відхилить (треба повторити). Для більшості CRUD достатньо Read Committed; для фінансових операцій, лічильників і «перевірив-і-записав» логіки — Repeatable Read/Serializable або явні блокування (SELECT ... FOR UPDATE).

Для просунутих

PostgreSQL реалізує ізоляцію через MVCC (Multi-Version Concurrency Control): при оновленні рядка база не перезаписує його, а створює нову версію, а стара лишається видимою транзакціям, що почалися раніше. Тому читачі не блокують писців, а писці — читачів. Побічний ефект: «мертві» версії накопичуються, і їх прибирає процес VACUUM (автоматично — autovacuum). Якщо ви колись побачите, що таблиця «розпухла» після мільйонів UPDATE, — це воно. Класична задача «перевірити залишок і списати» без блокування або Serializable — гонка (race condition): дві транзакції обидві бачать залишок 1, обидві списують, залишок стає −1. Правильно: UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0 RETURNING qty — одна атомарна операція.

import { pool } from "../db.mjs";

export const postsRepository = {
  async findPublished({ limit = 10, offset = 0 }) {
    // $1, $2 — параметри. Значення передаються ОКРЕМО від тексту SQL.
    const { rows } = await pool.query(
      `SELECT p.id, p.title, p.created_at, u.name AS author
       FROM posts p JOIN users u ON u.id = p.user_id
       WHERE p.published = true
       ORDER BY p.created_at DESC
       LIMIT $1 OFFSET $2`,
      [limit, offset]
    );
    return rows;
  },

  async create({ userId, title, body }) {
    const { rows } = await pool.query(
      `INSERT INTO posts (user_id, title, body) VALUES ($1, $2, $3) RETURNING *`,
      [userId, title, body]
    );
    return rows[0];
  },

  // Транзакція: потрібне ОДНЕ з'єднання на всі кроки, тому беремо клієнта з пулу
  async transferKarma(fromId, toId, amount) {
    const client = await pool.connect();
    try {
      await client.query("BEGIN");
      await client.query("UPDATE users SET karma = karma - $1 WHERE id = $2", [amount, fromId]);
      await client.query("UPDATE users SET karma = karma + $1 WHERE id = $2", [amount, toId]);
      await client.query("COMMIT");
    } catch (err) {
      await client.query("ROLLBACK"); // будь-яка помилка — відкотити все
      throw err;
    } finally {
      client.release();               // ЗАВЖДИ повернути з'єднання в пул
    }
  },
};

SQL-ін'єкції: чому параметри, а не конкатенація

Найнебезпечніша помилка новачка — склеювати SQL із рядка користувача. Гість ресторану пише в графі «ім'я для бронювання»: «Іван; а ще віддайте всю касу» — і якщо офіціант тупо читає записку вголос як команду, кухня виконає обидві частини.

// ❌ НІКОЛИ так

// ✅ Завжди так
const rows = await pool.query("SELECT * FROM users WHERE email = $1", [req.body.email]);

// Єдине, що не можна параметризувати — назви таблиць/колонок і напрямок сортування.
// Для них — білий список:
const allowedSort = { newest: "created_at DESC", oldest: "created_at ASC" };

await pool.query(`SELECT * FROM posts ORDER BY ${orderBy} LIMIT $1`, [limit]);

ORM і query builder: Drizzle та Prisma

Писати весь SQL рядками працює, але не дає автодоповнення, типів і захисту від одруків у назвах колонок. Тут допомагають два класи інструментів. ORM (Object-Relational Mapping) — бібліотека, яка представляє таблиці як об'єкти/класи і генерує SQL сама. Query builder — «конструктор SQL» із функцій, ближчий до самої мови. Два лідери в екосистемі TypeScript:

  • Prisma — «повноцінний ORM»: власна мова схеми (schema.prisma), генерований клієнт із ідеальними типами, вбудовані міграції, Prisma Studio для перегляду даних. Простий старт, але між вами й SQL — товстий шар абстракції.
  • Drizzle — «SQL-подібний» query builder із типами: схема описується в TypeScript, запити виглядають майже як SQL, тонкий і швидкий, є міграції (drizzle-kit). Якщо ви знаєте SQL, Drizzle не ховає його від вас. Саме його ми використовуватимемо далі в посібнику.

import { pgTable, integer, text, boolean, timestamp, primaryKey } from "drizzle-orm/pg-core";

export const users = pgTable("users", {
  id: integer("id").primaryKey().generatedAlwaysAsIdentity(),
  email: text("email").notNull().unique(),
  name: text("name").notNull(),
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
});

export const posts = pgTable("posts", {
  id: integer("id").primaryKey().generatedAlwaysAsIdentity(),
  userId: integer("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
  title: text("title").notNull(),
  body: text("body").notNull().default(""),
  published: boolean("published").notNull().default(false),
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
});

export const tags = pgTable("tags", {
  id: integer("id").primaryKey().generatedAlwaysAsIdentity(),
  name: text("name").notNull().unique(),
});

// Join-таблиця для N:M зі складеним первинним ключем
export const postTags = pgTable("post_tags", {

}, (t) => [primaryKey({ columns: [t.postId, t.tagId] })]);

import { drizzle } from "drizzle-orm/node-postgres";
import pg from "pg";
import * as schema from "./schema";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
export const db = drizzle(pool, { schema });

// src/repositories/posts.repository.ts — запити з типами
import { eq, desc, count } from "drizzle-orm";
import { db } from "../db";
import { posts, users } from "../db/schema";

export async function findPublished(limit = 10) {
  // Drizzle згенерує майже той самий SQL, що ми писали руками, але з автодоповненням
  return db
    .select({ id: posts.id, title: posts.title, author: users.name, createdAt: posts.createdAt })
    .from(posts)
    .innerJoin(users, eq(users.id, posts.userId))
    .where(eq(posts.published, true))
    .orderBy(desc(posts.createdAt))
    .limit(limit);
}

export async function createPost(data: { userId: number; title: string; body: string }) {
  const [post] = await db.insert(posts).values(data).returning(); // типізований результат
  return post;
}

export async function postsPerUser() {
  return db
    .select({ name: users.name, postsCount: count(posts.id) })
    .from(users)
    .leftJoin(posts, eq(posts.userId, users.id))
    .groupBy(users.id, users.name);
}

Міграції: як змінювати схему без втрати даних

Схема бази змінюється: додали колонку, перейменували таблицю, створили індекс. Робити це «руками в DBeaver» на продакшені — шлях до катастрофи: на вашому ноутбуці колонка є, у колеги немає, на сервері — інша версія. Міграція (migration) — це файл із SQL-змінами, пронумерований і закомічений у Git. База зберігає таблицю з переліком уже застосованих міграцій, тому команда «застосуй міграції» на будь-якому середовищі приводить схему до однакового стану.

# drizzle.config.ts вказує на schema.ts і DATABASE_URL
npx drizzle-kit generate   # порівняти schema.ts із попереднім станом → створити drizzle/0003_*.sql
npx drizzle-kit migrate    # застосувати незастосовані міграції до бази
npx drizzle-kit studio     # веб-інтерфейс для перегляду даних

Правила міграцій: ніколи не редагуйте вже застосовану міграцію — створюйте нову; небезпечні зміни (видалення колонки, перейменування) робіть у два кроки (спершу додати нове поле і перенести дані, потім у наступному релізі видалити старе), щоб старий і новий код могли працювати одночасно під час деплою.

Бекапи

База без бекапу — це не база, а тимчасовий кеш. Мінімум: pg_dump за розкладом у сховище (S3 тощо) і — головне — регулярна перевірка відновлення. Бекап, який ніхто не пробував відновити, не існує.

# Зробити дамп (стиснутий, "custom" формат — можна відновлювати вибірково)
docker exec pg-blog pg_dump -U postgres -Fc blog > blog-$(date +%F).dump

# Відновити в порожню базу
docker exec -i pg-blog pg_restore -U postgres -d blog_restored < blog-2026-09-09.dump

Керовані бази (Neon, Supabase, AWS RDS, Railway) роблять бекапи автоматично і дозволяють відновитися «на момент часу» (point-in-time recovery). Для продакшену це майже завжди правильний вибір замість власного контейнера.

Підводні камені
  • N+1 запитів. Взяли 100 постів одним запитом, а потім для кожного окремо запитали автора — 101 запит замість одного JOIN. ORM робить це непомітно; дивіться в логи SQL.
  • SELECT * у продакшен-коді. Тягне всі колонки (включно з body на 50 КБ), ламається при зміні порядку колонок. Перелічуйте потрібні.
  • Забутий client.release() — пул вичерпується, і всі наступні запити зависають назавжди. Завжди finally.
  • OFFSET для глибокої пагінації. OFFSET 100000 змушує базу прочитати й викинути 100 000 рядків. Використовуйте keyset-пагінацію: WHERE created_at < $last_seen ORDER BY created_at DESC LIMIT 20.
  • Пароль бази в коді або Docker-команді в README — тільки змінні оточення.

8. Проєктуємо схему блогу

Зберемо все разом. Типовий блог має користувачів, пости, коментарі та теги. Нижче — ER-діаграма (Entity-Relationship — «сутність-зв'язок»), стандартний спосіб малювати схему бази.

-- Повна DDL-схема блогу (той самий результат дасть drizzle-kit generate зі schema.ts вище)
CREATE TABLE users (
  id            integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email         text NOT NULL UNIQUE,
  name          text NOT NULL,
  password_hash text NOT NULL,                 -- ніколи не зберігаємо пароль відкритим (розділ 07)
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE posts (
  id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    integer NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title      text NOT NULL,
  slug       text NOT NULL UNIQUE,             -- для гарних URL: /posts/pro-kotiv
  body       text NOT NULL DEFAULT '',
  published  boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX posts_user_id_idx ON posts (user_id);
CREATE INDEX posts_published_created_idx ON posts (created_at DESC) WHERE published; -- частковий індекс

CREATE TABLE comments (
  id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  post_id    integer NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  user_id    integer NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  body       text NOT NULL CHECK (length(body) BETWEEN 1 AND 5000),
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX comments_post_id_idx ON comments (post_id);

CREATE TABLE tags (
  id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL UNIQUE
);

CREATE TABLE post_tags (
  post_id integer NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  tag_id  integer NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)               -- складений PK: пара унікальна і одразу індексована
);

-- Запит для головної сторінки: пости з автором, тегами і кількістю коментарів
SELECT
  p.id, p.title, p.slug, p.created_at,
  u.name AS author,
  count(DISTINCT c.id) AS comments_count,
  coalesce(array_agg(DISTINCT t.name) FILTER (WHERE t.name IS NOT NULL), '{}') AS tags
FROM posts p
JOIN users u        ON u.id = p.user_id
LEFT JOIN comments c ON c.post_id = p.id
LEFT JOIN post_tags pt ON pt.post_id = p.id
LEFT JOIN tags t     ON t.id = pt.tag_id
WHERE p.published
GROUP BY p.id, u.name
ORDER BY p.created_at DESC
LIMIT 20;
Чому це важливо

Схема бази — найдорожче для зміни рішення в проєкті. Код рефакторять щотижня, а «переїхати» таблицю на 50 мільйонів рядків без простою — окремий проєкт. Годину, витрачену на ER-діаграму до першого CREATE TABLE, ви окупите десятикратно. Питання, які треба ставити: «Що станеться, коли автор зміниться?», «Чи можуть у поста бути два автори?», «Чи буде цей запит швидким на мільйоні рядків?».

Спробуй сам
  1. Підніміть Postgres у Docker, виконайте DDL блогу, наповніть 3 користувачами, 5 постами, 10 коментарями і 4 тегами.
  2. Напишіть запити: «пости з тегом sql», «користувачі, що коментували чужі пости», «тег, який використовують найчастіше».
  3. Виконайте EXPLAIN ANALYZE для запиту головної сторінки. Видаліть індекс comments_post_id_idx і порівняйте план. Поверніть індекс.
  4. Замініть in-memory репозиторій нотаток із розділу 04 на Drizzle + Postgres. Контролери і сервіси не мають змінитися.
  5. Спробуйте SQL-ін'єкцію на власному API з конкатенацією, потім перепишіть на параметри і переконайтесь, що атака не працює.
  6. Зробіть pg_dump, видаліть базу, відновіть її з дампу. Це єдиний спосіб знати, що бекап справжній.

Перевір себе

Питання
1. Чим первинний ключ відрізняється від зовнішнього?

Первинний ключ (PK) унікально ідентифікує рядок у своїй таблиці. Зовнішній ключ (FK) — колонка, що містить значення PK іншої таблиці і створює зв'язок; база гарантує, що FK посилається на існуючий рядок.

2. Як реалізувати зв'язок «багато до багатьох» між постами й тегами?

Через проміжну (join) таблицю post_tags із двома зовнішніми ключами post_id і tag_id та складеним первинним ключем із них обох.

3. Чим LEFT JOIN відрізняється від INNER JOIN?

INNER JOIN повертає лише рядки, для яких є пара в обох таблицях. LEFT JOIN повертає всі рядки лівої таблиці, а для тих, у кого пари немає, колонки правої заповнюються NULL. «Автори без постів» — це LEFT JOIN із WHERE posts.id IS NULL.

4. Чим WHERE відрізняється від HAVING?

WHERE фільтрує рядки до групування, HAVING — групи після GROUP BY, тому в HAVING можна використовувати агрегати (count(*) > 2), а у WHERE — ні.

5. Чому не варто створювати індекс на кожну колонку?

Кожен індекс сповільнює вставки та оновлення (його треба підтримувати) і займає диск. Індекси на колонках із малою кількістю різних значень майже не допомагають. Створюйте індекси під конкретні повільні запити, підтверджені EXPLAIN ANALYZE.

6. Що гарантує «A» в ACID і як це виглядає у коді?

Atomicity — усі операції транзакції виконуються або жодна. У коді: BEGIN, кілька запитів на одному з'єднанні, COMMIT в разі успіху або ROLLBACK у catch, і client.release() у finally.

7. Чому параметризований запит захищає від SQL-ін'єкції?

Текст SQL і значення параметрів передаються базі окремо: база спершу розбирає команду з плейсхолдерами $1, а потім підставляє значення як літерали. Ввід користувача ніколи не інтерпретується як частина команди.

8. Навіщо міграції, якщо можна змінити таблицю в DBeaver?

Щоб зміни схеми були версійованими, відтворюваними та однаковими на всіх середовищах (ноутбук кожного розробника, CI, продакшен). Міграція — SQL-файл у Git; база зберігає список застосованих, тому команда migrate завжди приводить схему до відомого стану.

Що запам'ятати

  • База даних, а не файл: індексований пошук, паралельний доступ, надійність (WAL), зв'язки та мова запитів.
  • Реляційна модель: таблиці → рядки й типізовані колонки; PK ідентифікує рядок, FK створює зв'язок і охороняє цілісність.
  • Зв'язки: 1:1 (FK + UNIQUE), 1:N (FK на стороні «багато»), N:M (join-таблиця з двома FK).
  • Нормалізуйте до 3НФ (кожен факт в одному місці), денормалізуйте лише свідомо і з планом оновлення дубліката.
  • SQL: SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT; JOIN з'єднує таблиці за FK = PK; UPDATE/DELETE завжди з WHERE.
  • Індекс (B-tree) перетворює повне сканування на кілька кроків; створюйте на FK і під конкретні запити, перевіряйте через EXPLAIN ANALYZE.
  • Транзакції дають ACID: усе або нічого, дані не зникнуть після COMMIT, паралельні операції ізольовані згідно з обраним рівнем.
  • Ніколи не склеюйте SQL із рядків користувача — тільки параметри $1; для назв колонок — білий список.
  • Пул з'єднань один на застосунок; client.release() у finally.
  • Схема в коді (Drizzle) → міграції в Git → однакова база на всіх середовищах; бекап існує лише після успішного відновлення.
  • numeric для грошей, timestamptz для часу, text для рядків, identity для id.
Ресурси для поглиблення
  • PostgreSQL Documentation: Tutorial — офіційний вступ, далі — розділи про індекси та рівні ізоляції. Найточніше джерело.
  • PostgreSQL Tutorial — покрокові уроки з прикладами для кожної конструкції SQL саме в діалекті Postgres.
  • SQLBolt — інтерактивні уроки SQL у браузері; найшвидший спосіб «набити руку» на SELECT і JOIN.
  • PGExercises — задачі на PostgreSQL з перевіркою відповіді: від базових до агрегацій і віконних функцій.
  • Use The Index, Luke! — безкоштовна книга Маркуса Вінанда про індекси та продуктивність SQL. Обов'язкова після цього розділу.
  • Drizzle ORM Docs — схема, запити, міграції drizzle-kit; ми використовуємо Drizzle у наступних розділах.
  • Prisma Docs — альтернативний ORM; корисно знати обидва, бо зустрінете в проєктах.
  • node-postgres (pg) — документація драйвера: пул, параметризовані запити, транзакції.
  • PostgreSQL Wiki: Don't Do This — офіційний перелік антипатернів (timestamp без tz, char(n), money type тощо) з поясненнями.
  • «Designing Data-Intensive Applications», Martin Kleppmann — книга-біблія про зберігання даних: індекси, реплікація, транзакції, консистентність. Читати після рівня «Новачок».
  • DBeaver — безкоштовний графічний клієнт для Postgres та інших баз з ER-діаграмами.
  • roadmap.sh — PostgreSQL DBA — карта тем від основ до адміністрування й реплікації.
